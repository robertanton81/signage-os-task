# Test Review Workflow

**Announce:** "Using /test-review to audit test files for meaningfulness."

## Purpose

`/implement` already runs the `test-quality-reviewer` automatically in Stage 2 whenever the diff touches test files. This skill exists for everything outside that flow:

- Tests written or edited manually outside an `/implement` cycle
- Tests generated by another tool/agent and not yet reviewed
- A periodic audit of the existing suite for accumulated decay
- Reviewing the whole suite before submission

If you ran `/implement` and Stage 2 passed, you do **not** need to run this — the audit already happened.

## Phase 1: Determine Scope

1. If the user passed a path or glob via `$ARGUMENTS`, use it directly.
2. Otherwise, default to the unstaged + staged + last-commit diff:
   ```bash
   git diff --name-only HEAD
   git diff --cached --name-only
   git diff --name-only HEAD~1 HEAD
   ```
   Filter to test files: `*.test.ts`, `*.spec.ts`, anything under `test/` or `tests/`. Also collect non-test source files in the same diff so the reviewer can cross-check coverage.
3. If neither yields anything, ask the user which files to audit.
4. If the scope exceeds 30 test files, ask the user to narrow before proceeding.

## Phase 2: Dispatch the Reviewer

Launch the `test-quality-reviewer` subagent (`subagent_type: "test-quality-reviewer"`, `model: "sonnet"`).

Prompt includes:

- **Test files to review** — list of paths in scope.
- **Source files in scope** — non-test files in the same diff (or, for an ad-hoc audit, the source files those tests import from).
- **Diff context** — `git diff` for the test files. For a non-diff audit (the user asked to review existing tests not in any diff), provide the file contents instead and tell the reviewer it's an existence audit, not a change audit.
- **Reviewer instructions** — the reviewer's own definition under `.Codex/agents/test-quality-reviewer.md` is loaded automatically; you do not need to repeat its rules.

Capture the reviewer's report verbatim.

## Phase 3: Present and Decide

1. Show the reviewer's report to the user.
2. If `Verdict: PASS`, stop. Done.
3. If `Verdict: REVISE` with BLOCKING findings:
   - Ask the user how to proceed: "Fix all blocking findings now?" / "Fix a subset?" / "Stop and let me address them manually?"
   - On "fix now": for each BLOCKING finding, replace the offending test with the reviewer's suggested fix. Use concrete inputs and concrete expected outputs. Do not invent new behavior — if the reviewer says "this test is not meaningful and should assert X instead", and X is unclear from the SUT, ask the user before guessing.
   - After fixes land, re-dispatch the reviewer (max 2 iterations). If still REVISE, present to the user.
4. If only SUGGESTION findings remain, summarize them and let the user decide whether to address.

## Phase 4: Verify

After fixes:

```bash
pnpm --filter @telemetry/<package> test
```

Run scoped to the affected packages; integration tests need `docker compose up -d rabbitmq mongodb` first. If a previously passing test now fails after being made meaningful, that is the reviewer doing its job — the test was masking a real bug. Follow the **Debugging Protocol** from `/implement` (root cause first; do not paper over).

## Notes

- This skill never modifies tests without explicit user approval (Phase 3 step 3).
- This skill never weakens an assertion to make a test pass. If the only way to make a test pass is to weaken it back into meaninglessness, the SUT is broken and the test is doing its job — surface that to the user.
- This skill does not run on production code paths it didn't change. Scope discipline matters.
