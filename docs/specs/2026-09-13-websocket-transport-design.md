## Problem

Devices connect to ingest over raw TCP with one JSON object per line (shared-contract spec, decision 1). That decision was defended with "the Compose network has no firewall or proxy between the emulator and ingest" (shared-contract spec, "WebSocket or HTTP"). The defence optimises for the development environment, and the assignment says Compose is development only. A production signage fleet sits in customer networks behind firewalls and HTTP proxies: for its cloud connection signageOS needs only ports 443 and 80, with 80 as the fallback when TLS on 443 fails (Research). WebSocket over TLS on port 443 is the transport that passes such networks, and the upgrade request is where device identity would go.

On 2026-09-13 the user decided to switch the transport to WebSocket now, before the processing service, for two reasons: it is the transport a senior reviewer expects for this fleet, and every question it raises — framing, liveness, backpressure, the authentication point, TLS at the edge, load balancing, the closing handshake — is a real design decision worth defending, where raw TCP only had "deferred". The switch must not touch what the assignment grades: the message metadata, the freshness rule, the dedup key, the atomic update and the publish path stay exactly as the consistency spec fixes them.

## Chosen Approach

**Replace the TCP line protocol with WebSocket on both ends, and keep everything above the socket as it is.**

- The wire contract becomes "one compact JSON telemetry message per text WebSocket message", bounded by `maxPayload` = 64 KiB. Framing, fragment reassembly and UTF-8 validation move into the protocol; the shared package keeps the message bound, the socket path and `encodeMessage`.
- Ingest accepts upgrades on `/telemetry`, pauses each connection at once, and applies the same reading rule with `pause()` and `resume()`. Liveness is a server ping every 30 s to reading connections; a missing pong closes the connection. Shutdown sends close code 1001 to every device, keeps reading what they already sent, and terminates what is left at the budget.
- The emulator connects with the `ws` client to a pooled address, keeps its outbox and pump, and takes the send callback as its backpressure signal.
- TLS, authentication and load balancing are named at the edge and at the upgrade, not implemented.

**Why this over alternatives:** the assignment's socket connections become the transport a signage fleet uses, with a named place for every production concern, and the consistency mechanism, the publisher and the processing design are untouched. The cost is one dependency, vetted and pinned, and the loss of the "readable with `nc`" property.

## Design

### Wire contract (`packages/shared/src/framing.ts`)

```ts
export const TELEMETRY_SOCKET_PATH = '/telemetry';
/** Upper bound of one message on the wire: the server's maxPayload, the processing body bound. */
export const MAX_FRAME_BYTES = 64 * 1024;
/** One compact JSON message per WebSocket text message. */
export function encodeMessage(message: TelemetryMessage): string;
export function decodeUtf8Strict(bytes: Uint8Array): Utf8DecodeResult; // unchanged, used by processing
```

`FrameDecoder`, `FrameTooLongError`, `FrameRejection`, `FrameDecodeResult` and `encodeFrame` are deleted with their tests. `decodeTelemetryMessage` (`decode.ts`) is unchanged: its caller bounds the text, and here the bound is `maxPayload`. The name `MAX_FRAME_BYTES` stays because the processing spec (decision 14) and its plan use it for the AMQP body bound.

### Ingest server (`apps/ingest/src/server.ts`)

- `http.createServer((request, response) => 404 with `{}`)` bound to `INGEST_HOST:INGEST_PORT`; `listen()` resolves with the bound port and rejects on a bind error, as before.
- `new WebSocketServer({ noServer: true, maxPayload: MAX_FRAME_BYTES, perMessageDeflate: false, clientTracking: false })`.
- `server.on('upgrade', (request, socket, head))`: attach a no-op `'error'` listener to the socket (the README pattern; a reset during the handshake must not throw); if `request.url`'s path is not `TELEMETRY_SOCKET_PATH`, write `HTTP/1.1 404 Not Found\r\n\r\n`, destroy the socket, log at `debug`; otherwise `wss.handleUpgrade(request, socket, head, (ws) => this.#accept(ws, request))`. This listener is the authentication point (decision 14); nothing is checked here today.
- `#accept(ws, request)`: `ws.pause()` first, then `new DeviceConnection({ connectionId, ws, remote: request.socket.remoteAddress:remotePort, ... })`, then the `connection accepted` line and the first application of the reading rule — the same order as today.
- **Liveness interval:** `setInterval(() => this.#pingAll(), config.INGEST_PING_INTERVAL_MS)`, unref'd, started in `listen()` and cleared when the drain finishes, so a server that never listened owns no timer. `#pingAll()`: `connection.checkLiveness()` on every connection; the connection itself skips unless it is reading and its `readyState` is `OPEN`, destroys with reason `unresponsive` when the previous ping was not answered, and otherwise marks awaiting and pings.
- `stats()` unchanged. `shutdown()` as decision 8: `server.close()`, `connection.beginClose()` on each, the drain as today; at the budget `connection.destroy('shutdown')` on the rest; when the drain finishes (either way) `wss.close()` and `clearInterval`. The `http.Server`'s own close callback is not awaited: it fires when the last upgraded socket is gone, which the drain guarantees or forces.

### Ingest connection (`apps/ingest/src/connection.ts`)

```ts
export type CloseReason = 'end' | 'error' | 'protocol' | 'binary' | 'unresponsive' | 'shutdown';

type DeviceConnectionOptions = {
  connectionId: number;
  ws: WebSocket; // paused by the server before this constructor runs
  remote: string;
  publisher: PublishPort;
  window: Window;
  instanceWindow: Window;
  logger: Logger;
  onWindowChange;
  onInstanceWindowChange;
  onMessageConfirmed;
  onClose; // unchanged
};
```

- Listeners: `'message'` (data, isBinary) → `#onMessage`; `'pong'` → `#awaitingPong = false`; `'error'` → `WS_ERR_*` code: `warn` `protocol violation` with `code`, `err`, `connectionId`, `remote`, `lastDeviceId`, reason `protocol`; any other error: `warn` `connection error`, reason `error`; `'close'` (code, reason) → `#open = false`, `#reading = false`, `onClose(this, this.#closeReason ?? 'end')` with `closeCode: code`.
- `#onMessage(data, isBinary)`: binary → `rejected += 1`, `warn` `binary message rejected`, `ws.close(1003, 'text messages only')`, reason `binary`, return. Text → `data` is a `Buffer` (`binaryType` default `nodebuffer`; an `ArrayBuffer` or `Buffer[]` from the `RawData` union is joined with `Buffer.concat` / `Buffer.from` before decoding), `decodeTelemetryMessage(buffer.toString('utf8'))` — `ws` has validated the UTF-8 (`skipUTF8Validation` is `false`), so the substitution the strict decoder guarded against cannot happen — then exactly today's steps: reject-and-log (`message rejected`) or `received += 1`, `lastDeviceId`, both windows `add()`, `publisher.publish({...})`, and the two window callbacks after the message. The caps stay soft (ingest spec, decision 3; T31): `ws` may emit several `'message'` events from one socket read in the same tick (`allowSynchronousEvents`, default `true`), and a `pause()` issued by the window callback takes effect only for the next read, so a window can be exceeded by the messages of one 64 KiB read, exactly as before.
- `applyReadingRule(...)`: returns at once when `!#open` (as today); otherwise the unchanged predicate; on → `ws.resume()`, `#awaitingPong = false`; off → `ws.pause()`. `isReading` and `ws.isPaused` agree.
- `checkLiveness()`: returns at once unless `ws.readyState === WebSocket.OPEN` and the connection is reading; otherwise if `#awaitingPong` → `destroy('unresponsive')`; else `#awaitingPong = true; ws.ping()`. Called by the server's interval for every connection. `readyState` covers every close path (decision 6); `ws.ping()` would not throw on a closing socket anyway — it throws only in `CONNECTING` and otherwise calls the callback, if any, with an error (ws 8.21.3, `lib/websocket.js`, `ping` and `sendAfterClose`; Research) — but the guard keeps a closing device from being destroyed as `unresponsive`.
- `beginClose()`: `ws.close(1001, 'ingest shutting down')` when `ws.readyState === WebSocket.OPEN`; a connection that is already closing on its own (a binary message, a protocol violation, the device's close frame) is left to finish that close, and its reason stays the one already recorded. `ws.close()` on a `CLOSING` socket would be harmless anyway: it returns, or ends the socket when both close frames have already passed (ws 8.21.3, `lib/websocket.js`, `close`; Research). Reading continues under the rule; the connection is `CLOSING` from here on, so no ping reaches it (decision 6). `#open` means "the `'close'` event has not fired": `applyReadingRule` and `destroy` use it, because a `CLOSING` connection still reads and can still be terminated at the budget.
- `destroy(reason)`: no-op when `!#open`; otherwise `#closeReason ??= reason; ws.terminate()` — also on a `CLOSING` connection, which is what the drain budget needs.
- Getters as today minus `pendingBytes`, plus `closeCode` for the log line is passed through `onClose`.

Unchanged: `Window` and `shouldRead`.

### Emulator connection (`apps/emulator/src/connection.ts`)

```ts
type ConnectionState =
  | { name: 'idle' }
  | { name: 'resolving' }
  | { name: 'connecting'; socket: WebSocket }
  | { name: 'connected'; socket: WebSocket; writable: boolean }
  | { name: 'backoff'; attempt: number; timer: NodeJS.Timeout }

```

- `#connect(target, attempt)`: `const socket = new WebSocket(socketUrl(target), { perMessageDeflate: false, handshakeTimeout: this.#connectTimeoutMs })` where `socketUrl` brackets an IPv6 literal (`ws://[::1]:4000/telemetry`); `socket.on('upgrade', (response) => response.socket.setKeepAlive(true, KEEP_ALIVE_DELAY_MS))`; `'open'`, `'error'`, `'close'` as decision 10. `send` is never called before `'open'`.
- `write(text: string): boolean`: state must be `connected` and `writable`, else `false`; `socket.send(text, (error) => { ... })`; after the call, if `socket.bufferedAmount >= SEND_HIGH_WATER_BYTES` the state becomes `writable: false` and this send's callback, when it runs without error and the state is still this connection, sets `writable: true` and calls `onWritable`. A callback with an error does nothing: the `'close'` that follows a dead socket moves the connection to backoff. Returns `true`.
- `dropConnection()`: `terminate()` in `connecting` or `connected`. `stop()`: as decision 10.
- Constants: `KEEP_ALIVE_DELAY_MS` 30 000, `CONNECT_TIMEOUT_MS` 10 000 (now `handshakeTimeout`), `CLOSE_TIMEOUT_MS` 1 000, `RESOLVE_TIMEOUT_MS` 5 000, `SEND_HIGH_WATER_BYTES` 65 536 (documented as Node's default `writableHighWaterMark`, probe p2), backoff constants unchanged.

## Consistency & Failure Modes

## Scaling

- **Ingest:** N stateless instances behind any L7 balancer that forwards the HTTP upgrade; a device may land on any instance, and readiness is checked on `HEALTH_PORT`. In Compose, DNS spreads devices as before (consistency spec, decision 15).
- **Per-connection cost:** the `ws` object and its receiver, up to `maxPayload` (64 KiB) of reassembly buffer for one in-flight message, and the socket buffers a paused connection accumulates during an outage (as before). One ping and one pong per reading connection per 30 s: two control frames, no application work.
- **Per-message cost:** frame parsing, unmasking and UTF-8 validation in `ws` (JavaScript on Node 24, `buffer.isUtf8` for the validation), then the same `safeParse` as before. The NDJSON scan disappears. `permessage-deflate` is off, so no compression cost and no compressed bandwidth saving (T51).
- **Emulator:** unchanged; the send callback replaces the `'drain'` event at the same buffer bound.

## Alternatives Considered

### Keep raw TCP with NDJSON

The previous design. Rejected for the reasons in "Problem": it has no place for authentication, no passage through HTTP proxies, and its framing, liveness and close semantics were hand-written where the protocol provides them. Its one advantage, the `nc`-readable wire, is T50.

### Node's built-in `WebSocket` client in the emulator

Zero dependencies on the device side. Rejected: the WHATWG API has no send callback and no drain event, so backpressure would need a timer polling `bufferedAmount` per paused device; no ping or pong is visible; there is no handshake timeout, so the connect timeout would again be hand-rolled around `close()` in `CONNECTING`; every failure fires an `error` event with an empty message, so a refused port, a 404 and a bad handshake are indistinguishable in the log (Research: node-client §A5, §A6). The library the server already uses gives all four.

### `/readyz` on the device port

One port fewer. Rejected in decision 13.

### An application idle timer instead of pings

Re-arm a timer on every message, as the TCP idle timeout did. Rejected in decision 6: it cuts a device that is alive and has nothing to say, and it cannot tell a dead peer from a quiet one. The protocol has a liveness primitive for exactly this.

### TCP keepalive on the server side, kept next to the pings

Belt and braces. Rejected: keepalive is invisible through a proxy that terminates TCP, its detection time on Linux defaults is about eleven minutes, and the ping already covers the case. The emulator keeps keepalive because it has no ping of its own (T54).

### The `server` option of `WebSocketServer` instead of `noServer`

Less code. Rejected in decision 4: the path check moves into `shouldHandle` and there is no natural place for the authentication of decision 14.

### `permessage-deflate`

Rejected for now (T51).

### Custom close codes in the 4000–4999 range

For example 4000 for "contract violation". Rejected: the RFC's own codes say what happened (1003, 1007, 1009, 1001) and every client library maps them; a private code needs documentation the standard ones do not.
