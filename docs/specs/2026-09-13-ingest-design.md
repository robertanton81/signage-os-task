## Problem

Ingest is the only component that faces devices and the only producer on the queue. The consistency spec already fixes its contract: validate every frame with the shared schema, publish the message with publisher confirms, pause device sockets when the broker is unavailable or a confirm window is full, hold no per-device state, and drain on SIGTERM (consistency spec, decisions 12, 14 and 15, and its "Ingest" section). The shared-contract spec fixes the wire framing (NDJSON, `FrameDecoder`, `decodeTelemetryMessage`) and the client library (amqplib 2.0.1).

What is not decided anywhere, and what this spec decides:

- how a paused socket, its idle timer and the two confirm windows work together without flapping and without mass disconnects;
- how unconfirmed messages are tracked, so that nothing is dropped when a device or the broker disconnects;
- the reconnect state machine and what counts as a broker failure — in amqplib 2.0.1 a nack and a channel close arrive through the same callback, and a publish on a closed channel throws;
- the exact AMQP message properties, the readiness signal for Compose, the shutdown order, the configuration and the test strategy.

The research for this spec also found that one premise of the earlier specs is out of date: amqplib has offered opt-in automatic recovery since 1.1.0 (2026-05-09). Decision 9 evaluates it.

| 12  | What counts as a broker failure         | **One recycle rule.** Triggers: connection `close` or `error`; channel `close` or `error`; a publish callback with an error (a nack, or amqplib failing unconfirmed callbacks on close); a `return`; a confirm stall (decision 15); a throw from `channel.publish`. Effect, from `ready`: mark not ready (the reading rule pauses every socket), increase the generation — **every** generation increase, here and at the start of every connect attempt, runs `ledger.lose()`, so no `sent` entry can outlive its generation — then close the model within `AMQP_CLOSE_TIMEOUT_MS` (2 000) unless it has already emitted `close`, and enter `backoff`. A close that rejects counts as finished and is logged at `debug`. While `connecting`, a trigger fails the attempt instead (Design, "The publisher"). Callbacks and events of an older generation are ignored; a trigger during `recycling` or `backoff` does nothing. Event handlers change state synchronously and never call into amqplib synchronously: the model close is scheduled with `setImmediate`. Every recycle is logged at `warn` with its trigger; model and channel `error` events at `error`. A `handler-error` listener on the connection and the channel logs at `error` and recycles. | Replaces the consistency spec's "On `basic.nack` from the broker the message is re-published once, then logged at error level and dropped". A nack means "an internal error occurs in the Erlang process responsible for a queue", after which "the client may choose to re-publish" (confirms guide), and the streaming-confirms recipe schedules nacked messages for republishing (publishers guide) — dropping after one retry would lose data in exactly the queue-trouble case. amqplib calls the publish callback with `new Error('message nacked')` for a nack and with `new Error('channel closed')` for every unconfirmed message when the channel closes (`lib/channel.js`), so one path for both removes a classification by error text. The synchronous-state rule exists because amqplib runs listeners through `safeEmit`, which rethrows a listener's exception into its frame processing when no `handler-error` listener is registered (`lib/safe_emit.js`), and because `publish` on a closed channel throws `IllegalOperationError` (`lib/channel.js`, `invalidateSend`; amqplib's own test "publish on closed channel does not leak callbacks" wraps the call in `try`). The amqplib documentation says the callback receives an error in that case; in the 2.0.1 source `ConfirmChannel#publish` runs the plain publish, which throws on a closed channel, **before** it records the callback, so the callback is never called (`lib/channel_model.js`). The design depends on neither reading: an entry is marked `sent` only when the generation is unchanged after `publish` returns, and every generation increase moves `sent` entries back to `pending`. The common triggers — broker restart, heartbeat timeout, a channel closed by the broker — reach ingest after amqplib has already closed the model, and `close()` on such a model rejects with `IllegalOperationError` (`lib/connection.js`, `toClosed`); the recycle therefore skips the close when the model has emitted `close`, and treats a rejection as finished, so that no recycle can end in an unhandled rejection and exit code 1. A returned message is saved as well: RabbitMQ sends the `basic.return` before the `basic.ack` (confirms guide), and the return handler moves the entry back to `pending` and increases the generation synchronously, so the ack that follows is ignored and the message is published again once the recycle has declared the topology. It is logged at `error` with its identity. A routing fault that returns every message therefore becomes a slow recycle loop with `error` lines — no ack is ever accepted, so the backoff grows to its cap (decision 13) — rather than silent loss (T30). |

Resetting on connect would let a loop that connects and then fails at once — a queue that nacks everything, a stall — retry every 500 ms or less forever. The flag belongs to one connection: a `blocked` that arrives while the attempt is still `connecting` is carried into `ready`, and the next attempt starts with the flag cleared, so a recycle can never leave an instance "ready but blocked" for good.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | During a resource alarm RabbitMQ stops reading from publishing connections, and "Connection heartbeat monitoring will be deactivated, too" (alarms guide), so a long alarm does not turn into a heartbeat-driven reconnect loop. ## Chosen Approach

**A stateless TCP front with one reading rule, and a publisher that keeps every message until the broker acks it.**

- Each device connection decodes NDJSON frames, validates them with the shared decoder and hands valid messages to the publisher. Invalid frames are logged and dropped; an oversized line closes the connection.
- Whether a socket reads is one predicate over three inputs — publisher ready, connection window open, instance window open — evaluated when an input changes. Windows close at their cap and reopen at half of it. A paused socket has no idle timer.
- The publisher owns one AMQP connection and one confirm channel and keeps every message in an instance-wide ledger until it is acked. Every failure — connection or channel closed, a nack, a return, a stall — takes one recycle path: pause, close, back off, reconnect, declare the topology, re-publish the ledger, resume. The publisher's state machine is a pure function, tested per transition and per race sequence; the amqplib code only maps events and runs effects.
- Readiness is served on `/readyz` for Compose. SIGTERM stops accepting, half-closes every device connection and keeps reading until the devices have closed and the ledger is empty, within the budget; then it closes what is left, the broker connection and the health server.

**Why this over alternatives:** every broker-side failure maps to the same recovery path, so a broker restart, a nack, a stuck queue and a deleted queue behave the same and are tested once. Nothing is dropped on the broker side — even a returned message is published again after the topology has been declared again. Nothing is keyed by device, so capacity grows by adding replicas. The main alternative, amqplib's built-in recovery, would replace the reconnect loop but none of the channel, ledger or re-publish logic, and would split readiness across two state machines.

### The port between sockets and the broker

```ts
type PublishRequest = {
  message: TelemetryMessage;
  receivedAt: number;
  /** Runs once, when the broker acks the message. Never runs for a message that is not acked. */
  onConfirmed: () => void;
};

type PublishPort = {
  /** Adds the message to the ledger and sends it when the publisher is ready. */
  publish(request: PublishRequest): void;
  /** Publisher ready (decision 17): connected, confirm channel open, topology declared, not blocked. */
  readonly isReady: boolean;
  /** Called on every change of `isReady`; returns a function that unsubscribes. */
  onReadyChange(listener: (ready: boolean) => void): () => void;
  /** Number of ledger entries, for the summary line and the shutdown drain. */
  readonly unconfirmed: number;
  /** Stops reconnecting and closes the connection; resolves within AMQP_CLOSE_TIMEOUT_MS whatever the state. */
  stop(): Promise<void>;
};
```

`publish` takes one object because it has three inputs (shared-contract decision 14; `max-params` in `eslint.config.js`).

### One frame, from socket to ledger

1. A `data` chunk arrives on a reading socket and goes to `decoder.push(chunk)`.
2. Every frame goes to `decodeTelemetryMessage(frame)`.
   - Rejected: `rejectedMessageLogger(logger, result.identity).warn({ connectionId, reason, detail }, 'frame rejected')`, and `rejected` grows by one.
   - Valid: `received` grows by one, `lastDeviceId` becomes `message.deviceId`, both windows `add()`, and `publisher.publish({ message, receivedAt: Date.now(), onConfirmed })`.
3. If `push` returned `ok: false`: a `warn` line with `connectionId`, `remote`, `bytes` and `limit`, then the socket is destroyed with close reason `frame_too_long`.
4. If a window closed during the chunk, the server applies the reading rule: to this socket for its connection window, to every socket for the instance window.

`onConfirmed` always removes the message from the instance window, and from the connection window only while that connection still exists (decision 11); the server applies the rule again when a window reopened.

### Windows and the reading rule (`flow.ts`, `server.ts`)

```ts
class Window {
  constructor(cap: number); // closes when size reaches cap, reopens when size falls to Math.floor(cap / 2)
  add(): 'closed' | 'unchanged';
  remove(): 'reopened' | 'unchanged';
  readonly isOpen: boolean;
  readonly size: number;
}

function shouldRead(input: {
  publisherReady: boolean;
  connectionWindowOpen: boolean;
  instanceWindowOpen: boolean;
}): boolean;
```

A connection records whether it is reading, so applying the rule twice changes nothing. Turning reading on is `socket.resume()` then `socket.setTimeout(INGEST_SOCKET_IDLE_MS)`; turning it off is `socket.pause()` then `socket.setTimeout(0)`. A new connection starts with reading off (it was accepted paused), and the rule is applied once right after it is registered.

| Change                                   | Sockets the rule is applied to |
| ---------------------------------------- | ------------------------------ |
| A connection is accepted                 | That socket                    |
| Its connection window closed or reopened | That socket                    |
| The instance window closed or reopened   | Every socket                   |
| The publisher's readiness changed        | Every socket                   |

Shutdown is not in the table: it half-closes the connections and leaves reading to the rule (decision 19).

### The ledger (`ledger.ts`)

```ts
type LedgerEntry = {
  readonly id: number; // instance-local counter; the Map that holds entries keeps insertion order
  readonly args: PublishArgs; // from toPublishArgs: exchange, routingKey, content, options
  readonly onConfirmed: () => void;
  state: { name: 'pending' } | { name: 'sent'; generation: number };
};
```

| Operation                     | Effect                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| `add({ args, onConfirmed })`  | Creates a `pending` entry and returns it                                                    |
| `pending()`                   | The `pending` entries in insertion order                                                    |
| `markSent(entry, generation)` | `pending` becomes `sent` on that generation                                                 |
| `confirm(entry)`              | Removes the entry and calls its `onConfirmed`                                               |
| `lose()`                      | Every `sent` entry becomes `pending` again; runs on every generation increase (decision 12) |
| `size`, `sentCount`           | Counts                                                                                      |

`StallClock` (decision 15) reads `sentCount`: `onSent(now)` starts the waiting time when `sentCount` rises from zero; `onAck(now)` restarts it while entries remain `sent` and stops it otherwise; `restart(now)` is called on entering `ready` and on `unblocked`; `isStalled(now, timeoutMs)` is true when the waiting time is longer than `timeoutMs`.

### The publisher (`publisher-state.ts`, `publisher.ts`)

The state machine is pure: `transition(state, event)` returns `{ state, effects }` and touches neither amqplib, nor timers, nor the ledger. `publisher.ts` turns amqplib events and the outcomes of its own asynchronous work into events, and runs the effects in order. Every table row and every race sequence below is a unit test of `transition` (`publisher-state.test.ts`).

```ts
type PublisherState =
  | { name: 'connecting'; generation: number; attempt: number; failed: boolean; blocked: boolean }
  | { name: 'ready'; generation: number; attempt: number; blocked: boolean; readySince: number }
  | { name: 'recycling'; generation: number; attempt: number; reason: string }
  | { name: 'backoff'; generation: number; attempt: number; reason: string }
  | { name: 'stopped'; generation: number };

type PublisherEvent =
  | { type: 'backoff_elapsed'; generation: number }
  | { type: 'attempt_succeeded'; generation: number; now: number }
  | { type: 'attempt_failed'; generation: number; reason: string }
  | { type: 'trigger'; generation: number; reason: string; now: number } // any recycle trigger of decision 12
  | { type: 'close_finished'; generation: number }
  | { type: 'blocked'; generation: number; reason: string }
  | { type: 'unblocked'; generation: number }
  | { type: 'stop' };

type Effect =
  | { type: 'start_attempt' } // run the connect sequence of decision 10
  | { type: 'lose' } // ledger.lose()
  | { type: 'send_pending' } // publish every pending entry in insertion order
  | { type: 'restart_stall_clock' }
  | { type: 'close_model' } // setImmediate, then close within AMQP_CLOSE_TIMEOUT_MS unless the model already emitted close
  | { type: 'start_backoff'; attempt: number; reason: string } // timer of backoffDelay({ attempt, baseMs: 500, maxMs: 10_000, random }); one warn line with reason, attempt and delay
  | {
      type: 'log';
      level: 'debug' | 'info' | 'warn' | 'error';
      message: string;
      fields: Record<string, unknown>;
    };
```

The initial state is `backoff` with `generation` 0 and `attempt` 0; `start()` dispatches `backoff_elapsed` at once. Readiness is derived, not stored: `isReady(state)` is true only in `ready` with `blocked` false, and the shell notifies `onReadyChange` listeners whenever the derived value changes. Every event that carries a `generation` is ignored — same state, no effects — when it is not the current one; that one rule covers every stale callback: an ack after a return, the `close` of a model that was just recycled, a stall check that ran late. A current-generation pair of state and event that has no row below is also ignored: same state, no effects. The test walks every state against every event and asserts exactly that for every unlisted pair, so a pair that matters cannot go undefined by accident.

| From                         | Event               | To                                                                                                        | Effects                                                     |
| ---------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `backoff`                    | `backoff_elapsed`   | `connecting`, `generation + 1`, `failed` false, `blocked` false                                           | `lose`, `start_attempt`                                     |
| `connecting`, `failed` false | `attempt_succeeded` | `ready`, `blocked` carried over, `readySince = now`                                                       | `send_pending`, `restart_stall_clock`, `log info connected` |
| `connecting`, `failed` true  | `attempt_succeeded` | `backoff`, `attempt + 1`                                                                                  | `close_model`, `start_backoff` (reason: the trigger)        |
| `connecting`                 | `attempt_failed`    | `backoff`, `attempt + 1`                                                                                  | `start_backoff` (reason)                                    |
| `connecting`                 | `trigger`           | `connecting`, `failed` true, reason kept                                                                  | `log debug`                                                 |
| `connecting`                 | `blocked`           | `connecting`, `blocked` true                                                                              | `log warn` (reason)                                         |
| `connecting`                 | `unblocked`         | `connecting`, `blocked` false                                                                             | `log info`                                                  |
| `ready`                      | `trigger`           | `recycling`, `generation + 1`, `attempt` 0 if `now − readySince ≥ 10 000` else `attempt + 1`, reason kept | `lose`, `close_model`                                       |
| `recycling`                  | `close_finished`    | `backoff`                                                                                                 | `start_backoff` (reason: the trigger)                       |
| `ready`, `blocked` false     | `blocked`           | `ready`, `blocked` true                                                                                   | `log warn` (reason)                                         |
| `ready`, `blocked` true      | `unblocked`         | `ready`, `blocked` false                                                                                  | `restart_stall_clock`, `log info`                           |
| `recycling`, `backoff`       | `trigger`           | unchanged                                                                                                 | `log debug`                                                 |
| any but `stopped`            | `stop`              | `stopped`, `generation + 1`                                                                               | `close_model` (except from `backoff`), `log info`           |
| `stopped`                    | anything            | unchanged                                                                                                 | none                                                        |

Race sequences the test covers, each as a sequence of events with the expected states and effects: a `trigger` during `connecting` makes the later `attempt_succeeded` fail the attempt, so a model that was opened during a failing attempt is closed and never serves as `ready`; every event of an older generation is ignored in every state; `lose` is emitted on every generation increase — `backoff_elapsed` and `trigger` from `ready` — so entries marked `sent` under a generation that is gone are `pending` again before the next attempt sends anything; a `blocked` during `connecting` produces a `ready` that is not ready, an `unblocked` that follows while still `connecting` produces a `ready` that is ready, and the next `backoff_elapsed` starts with `blocked` false; `close_finished` from `recycling` always starts the backoff, whichever of the four close paths (skipped, resolved, rejected, timed out) produced it — the event is the same, so the machine has no fifth path; `trigger` from `ready` resets `attempt` exactly at the 10 000 ms boundary and raises it below; `stop` from every state ends in `stopped`, after which nothing changes the state.

The shell (`publisher.ts`) holds the current state, the ledger, the stall clock, the timers, and the amqplib model and channel it last opened — they belong to the generation that opened them and are kept until `close_model` has run for them, because a `trigger` from `ready` raises the generation before the close:

- **`start_attempt`** runs the connect sequence of decision 10 with the generation it started under. After each `await`, and once more before dispatching `attempt_succeeded`, it checks that the state is still `connecting` with that generation and `failed` false; otherwise it closes what it has opened (bounded by `AMQP_CLOSE_TIMEOUT_MS`, a rejection ignored) and dispatches `attempt_failed`, or nothing when the state is `stopped`. A throw or a timeout in the sequence closes what was opened the same way and dispatches `attempt_failed`. Listeners are attached as soon as the model and then the channel exist, and each dispatches with the generation it was attached under: model `error` and channel `error` are logged at `error` (no event of their own — the `close` that follows is the trigger); model `close`, channel `close`, channel `return` (logged at `error` with the message identity first) and `handler-error` (logged at `error`) dispatch `trigger`; model `blocked` and `unblocked` dispatch their events.
- **`send_pending`** and `publish(request)` send through one function: capture the current generation, call `channel.publish(exchange, routingKey, content, options, callback)` inside `try`, and mark the entry `sent` on that generation **only if the generation is still current** when `publish` returns; a throw dispatches `trigger` and leaves the entry `pending`. `publish(request)` adds the entry to the ledger and sends it at once in `ready`, blocked or not; in every other state the entry waits for the next `send_pending`. The callback carries its generation: with `err === null` it confirms the entry and calls `stallClock.onAck`; with an error it dispatches `trigger`.
- **`close_model`** runs on `setImmediate` (never inside an amqplib listener) for the model kept by the shell. Four paths, one outcome: the model has already emitted `close` (skip, the common case after a broker restart or heartbeat timeout), `model.close()` resolves, it rejects (logged at `debug`), or the `AMQP_CLOSE_TIMEOUT_MS` bound runs out (logged at `warn`). On **every** path, exactly once, it drops the model reference and dispatches `close_finished` with the generation of the recycle; that event is the only way out of `recycling`, so the effect may not end without it. When the state is `stopped` the same completion resolves the pending `stop()` promise.
- **`start_backoff`** computes the delay with the shared `backoffDelay` and `Math.random`, writes the one `warn` line of the failure — reason (the recycle trigger or the attempt's error), attempt number, delay — and dispatches `backoff_elapsed` from the timer. `stop` clears the timer. The `recycling` and `backoff` states carry the reason so that this line can name it.
- **`stop()`** dispatches `stop` and returns a promise that resolves when `close_model` has completed, at once from `backoff`, and in every case no later than `AMQP_CLOSE_TIMEOUT_MS` after the call: the promise is raced against that bound. From `connecting`, an attempt that is still inside `connect()` or a declaration cannot be interrupted (both are bounded by 10 s, longer than the close budget); the attempt is abandoned, and when it sees `stopped` at its next check it closes what it opened without anyone waiting — or the socket dies with the process. The stop therefore never exceeds `SHUTDOWN_TIMEOUT_MS + AMQP_CLOSE_TIMEOUT_MS` (decision 19). `stop()` is never called twice (the shared lifecycle handler exits on the second signal).
- **The stall check** runs on an unref'd interval of `confirmTimeoutMs / 3`, only in `ready` with `blocked` false, and dispatches `trigger` with reason `confirm_stall` when `stallClock.isStalled(now, confirmTimeoutMs)`.

### Health endpoint (`health.ts`)

`readinessReport({ publisherState, shuttingDown })` is pure, takes the `PublisherState` value (the blocked flag lives inside it, decision 14) and returns `{ ready: true }` or `{ ready: false, reason }`. The reason is `shutting_down` when shutting down, otherwise `blocked` for `ready` with `blocked` true, otherwise `connecting` for every publisher state other than `ready` (`connecting`, `recycling`, `backoff`, `stopped`).

`startHealthServer({ port, report, logger })` creates a `node:http` server listening on `HEALTH_PORT` on all interfaces. `GET /readyz` answers 200 or 503 with a JSON body and `content-type: application/json`; every other method or path answers 404. It returns `close()`, which calls `server.close()` and then `server.closeAllConnections()`. All interfaces, because the Compose healthcheck runs inside the container and a developer may call it through a published port. Step 6 chooses the healthcheck command; the endpoint needs nothing but an HTTP GET.

### Startup (`main.ts`)

1. `loadIngestConfig()`. A `ConfigError` ends the process; the call is not wrapped in `try`.
2. `createLogger({ service: 'ingest', level: LOG_LEVEL })`; log the effective configuration.
3. Install the shared lifecycle handlers for SIGTERM, SIGINT, `unhandledRejection` and `uncaughtException`.
4. Start the health server; it answers 503 until the publisher is ready.
5. Create the publisher and start its connect loop. The loop never throws; every failure goes to `backoff`.
6. Start the device server on `INGEST_HOST:INGEST_PORT`.
7. Start the summary interval (unref'd, every 10 seconds).

A failure to listen on `HEALTH_PORT` or `INGEST_PORT` is logged at `fatal` and ends the process with exit code 1. The health server starts first, so Compose sees a 503 rather than a refused connection while the rest starts. No step waits for the broker (decision 1).

### Shutdown (`server.ts`, `main.ts`)

Decision 19 gives the order. The drain resolves when the set of connections is empty and `publisher.unconfirmed` is 0; the two conditions are checked once when the drain starts — the normal case when the devices were stopped first, which must not wait for the budget — then when a connection closes and when a message is confirmed, and one timer of `SHUTDOWN_TIMEOUT_MS` ends the wait — no polling. Half-closed connections keep reading under the rule and keep their idle timers. When the timer ends the wait, the `warn` line carries `openConnections` and `unconfirmed`, and each remaining socket is destroyed with close reason `shutdown`. Then `publisher.stop()` and the health server's `close()` run. The whole stop takes at most `SHUTDOWN_TIMEOUT_MS` plus `AMQP_CLOSE_TIMEOUT_MS`, which is what step 6's `stop_grace_period` must exceed (decision 19).

A socket that is paused when shutdown starts — because the publisher is not ready — still gets its FIN, but ingest does not see the device's close until it reads again, so during a broker outage the drain runs until the budget ends (T28).

## Consistency & Failure Modes

Ingest carries the identity and order metadata but decides nothing about freshness. Its job is to lose nothing it has accepted and to add nothing that changes meaning.

**Metadata that carries identity and order:** `deviceId`, `sessionId` and `seq` in the body, unchanged from the device (consistency spec, decisions 1–3). Ingest adds only `messageId` (the identity string, for operators), `timestamp` (seconds) and `x-received-at` (milliseconds, stored by processing as `receivedAt`); none of them decides order.

**How "newer" is decided, and where the dedup key is enforced:** not in ingest, but in processing's conditional update and unique indexes (consistency spec, decisions 8 and 9). Ingest keeps no dedup state, because a duplicate may arrive through another instance.

**Atomic operations:** none in ingest. A publish is not atomic with the device's send; the at-least-once chain — ledger until the broker ack — plus idempotent storage makes that harmless.

**Delivery semantics:** device to ingest is fire-and-forget (T3). Ingest to broker is at-least-once: a message leaves the ledger only on a broker ack, and every other outcome publishes it again (decisions 11 and 12). The duplicates this creates are absorbed at the storage boundary (invariant 2).

## Scaling

- **Instances:** any number, all equivalent. A device chooses an instance at connect time through DNS (consistency spec, decision 15). Ingest holds no device-keyed state, so adding or removing an instance needs no coordination, and a device that lands on another instance after a reconnect is a normal case.
- **Limits of one instance:** open sockets (file descriptors, no cap: T27); CPU per message — JSON parse, zod validation, JSON encode and one publish (T12); one AMQP connection and one channel, whose confirm throughput bounds the instance (T32). Nothing is measured in this step, so no bottleneck is claimed and no optimisation is designed.
- **Memory of one instance:** per connection a decoder tail of at most 64 KiB plus the socket buffers; a paused socket keeps reading into its stream buffer up to the 64 KiB high-water mark plus one 64 KiB chunk before the handle stops (Node `lib/net.js`, `stream_base_commons.js`), so a long outage costs up to about 192 KiB of user-space memory per connection, plus the kernel buffers — 1.83 GiB for 10 000 connections in the worst case (T27, T37); instance-wide at most `INGEST_MAX_UNCONFIRMED_TOTAL` bodies plus one chunk — about 3.5 MiB for typical messages and 129 MiB for worst-case valid ones, up to twice that while messages wait unflushed in amqplib's write buffer, which holds its own copy (decision 16).
- **Scale-down:** SIGTERM half-closes the connections; devices that close on FIN reconnect elsewhere without loss (decision 19).
- **Cost of the consistency mechanism in ingest:** one ledger entry per message (a `Map` insert and delete), one callback per confirm, and publishing the ledger again after a recycle. No message waits for another: publishing does not wait for confirms (decision 8), and a device pauses only when a window is full or the broker is not ready.
- **Noisy devices:** one device can fill only its own connection window, but the instance window is shared, so a few very noisy connections can pause every other connection on the same instance (T35).

## Invariants (`CLAUDE.md`) and ingest's part in each

| Invariant                                                | Ingest's part                                                                                                                                                                                          |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Logical order wins                                    | Passes `sessionId` and `seq` through unchanged; order is decided in processing. Publishing the ledger again after a recycle can reorder messages on the queue, which the storage guard makes harmless. |
| 2. Duplicates have no effect                             | Ingest creates duplicates on purpose (publishing again after a recycle) and relies on the storage boundary; it keeps no dedup state that another instance could not see.                               |
| 3. Atomic state updates                                  | Not touched: ingest writes no state.                                                                                                                                                                   |
| 4. Parallel across devices, serial within one            | Connections are independent and nothing is serialised per device. Messages of one connection go out on one channel in arrival order, but correctness does not depend on that.                          |
| 5. Minimal throughput cost                               | Streaming confirms; a socket pauses only for a full window, a blocked broker or no broker; the gap between closing and reopening a window avoids pause churn per message.                              |
| 6. Both services scale horizontally; ingest is stateless | No device-keyed state; per-connection state dies with the connection; ledger entries are per message and bounded (decisions 11 and 21).                                                                |

## Alternatives Considered

### amqplib's opt-in recovery (`connect(url, { recovery })`)

Available since 1.1.0. It would replace the connect loop and the backoff timer. It would not re-create the confirm channel, declare the topology on it, publish the ledger again or notice a channel that closes while its connection stays open, so ingest would keep all of that and track readiness across two state machines. With recovery, `connect()` resolves only after the first successful connection, so the first failures cannot be observed (#858), and the delay cannot be Full Jitter (#855, #857). Revisit if the library gains channel and publisher recovery (decision 9).

### Pausing every socket at shutdown and draining only the ledger

Simpler, with one wait condition instead of two. It loses every frame that devices have written and ingest has not read, on every planned stop, although the probe shows that a device like the emulator closes cleanly on a FIN. Rejected (decision 19).

### Buffering in ingest during a broker outage, or closing device connections

Rejected by the consistency spec (decision 14): a buffer is per-instance state that a crash loses, and closing sends devices to other instances that have the same broker problem.

### Listening only after the first broker connection

Devices would get refused connections and wait in their backoff. It adds a startup path and helps nothing, because accepted connections wait paused anyway (decision 1).

### Forwarding the raw frame bytes as the body

Saves one `JSON.stringify` per message. A valid message padded with whitespace up to 64 KiB would pass through, and the memory bound of the windows would grow almost tenfold (decision 6).

### "Re-publish once, then drop" on a nack

The consistency spec's original rule. It drops data in exactly the situation a nack signals — trouble in the queue process — and needs a way to tell a nack from a channel close, which amqplib reports through the same callback (decision 12).

### A channel per device connection

Each channel is a broker process with its own confirm sequence; a large fleet would reach the channel limit, and every reconnect would open and abandon one. One channel per instance with one ledger has neither problem (decision 8).

### Stopping in the middle of a chunk when a window closes

Makes the caps exact, but needs a per-connection queue of decoded frames waiting for the window to reopen — a buffer the design avoids everywhere else — to gain at most one chunk (decision 3, T31).

### A liveness endpoint next to readiness, or a readiness file

Compose runs one healthcheck per service, and a blocked event loop fails the readiness request as well. A file cannot be checked with a real request in tests, and a file can survive the crash it should have reported (decision 17).

### Integration tests against RabbitMQ in step 4

Would test the adapter earlier, but would make `pnpm test` need Docker before step 7 decides how integration tests run, and would settle step 6 and step 7 questions inside the ingest spec (decision 25, T36).
