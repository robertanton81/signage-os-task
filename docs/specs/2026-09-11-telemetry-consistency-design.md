## Problem

Many devices send telemetry over long-lived socket connections. Messages pass through stateless ingest instances and a RabbitMQ queue to several processing instances that store every event and keep one "current state" per device in MongoDB. The assignment requires that the final state of a device reflects the logical order of the unique events the device produced: an older message must never overwrite newer known state, and a duplicated or redelivered message must never cause a second business effect (a counter counted twice, an alert created twice, an inconsistent state). Both services must scale horizontally, devices must be processed in parallel, and the consistency mechanism must cost as little throughput as possible.

Everything downstream — the shared contract (step 2), the emulator (step 3), ingest (step 4), processing (step 5), the Compose topology (step 6), the integration tests (step 7) and the README (step 8) — depends on the answers in this spec. Nothing in the repository decides them yet.

| 7   | What is the "current state" of a device and how is it stored?   | One document per device in `device_state`, `_id = deviceId`, with **one sub-document per section** (`status`, `metrics`, `counters`, `diagnostic`). | 8   | What is the freshness rule?                                     | Apply an event to section `T` if and only if `T` is absent or `(event.sessionId, event.seq) > (T.sessionId, T.seq)` lexicographically. Equal keys are duplicates and are not applied. The comparison is evaluated **by the server inside the update** — an aggregation-pipeline update whose `$cond` keeps the stored section unless the event is newer — never in application code that read first.                                                                                                                                                                                       | MongoDB evaluates an update against the document as it is at that moment and applies it atomically, so a comparison inside the update is a lost-update guard without a read. The classic variant — the comparison in the update **filter** — was rejected for the upsert case: when the stored section is newer, the filter matches nothing, the upsert tries to insert a second document with the same `_id`, and the server fails with duplicate key error 11000 (manual, "Upsert with Unique Index"). Every stale message would then cost an error plus a retry round trip. | 9   | Where is deduplication enforced?                                | At the storage boundary, three times, each idempotent: (a) `events` has a **unique index on `(deviceId, sessionId, seq)`**, so a second insert fails with duplicate key error 11000 and is treated as "already stored"; (b) `alerts` uses the message identity string as `_id`, so a second alert insert fails the same way; (c) `device_state` applies the freshness rule, under which a duplicate is "not newer" → no-op.                                                                                                                                                                | Dedup must live in the database, not in process memory, because the duplicate may arrive at a different processing instance than the original. ## Chosen Approach

**One queue, competing consumers, and correctness at the write.** Every message carries `(deviceId, sessionId, seq)` created on the device. Ingest validates and publishes it unchanged to one quorum queue with publisher confirms. Any number of processing instances consume the queue with a prefetch limit. For each delivery the handler runs three idempotent single-document writes in a fixed order — insert the event (unique index rejects duplicates), apply the event's section to the device's state document with a conditional update that replaces the section only when the event is newer than the stored one, and, for error diagnostics, insert an alert keyed by the message identity — and acknowledges the delivery afterwards. Two messages of the same device may be processed at the same time by two instances; whichever writes second either has a newer key and wins, or has an older or equal key and changes nothing. No lock, no routing, no transaction, no coordination between instances.

**Why this over alternatives:** the assignment's four hard problems (order, duplicates, atomicity, parallelism) are all answered by two properties chosen in the contract — absolute-valued typed events and a device-generated order key — plus one storage rule (compare in the filter). Everything else (routing, locks, buffering, transactions) would protect against problems that the contract already made impossible, and each would cost throughput or scaling freedom. The two alternatives below stay documented as upgrade paths with the trigger that would justify them.

## Research (source links)

RabbitMQ (series 4.3, current per [release information](https://www.rabbitmq.com/release-information), latest 4.3.5 of 2026-08-17; the full research notes with quotes per item are kept in `.local/research/` — gitignored, not part of the submission):

- [Consumer acknowledgements and publisher confirms](https://www.rabbitmq.com/docs/confirms) — manual `basic.ack`/`basic.nack`/`basic.reject`; "any delivery (message) that was not acked is automatically requeued when the channel (or connection) on which the delivery happened is closed"; redeliveries carry `redelivered=true`; automatic ack "should be considered unsafe"; `basic.ack` for a persistent message to a durable queue is sent after persisting to disk, for quorum queues after a quorum of replicas accepted it; confirms can arrive out of order; the publish-and-wait strategy is an anti-pattern.
- [Reliability guide](https://www.rabbitmq.com/docs/reliability) — with acks: at least once; without: at most once; after a reconnect, re-publishing unconfirmed messages can duplicate, "therefore consumer applications will need to perform deduplication or handle incoming messages in an idempotent manner".
- [Consumer prefetch](https://www.rabbitmq.com/docs/consumer-prefetch) — prefetch applies per consumer by default; "Values in the 100 through 300 range usually offer optimal throughput"; prefetch 1 "will significantly reduce throughput"; quorum queues reject global QoS and cap prefetch at 2,000.
- [Consumers](https://www.rabbitmq.com/docs/consumers) — delivery acknowledgement timeout (default 30 minutes, quorum queues only since 4.3: the channel is closed and outstanding deliveries requeued); single active consumer semantics and failover; the message properties table (`delivery_mode` 2 = persistent, `message_id` "arbitrary", `timestamp` application-provided; RabbitMQ does not validate or use `content_type`).
- [Queues](https://www.rabbitmq.com/docs/queues) — FIFO per queue; "Multiple active consumers on the same queue: the broker still dequeues in FIFO, but any redelivery can change order"; ways to preserve order: single active consumer or one consumer per queue, and "the x-modulus-hash exchange to partition messages across multiple queues, each with a single active consumer"; durable queues plus persistent messages survive a restart, transient messages are discarded even in durable queues.
- [Quorum queues](https://www.rabbitmq.com/docs/quorum-queues) — "should be considered the default choice when needing a replicated, highly available queue"; always durable and persisted; single node = 0 tolerated failures; `x-delivery-count` header; "Starting with RabbitMQ 4.0, the delivery limit for quorum queues defaults to 20" (`x-delivery-limit` argument or `delivery-limit` policy; over the limit → dropped or dead-lettered); **since 4.3 `basic.nack` increments only the acquired count, not the delivery count — only `basic.reject` and client crash / connection loss count toward the limit**; "It is recommended that all quorum queues have a dead letter configuration of some sort".
- [Dead letter exchanges](https://www.rabbitmq.com/docs/dlx) — dead-lettering on reject/nack with `requeue=false`, per-message TTL, length limit, delivery limit; `x-dead-letter-exchange` / `x-dead-letter-routing-key` as arguments or policy ("Hardcoded x-arguments are strongly recommended against"); a missing DLX at dead-letter time drops the message silently; the `x-death` header records `queue`, `reason`, `count`, `time`.
- [Publishers](https://www.rabbitmq.com/docs/publishers) — `mandatory=true` returns unroutable messages with `basic.return` before the `basic.ack`; unroutable messages are otherwise discarded.
- [Modulus hash exchange](https://www.rabbitmq.com/docs/modulus-hash-exchange) (4.3, built-in) — routes by `hash(routing key) mod N`, "guarantees stable routing ... even across node restarts", but "if you add or remove queues (changing N), the routing for almost all keys will be reshuffled"; recommended "if your topology is static and you need strict message ordering guarantees".
- [Consistent hash exchange plugin README](https://github.com/rabbitmq/rabbitmq-server/blob/main/deps/rabbitmq_consistent_hash_exchange/README.md) and [plugins guide](https://www.rabbitmq.com/docs/plugins) — tier-1 plugin shipped with the server, must be enabled; "after a restart ... a given routing key now may route to a different queue ... cannot guarantee stable queue routing locality".
- [Heartbeats](https://www.rabbitmq.com/docs/heartbeats) — default 60 s suggested by RabbitMQ; "Values within the 5 to 20 seconds range are optimal for most environments"; two missed heartbeats = peer unreachable. [Connections](https://www.rabbitmq.com/docs/connections) — recovery is the application's job for clients without automatic recovery; recover connection → channels → QoS/confirm mode → topology → consumers. The word "backoff" does not appear in RabbitMQ's client guidance; reconnect with backoff is an application practice adopted from `CLAUDE.md`.
- [Streams](https://www.rabbitmq.com/docs/streams) — append-only log, super streams partition with single active consumer; no dead-letter exchanges, TTL, or poison-message handling; need the stream protocol client.
- Clients, for step 2 (npm registry, 2026-09-11): `amqplib` 2.0.1 (2026-05-10, 2.15M weekly downloads, [channel API](https://amqp-node.github.io/amqplib/channel_api.html): `createConfirmChannel`, `prefetch`, `ack`/`nack`/`reject`, `persistent`, `mandatory`, `messageId`, no automatic reconnection); `rabbitmq-client` 5.0.8 (2025-12-01, 74k weekly, TypeScript, automatic reconnect and re-subscribe, needs ≥ 5.0.3 for RabbitMQ 4.1+). The choice is made in step 2.

MongoDB (manual 8.3 "Current"; server pinned to 8.0 per decision 23 — the cited pages describe behaviour present since 4.2 or earlier unless noted; Node driver `mongodb` 7.6.0, 2026-08-24, 10.8M weekly downloads, requires Node ≥ 20.19; the choice of driver is confirmed in step 2):

- [Atomicity and transactions](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) — "a write operation is atomic on the level of a single document, even if the operation modifies multiple values"; "When multiple update commands happen in parallel, each individual command ensures that the query condition still matches"; a filter that does not include the field being changed lets both updates apply and the first client "does not receive any indication that the update was overwritten"; "a distributed transaction incurs a greater performance cost over single document writes, and the availability of distributed transactions should not be a replacement for effective schema design".
- [Model data for atomic operations](https://www.mongodb.com/docs/manual/tutorial/model-data-for-atomic-operations/) — the worked "update if current" pattern with a range predicate in the filter; "If no document matched the update condition, then matchedCount and modifiedCount would be 0".
- [`update` command — Upsert with Unique Index](https://www.mongodb.com/docs/manual/reference/command/update/#upsert-with-unique-index) — when an upsert's insert collides on a unique index, the server updates the newly inserted document only if the filter is "A single equality predicate" (or a logical AND of them) on the unique index's fields and the update does not modify them; "Other update operations either update the newly-inserted document or fail due to a unique key collision". This is why the state write uses an equality-only filter on `_id` (decision 8).
- [`db.collection.updateOne()`](https://www.mongodb.com/docs/manual/reference/method/db.collection.updateOne/) — accepts an aggregation pipeline "expressing conditional updates based on current field values"; returns `matchedCount`, `modifiedCount`, `upsertedCount`, `upsertedId`; an upsert "creates a new document based on the filter criteria and update modifications"; `_id` is immutable.
- [Updates with Aggregation Pipeline](https://www.mongodb.com/docs/manual/tutorial/update-documents-with-aggregation-pipeline/) — pipeline updates support `$set`, `$addFields`, `$project`, `$unset`, `$replaceRoot`, `$replaceWith`; `$$NOW` is available; string values starting with `$` must be wrapped in `$literal`.
- [`db.collection.update()` — Upsert using an Aggregation Pipeline](https://www.mongodb.com/docs/manual/reference/method/db.collection.update/) — "If the `<update>` parameter is an aggregation pipeline, the update creates a base document from the equality clauses in the `<query>` parameter, and then applies the pipeline to the document to create the document to insert"; the same page's "Upsert with Duplicate Values" lists the conditions under which a colliding upsert updates the newly inserted document instead of failing (single equality predicate on the unique index's fields, `multi: false`, indexed fields not modified) and notes that omitting `writeConcern` uses the default `w: "majority"`.
- [`$literal`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/literal/) — "Returns a value without parsing. Use for values that the aggregation pipeline may interpret as an expression"; "If the `<value>` is an expression, `$literal` does not evaluate the expression but instead returns the unparsed expression" (documented with an object value, `{ $literal: { $add: [ 2, 3 ] } }`).
- [`$type` (expression)](https://www.mongodb.com/docs/manual/reference/operator/aggregation/type/) — "If the argument is a field that is missing in the input document, `$type` returns the string `"missing"`"; the documented existence-check pattern is `$cond: { if: { $eq: [{ $type: "$a" }, "missing"] }, ... }`.
- [`$cond`](https://www.mongodb.com/docs/manual/reference/operator/aggregation/cond/) — `{ $cond: { if, then, else } }`, all three required.
- [Unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/) — "A unique compound index ensures that any given combination of the index key values appears at most once"; a missing indexed field is stored as `null` (validation guarantees all three fields are present). Duplicate key error: name `DuplicateKey`, code `11000` ([server error codes](https://raw.githubusercontent.com/mongodb/mongo/master/src/mongo/base/error_codes.yml), [`insertMany` example](https://github.com/mongodb/docs/blob/main/content/manual/v8.2/source/reference/method/db.collection.insertMany.txt)). Node driver 7.6.0 throws [`MongoServerError`](https://mongodb.github.io/node-mongodb-native/7.6/classes/MongoServerError.html) with `code === 11000` from `insertOne` ([source](https://raw.githubusercontent.com/mongodb/node-mongodb-native/v7.6.0/src/operations/insert.ts)); the driver has no named constant for it, so `packages/shared` defines `DUPLICATE_KEY_ERROR_CODE = 11000` once. 11000 is not a retryable-write error code ([driver `error.ts`](https://raw.githubusercontent.com/mongodb/node-mongodb-native/v7.6.0/src/error.ts)).
- [Compound index prefixes](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/#index-prefixes) — "Compound indexes support queries on all fields included in the index prefix"; `{ deviceId, sessionId, seq }` serves `deviceId` and `deviceId + sessionId` lookups and an index-assisted sort on `seq` given equality on both prefix fields. No second index on `deviceId` is needed.
- [`$max`](https://www.mongodb.com/docs/manual/reference/operator/update/max/), [`$setOnInsert`](https://www.mongodb.com/docs/manual/reference/operator/update/setOnInsert/), [`$inc`](https://www.mongodb.com/docs/manual/reference/operator/update/inc/) — `$max` only guards the one field it is applied to, so it cannot protect the other fields of a section written in the same update (rejected as the guard); `$inc` is atomic within a document but not safe against duplicates.

- [Driver `WriteConcern` class (7.6)](https://mongodb.github.io/node-mongodb-native/7.6/classes/WriteConcern.html) — fields `w`, `journal` ("Request acknowledgment that the write operation has been written to the on-disk journal"), `wtimeoutMS`; `j` and `wtimeout` are deprecated aliases.

## Design

### Message contract (`packages/shared`)

Every message from a device is one JSON object (framing decided in step 2):

```ts
type TelemetryMessage = {
  v: 1; // contract version
  deviceId: string; // 1–64 chars, [A-Za-z0-9_-]
  sessionId: number; // integer ≥ 1, ms since epoch at session start
  seq: number; // integer ≥ 1, +1 per message within the session
  occurredAt: number; // integer, ms since epoch, device clock, diagnostic only
} & (
  | { type: 'status'; payload: { state: 'online' | 'degraded' | 'offline' } }
  | { type: 'metrics'; payload: { temperatureC: number; cpuPercent: number; ramPercent: number } }
  | { type: 'counters'; payload: { operationsTotal: number; uptimeMs: number } } // cumulative since session start, integers ≥ 0
  | {
      type: 'diagnostic';
      payload: { severity: 'info' | 'warning' | 'error'; code: string; message: string };
    }
);
```

Rules the schema enforces: all five envelope fields present with the given types and ranges; `type` is one of the four; the payload matches the type exactly (no unknown keys); numbers are finite; strings are bounded (code ≤ 64, message ≤ 1024 chars). The TypeScript types are derived from the schema (step 2), never redeclared.

Message identity: `messageIdentity(m) = `${m.deviceId}:${m.sessionId}:${m.seq}``. Order key: `orderKey(m) = [m.sessionId, m.seq]`. Both are pure helpers in `packages/shared` with unit tests. `isNewer(a, b)` returns `a.sessionId > b.sessionId || (a.sessionId === b.sessionId && a.seq > b.seq)` and is the single definition of "newer" — the MongoDB filter builder below is derived from it and tested against it.

### Device behaviour (`apps/emulator`)

- Each emulated device has a fixed `deviceId` (`dev-0001` …) and, at process start, `sessionId = Date.now()`; `seq` starts at 1 and increments per message. Restarting the emulator process starts new sessions; sessions are never resumed.
- Events per device: `status` on start (`online`) and on every simulated change; `metrics` every `EMULATOR_EVENT_INTERVAL_MS`; `counters` every fifth metrics tick, cumulative; `diagnostic` at random, `error` severity rarely. A `status` heartbeat is sent when nothing else was sent for `EMULATOR_HEARTBEAT_MS` (default 30 000), so an idle connection still carries traffic.
- Connection: resolve every entry of `INGEST_HOSTS` (default `ingest:4000`) with `dns.lookup({ all: true })`, pool the addresses, pick one at random, connect; on any error or close, reconnect with exponential backoff (500 ms → 10 s, jitter) and resolve again.
- Outbox: messages that cannot be written (socket paused by TCP backpressure or disconnected) queue in a bounded per-device outbox (`EMULATOR_OUTBOX_MAX`, default 1 000); when full, the **oldest** entry is dropped and a warning is logged with the device id and the dropped identity. Newest state is worth more than oldest under absolute values.
- Chaos modes (`EMULATOR_CHAOS`, comma-separated, default empty) must be able to produce: exact duplicates (same triple sent twice), out-of-order pairs (adjacent `seq` swapped), disconnect-and-reconnect within a session, and a simulated device restart (new `sessionId`, `seq` from 1). These are what the integration tests in step 7 drive.

### Ingest (`apps/ingest`)

- Accepts device connections, parses frames, validates with the shared schema. An invalid message is logged (reason, `deviceId` if parseable, identity if parseable) and dropped; the connection stays open. A connection idle for `INGEST_SOCKET_IDLE_MS` (default 90 000) is closed.
- Publishes every valid message unchanged as the body, on a confirm channel, to exchange `telemetry` with routing key `event`, `persistent: true`, `mandatory: true`, `contentType: application/json`, `messageId = messageIdentity(m)` and the header `x-received-at` (integer milliseconds, ingest clock; processing stores it as `receivedAt`). A returned (unroutable) message is a startup-topology bug and is logged at error level.
- Per connection, at most `INGEST_MAX_UNCONFIRMED` (default 256) messages await confirmation; when the window is full the socket is paused and resumed as confirms arrive. On broker disconnect: pause all sockets, mark not-ready, reconnect with backoff (500 ms → 10 s), re-assert topology, re-publish the still-unconfirmed messages of every connection (duplicates possible; dedup handles them), resume. On `basic.nack` from the broker the message is re-published once, then logged at error level and dropped.
- Holds no per-device state: nothing keyed by device outlives the connection or is needed by another instance. The unconfirmed window is per connection and dies with it (named loss window, decision 12).
- Readiness = AMQP connection open and topology asserted. Graceful shutdown on SIGTERM: stop accepting, wait up to `SHUTDOWN_TIMEOUT_MS` (default 10 000) for the unconfirmed windows to drain, close device sockets, close the AMQP connection.

### Queue topology (declared by ingest and processing at startup, idempotently)

| Object             | Kind     | Properties                                                                                                                    |
| ------------------ | -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `telemetry`        | exchange | `direct`, durable                                                                                                             |
| `telemetry.events` | queue    | `x-queue-type: quorum`, `x-delivery-limit: 5`, `x-dead-letter-exchange: telemetry.dlx`, bound to `telemetry` with key `event` |
| `telemetry.dlx`    | exchange | `fanout`, durable                                                                                                             |
| `telemetry.dead`   | queue    | `x-queue-type: quorum`, bound to `telemetry.dlx`                                                                              |

Nothing consumes `telemetry.dead` in this scope; it is inspected through the management UI (named limit).

### Processing (`apps/processing`)

Consumer: one channel, `prefetch(PROCESSING_PREFETCH)` (default 50; the documentation's 100–300 guidance is for lighter handlers, this one does three round trips), manual acknowledgements, heartbeat 10 s.

Concurrency: the consume callback does **not** await the handler. Every delivery is dispatched to its own asynchronous handler, so up to `PROCESSING_PREFETCH` handlers run concurrently per instance — the broker enforces the bound through the unacknowledged count. This is what lets one slow or retrying message not block the others on the same instance, and what makes the prefetch window fill during an outage (backpressure below). Every handler receives an `AbortSignal` tied to the channel's close event and checks it before each of steps 2–5. Once it has fired the handler stops without acknowledging: its delivery tag is void, because the broker requeued the delivery when the channel closed. An acknowledgement attempted on a closed channel fails client-side; the handler catches that error, logs it at debug with the identity, and ends — nothing is retried on a void tag and nothing crashes.

Handler for one delivery, in this order:

1. Parse JSON and validate with the shared schema. On failure: log at warn with the raw identity fields if present, `basic.reject(requeue=false)` → dead-lettered. Done.
2. `events.insertOne({ deviceId, sessionId, seq, type, occurredAt, receivedAt, processedAt, payload })`. Duplicate key error 11000 → set `duplicate = true`, log at debug, continue. Any other error → transient path.
3. Conditional upsert of the section (see below). Outcome `created | applied | stale`. Continue.
4. If `type === 'diagnostic'` and `payload.severity === 'error'`: `alerts.insertOne({ _id: messageIdentity, deviceId, sessionId, seq, code, message, occurredAt, createdAt })`. 11000 → already exists, continue.
5. `basic.ack`. Log at info: identity, type, outcome of step 3, `duplicate`, `redelivered` flag.

Transient path (network error, server selection timeout, operation timeout from MongoDB): retry the whole handler from step 2 with exponential backoff (200 ms → 5 s, jitter) while the delivery stays unacknowledged; log each retry at warn with the attempt number. With all handlers retrying, the prefetch window is full and the broker stops delivering — that is the backpressure. The retry loop checks the `AbortSignal` before every attempt: when the broker closes the channel (consumer acknowledgement timeout, connection loss) the loop stops, because its delivery tag is void and the broker has already requeued the message for another consumer. A handler that is inside a MongoDB call when the signal fires finishes that one call; the write may then be applied by two handlers, which is the redelivery case — idempotent, harmless, and named in the failure table. Readiness = AMQP consumer running and MongoDB ping succeeding.

Graceful shutdown on SIGTERM: `basic.cancel` the consumer, wait up to `SHUTDOWN_TIMEOUT_MS` for in-flight handlers to finish and ack, close channel, connection, MongoDB client. Deliveries still unacknowledged at the deadline are left unacked; the broker requeues them when the connection closes. Closing the MongoDB client rejects any call still in flight; the handler catches that error, logs it at warn with the identity, and ends without acknowledging — no unhandled rejection during shutdown.

### MongoDB collections and indexes (created by processing at startup, idempotently)

`events` — one document per unique event.

```
{ _id: ObjectId, deviceId, sessionId, seq, type, occurredAt, receivedAt, processedAt, payload }
unique index { deviceId: 1, sessionId: 1, seq: 1 }   // the dedup key; prefix serves per-device reads
```

`device_state` — one document per device, `_id = deviceId`.

```
{
  _id: 'dev-0001',
  status:     { sessionId, seq, occurredAt, receivedAt, state },
  metrics:    { sessionId, seq, occurredAt, receivedAt, temperatureC, cpuPercent, ramPercent },
  counters:   { sessionId, seq, occurredAt, receivedAt, operationsTotal, uptimeMs },
  diagnostic: { sessionId, seq, occurredAt, receivedAt, severity, code, message }
}
```

A section is absent until the first event of its type arrives. There is deliberately no top-level `updatedAt`: an unconditional field would be modified on every write and hide the `stale` outcome; each section's `receivedAt` says when it last changed. The counters section belongs to the session it names; a new session's first counters event replaces it (higher `sessionId`), so counters restart at 0 per session by design (decision 6).

`alerts` — `_id` = message identity string; `{ deviceId, sessionId, seq, code, message, occurredAt, createdAt }`.

### The conditional upsert (the one operation that enforces invariants 1–3)

For an event of type `T` with key `(s, q)` and the new section value `next = { sessionId: s, seq: q, occurredAt, receivedAt, ...payload }`:

```js
filter = { _id: deviceId }; // single equality on the unique _id index
update = [
  {
    $set: {
      [T]: {
        $cond: {
          if: {
            $or: [
              { $eq: [{ $type: `$${T}` }, 'missing'] },
              { $lt: [`$${T}.sessionId`, s] },
              { $and: [{ $eq: [`$${T}.sessionId`, s] }, { $lt: [`$${T}.seq`, q] }] },
            ],
          },
          then: { $literal: next },
          else: `$${T}`,
        },
      },
    },
  },
];
options = { upsert: true }; // write concern { w: MONGODB_WRITE_W, journal: true, wtimeoutMS } is set on the client
```

Outcomes read from the `UpdateResult`:

- `upsertedCount === 1` → no document for the device existed; created with this section (`created`).
- `modifiedCount === 1` → the section was absent or older; replaced (`applied`).
- `matchedCount === 1 && modifiedCount === 0` → the stored section is newer or has the same key; nothing changed (`stale`; with `duplicate` from step 2 it is a duplicate, otherwise an older message).

Why this is safe without a read: the server evaluates the `$cond` against the document as it is at the moment of the update and writes the result atomically, so two concurrent writers for the same section cannot both win with a stale key — the second one sees the first one's section in `$${T}`. On the insert path the server "creates a base document from the equality clauses in the query parameter, and then applies the pipeline to the document to create the document to insert" (manual, `db.collection.update()` → "Upsert using an Aggregation Pipeline"), so the new document gets `_id: deviceId` from the filter and the section from the `$cond` (`$${T}` is missing on the base document, so the first branch is taken). The first two messages of a new device may race on the upsert; because the filter is a single equality on `_id` and the update does not touch `_id`, the server's documented behaviour is to turn the losing insert into an update of the newly inserted document, so no duplicate key error reaches the application (manual, "Upsert with Duplicate Values"). The `$literal` wrapper around the whole `next` object is required because inside a pipeline an object is parsed as an expression and a string starting with `$` (a diagnostic `message`) would be read as a field path; `$literal` "returns a value without parsing", for objects as well as strings (manual, `$literal`).

Where the logic lives: `packages/shared` exports only `isNewer(a, b)` — a pure comparison with no MongoDB types, part of the contract. The pipeline builder `newerThanStoredExpr(sectionPath, key)` (the `$or` above) is a storage decision and lives in `apps/processing`; its unit test runs the same five cases as `isNewer` — absent section; older session; same session, older `seq`; same key; newer session with a lower `seq` — and asserts the two agree. The integration tests in step 7 run the real update against MongoDB for each outcome, for the two-writer race, and with a diagnostic `message` that starts with `$` to prove the `$literal` wrapping.

## Consistency & Failure Modes

**Identity and order in the message:** `deviceId` (whose state), `sessionId` + `seq` (order key and, with `deviceId`, the identity), `type` (which section), `occurredAt` (diagnostic only). Nothing added by ingest or the broker is needed for correctness; the AMQP `messageId` and `timestamp` properties are for operators and logs.

**How "newer" is decided:** per section, `(sessionId, seq)` strictly greater than the stored watermark, evaluated by the server inside the atomic update (conditional upsert above). Equal = duplicate. Absent section = anything is newer.

**Dedup key and where it is enforced:** `(deviceId, sessionId, seq)`; enforced by the unique index on `events`, the `_id` of `alerts`, and the strictness of the state guard. All three are in MongoDB, so a duplicate arriving at another instance, minutes later, or after a restart is still rejected.

**Atomic operations and the guarantee:** three single-document writes, each atomic by MongoDB's single-document guarantee; the handler as a whole is idempotent, so its non-atomicity is harmless (table below). No transaction, no lock.

**Delivery semantics:** at-least-once from ingest to storage (confirms, manual ack after journaled writes); fire-and-forget from device to ingest with a bounded, named loss window; exactly-once effect at storage.

## Scaling

- **Ingest:** N instances, stateless; devices spread by address choice at connect time; an instance's capacity is bounded by open sockets and the confirm throughput of its AMQP connection. Adding an instance adds capacity linearly; no rebalancing is needed because nothing is pinned.
- **Processing:** M instances, all competing on `telemetry.events`. RabbitMQ dispatches round-robin among consumers with free prefetch slots. Adding an instance adds throughput until MongoDB's write capacity is the limit (three round trips per message on indexed keys). No upper bound from the topology; no partition count to manage.
- **Cost of the consistency mechanism per message:** one unique-index insert, one conditional single-document update, one keyed insert for the rare error diagnostic. All single-document, index-hit, lock-free at the application level. A stale message costs one matched-but-unmodified update; a duplicate additionally costs the rejected insert (one 11000 round trip). No message waits for another.
- **Hot device:** its messages spread over all consumers like any other device; the only effect is more concurrent conditional updates on one document, each still a single atomic write, with the losers costing one unmodified update. The alternative (routing by device) would make a hot device a single-consumer bottleneck instead.
- **What it does not give:** physical serialisation per device. A future event type with side effects that must run in order (or delta-shaped values) would need the modulus-hash + single-active-consumer topology (Alternatives). That switch changes the queue topology and the consumer setup, not the contract or the storage rules.

## Alternatives Considered

### Per-device routing: `x-modulus-hash` exchange + single active consumer

Partition `telemetry.events` into K quorum queues bound to a modulus-hash exchange keyed by `deviceId`, each with `x-single-active-consumer: true`, so all messages of one device are processed by one consumer in arrival order. Gains physical per-device serialisation (needed only for delta events or ordered side effects). Costs: the consumer count is capped at K; a hot device saturates one queue; changing K reshuffles almost every key and breaks order during the change; the consistent-hash plugin variant additionally loses locality across node restarts. Rejected because the contract already makes processing order irrelevant; documented as the upgrade path with its trigger.

### Freshness guard in the update filter (`{ _id, 'T.seq': { $lt: q } }` + upsert)

The textbook "update if current" form. Correct for a plain update, but with `upsert: true` a stale message makes the filter match nothing, the server tries to insert a second document with the same `_id`, and the application receives duplicate key error 11000 — an error round trip plus a retry for every stale or duplicate message, and error handling as normal control flow. The pipeline `$cond` form (decision 8) gives the same atomic guarantee in one round trip with no expected error.

### `$max` on the watermark

`$max` only protects the one field it is applied to; the other fields of the section written with `$set` in the same update would still be overwritten by an older message. Rejected.

### Single-node replica set in Docker Compose

Would enable retryable writes, transactions and change streams. Costs a one-time `rs.initiate()`, a not-yet-primary start-up window and `directConnection=true` for host-side tests. Nothing in this design uses any of the three features; the handler's in-place retry covers transient errors. Production runs a replica set; the switch is configuration only — the connection string and `MONGODB_WRITE_W=majority` (decision 22).

### Multi-document transaction around the three writes

Would make the handler atomic as a whole. Costs a replica set, more latency per message, and it protects nothing: the handler is already idempotent, so a partial run is repaired by the redelivery. MongoDB's guidance is to prefer single-document design over transactions.

### Increment-shaped counters

Would preserve per-increment detail and lifetime totals in the state document. Requires exactly-once application: every duplicate must be detected before `$inc` (dedup record consulted first, or the event insert as the gate with a crash window between insert and `$inc` that needs a transaction), and every lost message becomes a permanent error. Rejected in favour of cumulative values; lifetime totals can be derived from `events`.

### Full device snapshot in every message, one watermark per device

Simplest freshness rule (one comparison), but diagnostics are events, not state, and every message would carry every field. Per-section watermarks give the same simplicity per section at the cost of one helper.

### Device timestamp as the order key

No device-side counter, but collisions within a millisecond, unsynchronised clocks and clock jumps make it unsafe as the deciding key. Kept as diagnostics only.

### Application-level acknowledgement from ingest to the device

Closes the ingest-crash loss window: ingest replies "acked up to seq N" after the broker confirm, the device resends what is unacked. More protocol in both emulator and ingest, and per-connection in-flight tracking. Not needed while values are absolute and counters cumulative; documented as the upgrade path. Its resends would be handled by the existing dedup.

### Buffered reordering in processing (wait for a missing `seq`)

Adds latency and a per-device buffer per instance, and only helps when every event must be applied in order. Under absolute values, dropping the stale event is strictly cheaper.

### Distributed lock per device

Adds a component and latency; on lock expiry it produces exactly the race it was meant to prevent. The guarded update solves the same problem without it.

### In-process serialisation per device (async mutex keyed by `deviceId`)

Only orders work within one instance; two instances still race. Rejected as false safety.

### RabbitMQ streams / super streams

Kafka-like partitions with offsets and replay. No dead-letter or poison handling, a separate client library, offset management on the consumer. Out of proportion for this scope.

### TTL on `events` for dedup retention

Bounds storage; reopens the dedup window after expiry. Acceptable later because the state guard still rejects any late duplicate as "not newer"; not needed now.

### TCP load balancer in front of ingest

Production shape; adds a container and a config file to a dev Compose. Client-side address choice is enough to demonstrate the spread and the statelessness.
