## Problem

Many devices send telemetry over long-lived socket connections. Messages pass through stateless ingest instances and a RabbitMQ queue to several processing instances that store every event and keep one "current state" per device in MongoDB. The assignment requires that the final state of a device reflects the logical order of the unique events the device produced: an older message must never overwrite newer known state, and a duplicated or redelivered message must never cause a second business effect (a counter counted twice, an alert created twice, an inconsistent state). Both services must scale horizontally, devices must be processed in parallel, and the consistency mechanism must cost as little throughput as possible.

Everything downstream — the shared contract (step 2), the emulator (step 3), ingest (step 4), processing (step 5), the Compose topology (step 6), the integration tests (step 7) and the README (step 8) — depends on the answers in this spec. Nothing in the repository decides them yet.

| 1   | What carries the logical order of a device's events?                 | A per-device **sequence number `seq`** (integer, starts at 1, +1 per message) combined with a **`sessionId`** (integer, milliseconds since epoch when the device session started). The order key is the pair `(sessionId, seq)`, compared lexicographically.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | The assignment asks for the order in which the device produced the events, so the carrier must be created on the device, not by the broker (queue position is arrival order). A sequence number is unique and contiguous, so gaps are detectable; a timestamp alone is neither (two events in one millisecond collide, clock jumps reorder). `sessionId` solves the device restart: a restarted device starts a new session with a higher `sessionId` and `seq` from 1 again, and the pair still orders correctly without persisting anything on the device. | 5   | What shape do events have?                                           | **Typed events with absolute values.** Each message carries exactly one `type` — `status`, `metrics`, `counters` or `diagnostic` — and the full current value of that section. | 6   | Do counters travel as increments or as cumulative values?            | **Cumulative values per session** (`operationsTotal`, `uptimeMs` since session start). Processing never adds; it stores the latest value under the freshness rule.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | This is the single decision that makes "a duplicate never counts twice" true by construction instead of by bookkeeping, and it makes a lost message harmless (the next one carries the correct total). | 7   | What is the "current state" of a device and how is it stored?        | One document per device in `device_state`, `_id = deviceId`, with **one sub-document per section** (`status`, `metrics`, `counters`, `diagnostic`). Each section stores the payload of the newest unique event of that type **plus its own `(sessionId, seq)` watermark**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | With typed events, one watermark per device would be wrong: after a `metrics` event with `seq` 5 is applied, a late `status` event with `seq` 4 is still the newest known status and must be applied. A per-section watermark gives the correct final state for every section, and the whole document is still updated by one atomic single-document operation. Rejected: one watermark per device (drops genuinely newest section updates).                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 8   | What is the freshness rule?                                          | Apply an event to section `T` if and only if `T` is absent or `(event.sessionId, event.seq) > (T.sessionId, T.seq)` lexicographically. Equal keys are duplicates and are not applied. The comparison is evaluated **by the server inside the update** — an aggregation-pipeline update whose `$cond` keeps the stored section unless the event is newer — never in application code that read first.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | MongoDB evaluates an update against the document as it is at that moment and applies it atomically, so a comparison inside the update is a lost-update guard without a read. The classic variant — the comparison in the update **filter** — was rejected for the upsert case: when the stored section is newer, the filter matches nothing, the upsert tries to insert a second document with the same `_id`, and the server fails with duplicate key error 11000 (manual, "Upsert with Unique Index"). Every stale message would then cost an error plus a retry round trip. The pipeline form makes it one matched, unmodified update, and the first-message race of a new device is resolved by the server itself because the filter is a single equality on `_id`.                                                                                                                                 |
| 9   | Where is deduplication enforced?                                     | At the storage boundary, three times, each idempotent: (a) `events` has a **unique index on `(deviceId, sessionId, seq)`**, so a second insert fails with duplicate key error 11000 and is treated as "already stored"; (b) `alerts` uses the message identity string as `_id`, so a second alert insert fails the same way; (c) `device_state` applies the freshness rule, under which a duplicate is "not newer" → no-op.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Dedup must live in the database, not in process memory, because the duplicate may arrive at a different processing instance than the original. Because every effect is idempotent, no dedup record needs to be consulted before acting — the effect itself rejects the duplicate. Rejected: an in-memory seen-set (per instance, lost on restart); a separate dedup collection with a TTL (an extra write per message and a window after which a duplicate passes again).                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 10  | Which operations are atomic and what guarantees it?                  | Each of the three writes is a **single-document operation**, atomic by MongoDB's guarantee for one document. There is **no multi-document transaction**: the handler runs the three writes in a fixed order and each is idempotent, so a crash between them is repaired by the redelivery.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | The event insert is the dedup gate and is idempotent (11000 = done). The state update is guarded and idempotent. The alert insert is keyed and idempotent. Re-running the whole handler after a crash at any point produces the same end state, so the sequence does not need to be atomic as a whole. A transaction would need a replica set, cost more per message and — per MongoDB's own guidance — is not a substitute for a schema where the state lives in one document.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 11  | How do we get serial-within-device and parallel-across-devices?      | **One quorum queue, competing consumers, optimistic guarded writes.** Messages of one device may be processed concurrently by different instances; the storage guard makes the order of processing irrelevant to the result. Nothing is routed by device.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Because events are absolute-valued and sections carry watermarks, correctness never depends on processing order, only on the comparison at write time. Routing by device (hash exchange plus single active consumer) would buy physical serialisation that this design does not need, and would cost hotspots (one loud device saturates one consumer), a consumer count capped by the queue count, and reshuffling when the queue count changes. Named upgrade path: `x-modulus-hash` exchange + single active consumer (RabbitMQ 4.3 built-in) if a future event type needs physical serialisation (deltas, ordered side effects).                                                                                                                                                                                                                                                                    |
| 12  | Which delivery semantics, and where?                                 | **At-least-once** between ingest and broker (publisher confirms; unconfirmed messages are re-published after a broker reconnect) and between broker and processing (manual `basic.ack` only after all three writes are acknowledged by MongoDB). **Fire-and-forget** between device and ingest (no application-level acknowledgement to the device). The **effect** is exactly-once at the storage boundary (decision 9).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Exactly-once delivery would need coordination between broker and database (two-phase commit or an outbox) and is out of proportion for this scope; at-least-once plus idempotent effects is the standard answer and is what the RabbitMQ documentation itself prescribes. The device-side acknowledgement was left out on purpose: the loss window it would close (messages the device wrote to the socket that ingest had not yet had confirmed when it crashed) is bounded by the per-connection confirm window, and decisions 5–6 make such a loss harmless — the next periodic message restores the truth. Named upgrade path: a cumulative "acked up to `seq`" reply and device-side resend; the dedup already tolerates the resends it would produce.                                                                                                                                             |
| 13  | How are poison messages and transient failures told apart?           | **Deterministic failures** (unparsable body, schema violation) → `basic.reject` with `requeue=false` → dead-letter exchange → `telemetry.dead`. **Transient failures** (MongoDB unreachable, timeout) → retry the same handler in place with exponential backoff while the delivery stays unacknowledged; the prefetch limit then stops further deliveries, which is the backpressure. The quorum queue's delivery limit (5) catches crash loops: a message whose processing crashes the process is requeued with an incremented delivery count and dead-lettered after the fifth attempt.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | RabbitMQ 4.3 changed the counting: `basic.nack` no longer increments the delivery count, only `basic.reject` and connection loss do. A nack-requeue retry loop would therefore never reach the limit, and a reject-requeue loop during a database outage would dead-letter good messages. Retrying in place avoids both. Trade-off named: an in-place retry is bounded by the broker's consumer timeout (30 minutes by default); after it the broker returns the deliveries to the queue and cancels the consumer (decision 25), which is the correct outcome for an outage that long — and decision 26 pauses the consumer explicitly well before that, so the timeout is not the normal path. The three error classes are decision 26.                                                                                                                                                                |
| 14  | What does ingest do when RabbitMQ is unavailable?                    | It **pauses reading from every device socket**, reports not-ready, reconnects with backoff, then resumes and re-publishes the unconfirmed messages. It never buffers beyond the per-connection confirm window (`INGEST_MAX_UNCONFIRMED`, default 256) and never drops silently.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Pausing pushes the backpressure to the device through TCP, where the emulator keeps a bounded outbox. Buffering in ingest memory would create per-instance state that a crash loses, and dropping would be silent loss. Closing device connections was rejected: if the broker is down, every ingest instance is affected, so reconnecting elsewhere helps nobody, and the AMQP reconnect handles the case where only this instance's broker connection broke.                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| 25  | What happens when a handler outlives the broker's consumer timeout?  | RabbitMQ 4.3 returns the deliveries to the queue and, because amqplib advertises `consumer_cancel_notify`, sends `basic.cancel` for that consumer only; the channel stays open and amqplib invokes the consume callback with `null`. A timeout does not increment the delivery count, so no message is dead-lettered because of one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Verified in the 4.3 release notes and the quorum-queue guide. The instance would also stop consuming silently while readiness still reported the connection as open. Rejected: relying on channel close alone (the pre-4.3 behaviour).                                                                                                                                                                                                                                                                                            |
| 26  | How does the handler classify errors?                                | Three classes. **Deterministic** (unparsable body, schema violation, malformed `x-received-at`) → `basic.reject(requeue=false)`, dead-lettered. **Transient** (`MongoNetworkError`, `MongoServerSelectionError`, a `MongoServerError` carrying the `RetryableWriteError` label or one of the codes 50 `MaxTimeMSExpired`, 262 `ExceededTimeLimit`, 24 `LockTimeout`, 64 `WriteConcernTimeout`, 10107 `NotWritablePrimary`, 11600 `InterruptedAtShutdown`, 91 `ShutdownInProgress`) → retry in place with backoff; after `PROCESSING_TRANSIENT_ATTEMPTS` (default 5) consecutive failures the instance pauses: it cancels its consumer (no new deliveries), lets the in-flight handlers stop at their abort check, returns every delivery it still holds with `basic.nack(requeue=true)` — a cancel alone neither discards nor requeues in-flight deliveries (consumers guide), and in 4.3 a nack does not increment the delivery count — reports not-ready and re-registers the consumer once the MongoDB ping succeeds. **Permanent** (everything else) → log at error with the identity, `basic.reject(requeue=false)`, dead-lettered. Every dispatched handler is wrapped in a catch-all that can never reject. | "Any other error → transient" made a permanent write failure an unbounded loop that held a prefetch slot, and a floating handler rejection would end the process (Node 24 terminates on an unhandled rejection) and requeue all prefetched deliveries with their count incremented. Pausing the consumer during an outage is what the 4.3 release notes recommend over retrying every delivery.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 27  | Does the state document carry a device-wide watermark?               | Yes: `lastEvent = { sessionId, seq, type, receivedAt }`, advanced by the same conditional pipeline only when the event is newer than the stored `lastEvent`. It is the reader's "as of" marker (the sections are a per-section latest-value projection, not a point-in-time snapshot), the input for liveness — a reader treats a device as presumed offline when `now - lastEvent.receivedAt` exceeds three times `EMULATOR_HEARTBEAT_MS` — and the reference for gap logging (`seq` skipped a value within one session).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | A device whose power is pulled never sends `status: offline`, so without this the state said `online` forever and nothing in the document told the reader when the device was last heard from. The earlier reason for omitting a top-level marker (it would hide the `stale` outcome) holds only for an unconditional field: a conditional `lastEvent` is never overwritten by a stale message, so it stays a true watermark and its previous value survives for the gap log. The per-section outcome is unaffected either way, because `returnDocument: 'before'` (decision 29) hands `isNewer` the untouched `before[T]` however `lastEvent` is written. A message newer than `lastEvent` is newer than every section, so `lastEvent` never moves without its section moving. Rejected: ingest publishing connect/disconnect events (ingest would have to mint identities that are not the device's). |
| 28  | What guarantees the dedup key is never reused?                       | A contract invariant, now explicit: a device never reuses `(sessionId, seq)` and `sessionId` strictly increases across its sessions. The emulator enforces it with `sessionId = max(Date.now(), previousSessionId + 1)` per device. The schema bounds `sessionId` to 1 500 000 000 000–4 100 000 000 000 (2017–2099, epoch milliseconds), so a clock unit error (seconds, microseconds) or an unset clock is rejected loudly at validation instead of freezing the device's state, and bounds `occurredAt` to ≥ 0. Device ids carry `EMULATOR_DEVICE_ID_PREFIX` (default `dev`); the emulator scales by `EMULATOR_DEVICE_COUNT`, and `--scale emulator=N` needs a distinct prefix per replica (T14). Repair path for a device poisoned by an out-of-range value that slipped through: rebuild its `device_state` document from `events`.                                                                                                                                                                                                                                                                                                                                                                           | Two restarts within one millisecond reused a `sessionId`, so genuinely new events collided with old ones in the unique index, were logged as duplicates and the state froze; two emulator replicas with the same ids were two physical devices fighting over one document, the higher `sessionId` winning forever. Named residual: a real device without persistence can still reuse a `sessionId` across a sub-millisecond restart (T1).                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| 29  | How does the handler learn the outcome and the previous `lastEvent`? | The state write is `findOneAndUpdate(filter, pipeline, { upsert: true, returnDocument: 'before' })` — same filter, same pipeline, same single-document atomicity — and the handler classifies the outcome from the returned pre-update document with `isNewer`: `null` → `created`; section absent or `isNewer(event, before[T])` → `applied`; otherwise `stale`. The same document carries the previous `lastEvent` for the gap log.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | The outcome becomes a pure function of the previous document and the one freshness rule in shared — unit-testable against `isNewer` — instead of the server's modified-count semantics for a no-op `$set`, a detail the design had never verified. Cost named (T16): on a replica set with retryable writes `findAndModify` copies the document into a side collection per node before the update (the manual's own performance note); the document is about 1 KiB. The duplicate-values upsert retry is documented for `update`; for `findAndModify` the handler's own one-shot 11000 retry covers the racing first insert either way.                                                                                                                                                                                                                                                                 |

## Chosen Approach

**One queue, competing consumers, and correctness at the write.** Every message carries `(deviceId, sessionId, seq)` created on the device. Ingest validates and publishes it unchanged to one quorum queue with publisher confirms. Any number of processing instances consume the queue with a prefetch limit. For each delivery the handler runs three idempotent single-document writes in a fixed order — insert the event (unique index rejects duplicates), apply the event's section to the device's state document with a conditional update that replaces the section only when the event is newer than the stored one, and, for error diagnostics, insert an alert keyed by the message identity — and acknowledges the delivery afterwards. Two messages of the same device may be processed at the same time by two instances; whichever writes second either has a newer key and wins, or has an older or equal key and changes nothing. No lock, no routing, no transaction, no coordination between instances.

**Why this over alternatives:** the assignment's four hard problems (order, duplicates, atomicity, parallelism) are all answered by two properties chosen in the contract — absolute-valued typed events and a device-generated order key — plus one storage rule (one conditional pipeline update evaluated by the server). Everything else (routing, locks, buffering, transactions) would protect against problems that the contract already made impossible, and each would cost throughput or scaling freedom. The two alternatives below stay documented as upgrade paths with the trigger that would justify them.

## Design

### Message contract (`packages/shared`)

Every message from a device is one JSON object (framing decided in step 2):

```ts
type TelemetryMessage = {
  v: 1; // contract version
  deviceId: string; // 1–64 chars, [A-Za-z0-9_-]
  sessionId: number; // integer ≥ 1, ms since epoch at session start
  seq: number; // integer ≥ 1, +1 per message within the session
  occurredAt: number; // integer, ms since epoch, device clock, diagnostic only
} & (
  | { type: 'status'; payload: { state: 'online' | 'degraded' | 'offline' } }
  | { type: 'metrics'; payload: { temperatureC: number; cpuPercent: number; ramPercent: number } }
  | { type: 'counters'; payload: { operationsTotal: number; uptimeMs: number } } // cumulative since session start, integers ≥ 0
  | {
      type: 'diagnostic';
      payload: { severity: 'info' | 'warning' | 'error'; code: string; message: string };
    }
);
```

Rules the schema enforces: all five envelope fields present with the given types and ranges; `type` is one of the four; the payload matches the type exactly (no unknown keys); numbers are finite; strings are bounded (code ≤ 64, message ≤ 1024 chars). The TypeScript types are derived from the schema (step 2), never redeclared.

Message identity: `messageIdentity(m) = `${m.deviceId}:${m.sessionId}:${m.seq}``. Order key: `orderKey(m) = [m.sessionId, m.seq]`. Both are pure helpers in `packages/shared` with unit tests. `isNewer(a, b)` returns `a.sessionId > b.sessionId || (a.sessionId === b.sessionId && a.seq > b.seq)` and is the single definition of "newer" — the MongoDB filter builder below is derived from it and tested against it.

### Device behaviour (`apps/emulator`)

- Each emulated device has a fixed `deviceId` (`<EMULATOR_DEVICE_ID_PREFIX>-0001` …, default prefix `dev`) and, at every session start, `sessionId = max(Date.now(), previousSessionId + 1)`, so two sessions of one device never share a `sessionId` even when a simulated restart happens within one millisecond (decision 28); `seq` starts at 1 and increments per message. Restarting the emulator process starts new sessions; sessions are never resumed. Scaling the emulator service itself (`--scale emulator=N`) needs a distinct prefix per replica: two replicas with the same ids are two physical devices fighting over one state document (T14).
- Events per device: `status` on start (`online`) and on every simulated change; `metrics` every `EMULATOR_EVENT_INTERVAL_MS`; `counters` every fifth metrics tick, cumulative; `diagnostic` at random, `error` severity rarely. A `status` heartbeat is sent when nothing else was sent for `EMULATOR_HEARTBEAT_MS` (default 30 000), so an idle connection still carries traffic.
- Connection: resolve every entry of `INGEST_HOSTS` (default `ingest:4000`) with `dns.lookup({ all: true })`, pool the addresses, pick one at random, connect; on any error or close, reconnect with exponential backoff (500 ms → 10 s, jitter) and resolve again.
- Outbox: messages that cannot be written (socket paused by TCP backpressure or disconnected) queue in a bounded per-device outbox (`EMULATOR_OUTBOX_MAX`, default 1 000); when full, the **oldest non-diagnostic** entry is dropped and a warning is logged with the device id and the dropped identity; diagnostics are dropped only when nothing else is left, because a dropped `error` diagnostic is an alert that is never created. Newest state is worth more than oldest under absolute values.
- Chaos modes (`EMULATOR_CHAOS`, comma-separated, default empty) must be able to produce: exact duplicates (same triple sent twice), out-of-order pairs (adjacent `seq` swapped), disconnect-and-reconnect within a session, and a simulated device restart (new `sessionId`, `seq` from 1). These are what the integration tests in step 7 drive.

### Ingest (`apps/ingest`)

- Accepts device connections, parses frames, validates with the shared schema. An invalid message is logged (reason, `deviceId` if parseable, identity if parseable) and dropped; the connection stays open. A connection that has delivered no bytes for `INGEST_SOCKET_IDLE_MS` (default 90 000) is closed; the idle timer is suspended while the socket is paused for backpressure, so a broker outage (decision 14) never turns into a mass disconnect 90 seconds in.
- Publishes every valid message unchanged as the body, on a confirm channel, to exchange `telemetry` with routing key `event`, `persistent: true`, `mandatory: true`, `contentType: application/json`, `messageId = messageIdentity(m)` and the header `x-received-at` (integer milliseconds, ingest clock; processing stores it as `receivedAt`). A returned (unroutable) message is a startup-topology bug and is logged at error level.
- Per connection, at most `INGEST_MAX_UNCONFIRMED` (default 256) messages await confirmation, and at most `INGEST_MAX_UNCONFIRMED_TOTAL` (default 20 000) per instance; when either window is full the affected sockets (one, or all) are paused and resumed as confirms arrive — without the instance-wide cap the memory bound would grow with the device count. On broker disconnect: pause all sockets, mark not-ready, reconnect with backoff (500 ms → 10 s), re-assert topology, re-publish the still-unconfirmed messages of every connection (duplicates possible; dedup handles them), resume. On `basic.nack` from the broker the message is re-published once, then logged at error level and dropped.
- Holds no per-device state: nothing keyed by device outlives the connection or is needed by another instance. The unconfirmed window is per connection and dies with it (named loss window, decision 12).
- Readiness = AMQP connection open and topology asserted. Graceful shutdown on SIGTERM: stop accepting, wait up to `SHUTDOWN_TIMEOUT_MS` (default 10 000) for the unconfirmed windows to drain, close device sockets, close the AMQP connection.

### Processing (`apps/processing`)

Consumer: one channel, `prefetch(PROCESSING_PREFETCH)` (default 50; the documentation's 100–300 guidance is for lighter handlers, this one does three round trips), manual acknowledgements, heartbeat 10 s.

Concurrency: the consume callback does **not** await the handler. Every delivery is dispatched to its own asynchronous handler, so up to `PROCESSING_PREFETCH` handlers run concurrently per instance — the broker enforces the bound through the unacknowledged count. This is what lets one slow or retrying message not block the others on the same instance, and what makes the prefetch window fill during an outage (backpressure below). Every handler receives an `AbortSignal` that fires when the channel closes **or when the broker cancels the consumer** (amqplib invokes the consume callback with `null`; RabbitMQ 4.3 cancels only the timed-out consumer and leaves the channel open — decision 25) and checks it before each of steps 2–5. Once it has fired the handler stops without acknowledging: its delivery tag is void, because the broker returned the delivery to the queue, and an acknowledgement of an unknown tag is a channel error (406) that would close the channel and requeue every other in-flight delivery with its delivery count incremented. On a broker-initiated cancel the service re-registers the consumer on the same channel; on a close it reconnects. When the service pauses itself (decision 26) the order is: cancel, wait for the handlers to stop at their abort check, `basic.nack(requeue=true)` for everything still held — a client-initiated cancel returns nothing by itself — then re-consume after the ping succeeds. Every dispatched handler is wrapped in a catch-all that can never reject (decision 26). The consumer is registered only after `createIndexes` has resolved, because invariant 2 depends on the unique index existing before the first insert.

Handler for one delivery, in this order:

1. Parse JSON and validate with the shared schema; read `x-received-at` as a safe non-negative integer, or use the handler's clock and log at warn (decision 18). On a body failure: log at warn with the raw identity fields if present, `basic.reject(requeue=false)` → dead-lettered. Done.
2. `events.insertOne({ deviceId, sessionId, seq, type, occurredAt, receivedAt, processedAt, payload })`. Duplicate key error 11000 → set `duplicate = true`, log at debug, continue. A transient error (decision 26) → transient path; any other error → permanent path.
3. Conditional upsert of the section (see below), which also advances `lastEvent` when the event is newer than it (decision 27). Outcome `created | applied | stale`. If the pre-update document's `lastEvent` (decision 29) had the same `sessionId` and `event.seq > lastEvent.seq + 1`, log a gap at info with both sequence numbers. Continue.
4. If `type === 'diagnostic'` and `payload.severity === 'error'`: `alerts.insertOne({ _id: messageIdentity, deviceId, sessionId, seq, code, message, occurredAt, createdAt })`. 11000 → already exists, continue.
5. `basic.ack`. Log at info: identity, type, outcome of step 3, `duplicate`, `redelivered` flag.

Transient path (the error set of decision 26): retry the whole handler from step 2 with exponential backoff (200 ms → 5 s, jitter) while the delivery stays unacknowledged; log each retry at warn with the attempt number. After `PROCESSING_TRANSIENT_ATTEMPTS` consecutive failures of one handler the instance pauses (decision 26): `basic.cancel` stops new deliveries, the in-flight handlers stop at their next abort check, every delivery still held is returned with `basic.nack(requeue=true)` — which in 4.3 does not increment the delivery count — and the instance reports not-ready, pings MongoDB with backoff and re-registers the consumer when the ping succeeds. Permanent path: log at error with the identity and the error, `basic.reject(requeue=false)` → dead-lettered with `x-death` reason `rejected`. The retry loop checks the `AbortSignal` before every attempt: when the broker cancels the consumer or closes the channel (consumer timeout, connection loss) the loop stops, because its delivery tag is void and the broker has already returned the message to the queue for another consumer. A handler that is inside a MongoDB call when the signal fires finishes that one call; the write may then be applied by two handlers, which is the redelivery case — idempotent, harmless, and named in the failure table. Readiness = AMQP consumer running and MongoDB ping succeeding.

Graceful shutdown on SIGTERM: `basic.cancel` the consumer, wait up to `SHUTDOWN_TIMEOUT_MS` for in-flight handlers to finish and ack, close channel, connection, MongoDB client. Deliveries still unacknowledged at the deadline are left unacked; the broker requeues them when the connection closes. Closing the MongoDB client rejects any call still in flight; the handler catches that error, logs it at warn with the identity, and ends without acknowledging — no unhandled rejection during shutdown.

### MongoDB collections and indexes (created by processing at startup, idempotently)

`events` — one document per unique event.

```
{ _id: ObjectId, deviceId, sessionId, seq, type, occurredAt, receivedAt, processedAt, payload }
unique index { deviceId: 1, sessionId: 1, seq: 1 }   // the dedup key; prefix serves per-device reads
```

`device_state` — one document per device, `_id = deviceId`.

```
{
  _id: 'dev-0001',
  lastEvent:  { sessionId, seq, type, receivedAt },              // device-wide watermark, decision 27
  status:     { sessionId, seq, occurredAt, receivedAt, state },
  metrics:    { sessionId, seq, occurredAt, receivedAt, temperatureC, cpuPercent, ramPercent },
  counters:   { sessionId, seq, occurredAt, receivedAt, operationsTotal, uptimeMs },
  diagnostic: { sessionId, seq, occurredAt, receivedAt, severity, code, message }
}
```

A section is absent until the first event of its type arrives. There is deliberately no unconditional `updatedAt`: it would be modified on every write and hide the `stale` outcome. `lastEvent` is conditional (decision 27): it moves only when the event is newer than it, so a stale message still leaves the document untouched; it is the reader's "as of" marker, the input for liveness (`now - lastEvent.receivedAt`) and the reference for gap logging. The counters section belongs to the session it names; a new session's first counters event replaces it (higher `sessionId`), so counters restart at 0 per session by design (decision 6).

`alerts` — `_id` = message identity string; `{ deviceId, sessionId, seq, code, message, occurredAt, createdAt }`.

### The conditional upsert (the one operation that enforces invariants 1–3)

For an event of type `T` with key `(s, q)` and the new section value `next = { sessionId: s, seq: q, occurredAt, receivedAt, ...payload }`:

```js
filter = { _id: deviceId }; // single equality on the unique _id index
update = [
  {
    $set: {
      [T]: {
        $cond: {
          if: {
            $or: [
              { $eq: [{ $type: `$${T}` }, 'missing'] },
              { $lt: [`$${T}.sessionId`, s] },
              { $and: [{ $eq: [`$${T}.sessionId`, s] }, { $lt: [`$${T}.seq`, q] }] },
            ],
          },
          then: { $literal: next },
          else: `$${T}`,
        },
      },
      lastEvent: {
        $cond: {
          if: {
            $or: [
              { $eq: [{ $type: '$lastEvent' }, 'missing'] },
              { $lt: ['$lastEvent.sessionId', s] },
              { $and: [{ $eq: ['$lastEvent.sessionId', s] }, { $lt: ['$lastEvent.seq', q] }] },
            ],
          },
          then: { $literal: { sessionId: s, seq: q, type: T, receivedAt } },
          else: '$lastEvent',
        },
      },
    },
  },
];
options = { upsert: true, returnDocument: 'before' }; // findOneAndUpdate, decision 29; write concern { w: MONGODB_WRITE_W, journal: true, wtimeoutMS } is set on the client
```

Outcomes read from the document the operation returns — the document as it was before the update (`findOneAndUpdate`, `returnDocument: 'before'`, decision 29):

- `null` → no document for the device existed; created with this section (`created`).
- the section was absent, or `isNewer(event, before[T])` → replaced (`applied`).
- otherwise the stored section is newer or has the same key; nothing changed (`stale`; with `duplicate` from step 2 it is a duplicate, otherwise an older message).

`lastEvent` never moves alone: a message newer than `lastEvent` is newer than every section, so the three outcomes are unchanged by it; the previous `lastEvent` on the same returned document feeds the gap log of step 3.

Why this is safe without a read: the server evaluates the `$cond` against the document as it is at the moment of the update and writes the result atomically, so two concurrent writers for the same section cannot both win with a stale key — the second one sees the first one's section in `$${T}`. On the insert path the server "creates a base document from the equality clauses in the query parameter, and then applies the pipeline to the document to create the document to insert" (manual, `db.collection.update()` → "Upsert using an Aggregation Pipeline"), so the new document gets `_id: deviceId` from the filter and the section from the `$cond` (`$${T}` is missing on the base document, so the first branch is taken). The first two messages of a new device may race on the upsert; because the filter is a single equality on `_id` and the update does not touch `_id`, the server's documented behaviour is to turn the losing insert into an update of the newly inserted document, so no duplicate key error reaches the application (manual, "Upsert with Duplicate Values"). If the update nevertheless reports duplicate key error 11000 — a server that does not retry the colliding insert as an update — the handler runs the same update once more: the document now exists, the filter matches and the `$cond` decides. It is expected never to fire; three lines that take a server detail off the critical path. The `$literal` wrapper around the whole `next` object is required because inside a pipeline an object is parsed as an expression and a string starting with `$` (a diagnostic `message`) would be read as a field path; `$literal` "returns a value without parsing", for objects as well as strings (manual, `$literal`).

Where the logic lives: `packages/shared` exports only `isNewer(a, b)` — a pure comparison with no MongoDB types, part of the contract. The pipeline builder `newerThanStoredExpr(sectionPath, key)` (the `$or` above) is a storage decision and lives in `apps/processing`; its unit test runs the same five cases as `isNewer` — absent section; older session; same session, older `seq`; same key; newer session with a lower `seq` — and asserts the two agree. The integration tests in step 7 run the real update against MongoDB for each outcome, for the two-writer race, and with a diagnostic `message` that starts with `$` to prove the `$literal` wrapping.

## Consistency & Failure Modes

**Identity and order in the message:** `deviceId` (whose state), `sessionId` + `seq` (order key and, with `deviceId`, the identity), `type` (which section), `occurredAt` (diagnostic only). Nothing added by ingest or the broker is needed for correctness; the AMQP `messageId` and `timestamp` properties are for operators and logs.

**How "newer" is decided:** per section, `(sessionId, seq)` strictly greater than the stored watermark, evaluated by the server inside the atomic update (conditional upsert above). Equal = duplicate. Absent section = anything is newer.

**Dedup key and where it is enforced:** `(deviceId, sessionId, seq)`; enforced by the unique index on `events`, the `_id` of `alerts`, and the strictness of the state guard. All three are in MongoDB, so a duplicate arriving at another instance, minutes later, or after a restart is still rejected.

**Atomic operations and the guarantee:** three single-document writes, each atomic by MongoDB's single-document guarantee; the handler as a whole is idempotent, so its non-atomicity is harmless (table below). No transaction, no lock.

**Delivery semantics:** at-least-once from ingest to storage (confirms, manual ack after journaled writes); fire-and-forget from device to ingest with a bounded, named loss window; exactly-once effect at storage.

## Scaling

- **Ingest:** N instances, stateless; devices spread by address choice at connect time; an instance's capacity is bounded by open sockets and the confirm throughput of its AMQP connection. Adding an instance adds capacity linearly; no rebalancing is needed because nothing is pinned.
- **Processing:** M instances, all competing on `telemetry.events`. RabbitMQ dispatches round-robin among consumers with free prefetch slots. Adding an instance adds throughput until MongoDB's write capacity is the limit (three round trips per message on indexed keys). No upper bound from the topology; no partition count to manage.
- **Cost of the consistency mechanism per message:** one unique-index insert, one conditional single-document update, one keyed insert for the rare error diagnostic. All single-document, index-hit, lock-free at the application level. A stale message costs one matched-but-unmodified update; a duplicate additionally costs the rejected insert (one 11000 round trip). No message waits for another.
- **Hot device:** its messages spread over all consumers like any other device; the only effect is more concurrent conditional updates on one document, each still a single atomic write, with the losers costing one unmodified update. The alternative (routing by device) would make a hot device a single-consumer bottleneck instead.
- **What it does not give:** physical serialisation per device. A future event type with side effects that must run in order (or delta-shaped values) would need the modulus-hash + single-active-consumer topology (Alternatives). That switch changes the queue topology and the consumer setup, not the contract or the storage rules.

## Alternatives Considered

### Per-device routing: `x-modulus-hash` exchange + single active consumer

Partition `telemetry.events` into K quorum queues bound to a modulus-hash exchange keyed by `deviceId`, each with `x-single-active-consumer: true`, so all messages of one device are processed by one consumer in arrival order. Gains physical per-device serialisation (needed only for delta events or ordered side effects). Costs: the consumer count is capped at K; a hot device saturates one queue; changing K reshuffles almost every key and breaks order during the change; the consistent-hash plugin variant additionally loses locality across node restarts. Rejected because the contract already makes processing order irrelevant; documented as the upgrade path with its trigger.

### Freshness guard in the update filter (`{ _id, 'T.seq': { $lt: q } }` + upsert)

The textbook "update if current" form. Correct for a plain update, but with `upsert: true` a stale message makes the filter match nothing, the server tries to insert a second document with the same `_id`, and the application receives duplicate key error 11000 — an error round trip plus a retry for every stale or duplicate message, and error handling as normal control flow. The pipeline `$cond` form (decision 8) gives the same atomic guarantee in one round trip with no expected error.

### `$max` on the watermark

`$max` only protects the one field it is applied to; the other fields of the section written with `$set` in the same update would still be overwritten by an older message. Rejected.

### Single-node replica set in Docker Compose

Would enable retryable writes, transactions and change streams. Costs a one-time `rs.initiate()`, a not-yet-primary start-up window and `directConnection=true` for host-side tests. Nothing in this design uses any of the three features; the handler's in-place retry covers transient errors. Production runs a replica set; the switch is configuration only — the connection string and `MONGODB_WRITE_W=majority` (decision 22).

### Multi-document transaction around the three writes

Would make the handler atomic as a whole. Costs a replica set, more latency per message, and it protects nothing: the handler is already idempotent, so a partial run is repaired by the redelivery. MongoDB's guidance is to prefer single-document design over transactions.

### Increment-shaped counters

Would preserve per-increment detail and lifetime totals in the state document. Requires exactly-once application: every duplicate must be detected before `$inc` (dedup record consulted first, or the event insert as the gate with a crash window between insert and `$inc` that needs a transaction), and every lost message becomes a permanent error. Rejected in favour of cumulative values; lifetime totals can be derived from `events`.

### Full device snapshot in every message, one watermark per device

Simplest freshness rule (one comparison), but diagnostics are events, not state, and every message would carry every field. Per-section watermarks give the same simplicity per section at the cost of one helper.

### Device timestamp as the order key

No device-side counter, but collisions within a millisecond, unsynchronised clocks and clock jumps make it unsafe as the deciding key. Kept as diagnostics only.

### Application-level acknowledgement from ingest to the device

Closes the ingest-crash loss window: ingest replies "acked up to seq N" after the broker confirm, the device resends what is unacked. More protocol in both emulator and ingest, and per-connection in-flight tracking. Not needed while values are absolute and counters cumulative; documented as the upgrade path. Its resends would be handled by the existing dedup.

### Buffered reordering in processing (wait for a missing `seq`)

Adds latency and a per-device buffer per instance, and only helps when every event must be applied in order. Under absolute values, dropping the stale event is strictly cheaper.

### Distributed lock per device

Adds a component and latency; on lock expiry it produces exactly the race it was meant to prevent. The guarded update solves the same problem without it.

### In-process serialisation per device (async mutex keyed by `deviceId`)

Only orders work within one instance; two instances still race. Rejected as false safety.

### RabbitMQ streams / super streams

Kafka-like partitions with offsets and replay. No dead-letter or poison handling, a separate client library, offset management on the consumer. Out of proportion for this scope.

### TTL on `events` for dedup retention

Bounds storage; reopens the dedup window after expiry. Acceptable later because the state guard still rejects any late duplicate as "not newer"; not needed now.

### TCP load balancer in front of ingest

Production shape; adds a container and a config file to a dev Compose. Client-side address choice is enough to demonstrate the spread and the statelessness.
