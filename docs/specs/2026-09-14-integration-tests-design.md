## Problem

Steps 4 and 5 shipped ingest and processing with their broker and database adapters proven only by
scripted runs: throwaway Node scripts in `.local/research/` that start containers with `docker run`,
spawn the built service, and print PASS lines (ingest spec decision 25, processing spec decision
27). Those runs are evidence, not tests. Nothing fails when a regression lands (trade-offs T36 and
T44), and the assignment asks for automated tests with at least a part of them against real
MongoDB and RabbitMQ instances ("Testy" section of the PDF).

The tooling spec (step 1, decision 8) reserved a Vitest project named `integration` for exactly
this, with longer timeouts and no file parallelism, and left it empty. The Compose spec (step 6)
named the seam: the development stack fixes the project name `telemetry`, the queue names and the
host ports 15672 and 27017, so the tests need their own project name or their own Compose file.

This spec decides how the integration tests get their broker and database, how they isolate
themselves from the development stack and from each other, how the services under test are
started and stopped, how faults are injected, what counts as "processing has finished" in a
consumer that runs handlers concurrently, and which scenarios the three test files cover. It also
settles the questions the earlier specs deferred to step 7: how the infrastructure starts for
tests, and how `pnpm test` includes them.

| 12  | Fault injection                                               | Through the Compose CLI on the test project (`pause` / `unpause`, `restart`, `stop` / `start`, each followed by `up -d --wait` where the service must be healthy again), `docker compose exec -T rabbitmq rabbitmqctl set_vm_memory_high_watermark 0` (restored to `0.6`), and the management HTTP API (`DELETE /api/queues/{vhost}/telemetry.events`). **Every fault helper registers its recovery on the test environment before it issues the mutation and returns `recover()`, which runs until it has succeeded once (a concurrent call joins the running attempt; a failed or aborted attempt is retried, by `dispose()` under its own timeout if need be); `dispose()` runs, in reverse order, every recovery that has not succeeded yet, whether the test passed or failed.**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | These are the exact commands the scripted runs used, now behind typed helpers. Measured today: `pause` 115 ms, `restart` plus healthy 4 s, the memory alarm turns `GET /api/health/checks/alarms` from 200 to 503 within a second and back. `0.6` is the documented RabbitMQ 4.3 default. The undo stack is what keeps one failing test from leaving the broker paused or blocked for the next one; the stack's own `down -v` is the last resort. A test that restores a fault mid-way (I4, I7, C8, C9) calls `recover()`; if its attempt succeeded, `dispose()`'s call resolves at once, and if it failed or was cut off by the test's timeout, `dispose()` retries under its own timeout — a run-at-most-once wrapper would have skipped exactly the recovery that did not happen and left MongoDB stopped or paused for the next test. Because a retry may follow a partly successful attempt, every recovery checks the service's state first: measured today, `unpause` on a running service and `pause` on a paused one exit 1, `start` on a running service exits 0, a repeated `up -d --wait` on a healthy service returns in 0.6 s, and a paused container reads `unhealthy` in Docker at once and until about 10 s after its unpause, during which `up --wait` fails fast with exit 1 — so `unpause` is never followed by `up --wait`, while `restart` and `start` reset the status to `starting` and `up --wait` then waits as intended (2.6 s after a restart). The recovery is registered before the mutation is issued, and every in-body fault command runs with the test's own `AbortSignal` (bound to `env.signal` by the accessor every test body starts with), so a test that times out kills its Docker child at once rather than at the command's own timeout — a per-command timeout below `testTimeout` would not do, because a command started late in the test could still outlive it; `dispose()` awaits any command still settling and then undoes the mutation under the hook budget, so nothing is left running into the next test.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 13  | Waiting, and what "processing has finished" means             | Every wait resolves on an event (a log line, a `close`) or on a bounded poll (`waitFor(predicate, { timeoutMs, intervalMs })`, the same shape as `scripts/compose-check-lib.mjs`), with the Vitest `testTimeout` as the outer bound. **The completion signal for processing is the consumer's own acknowledgement count:** `stats().acked === <deliveries the test made>` together with `stats().inFlight === 0`. Assertions on events, state, counters and alerts are made only after that signal, and a test whose expectation depends on processing order (P2–P5, C13, C14) sends the next message only after the previous one is acknowledged. Where a redelivery could add deliveries the test did not make (C10: an acknowledgement lost in the restart), the signal is the **complete expected end state in the database** — every expected identity stored, every section at its expected key, every expected alert present (`awaitEndState`) — followed by `inFlight === 0`; once that state exists, a handler still running can only repeat a write that has no effect. **A queue count is never a completion signal**, and a threshold read while messages still move is `≥`, never `===` (I2: the count can pass the value between two polls). Queue emptiness is asserted after the signal through amqplib's `checkQueue` (`queueDepth`, live), never through the management API's `messages`. No `retry`. One deliberate fixed delay: I4 holds the memory alarm for 3 s, because a blocked connection produces no event and no predicate to wait on; the hold is the duration of the fault, not a wait for an outcome.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | The consumer runs up to `PROCESSING_PREFETCH` handlers at once (`apps/processing/src/consumer.ts`: `void this.#run(registration, message)`, not awaited), so observing a later message's effect proves nothing about an earlier handler that may still be between its event insert and its alert insert; the first draft's "sentinel message" rule was wrong for exactly that reason. An event document exists after the first of the three writes, so an event count is not a completion signal either. The acknowledgement is the one observation that follows every effect: `#settle` increments `acked` and calls `channel.ack` only with the handler's final result. The unit tests already follow "no sleep as a way to wait for something" (ingest spec, Tests), the test-quality reviewer rejects sleep-driven and retried integration tests, and a retry would hide the ordering and timing bugs these tests exist to catch. The management API's queue metrics are a snapshot emitted every `collect_statistics_interval` (5 s): measured today, a fresh quorum queue was returned by `GET /api/queues/{vhost}/{name}` without a `messages` field for 1.5 s after 100 confirmed publishes and then reported `messages: 0` for a further 5 s while the 100 messages sat in it, so the earlier `awaitQueueEmpty` (a poll for `messages === 0`) would have resolved on a stale zero with all the work still ahead — polling does not help when the first stale value already satisfies the condition. `rabbitmqctl list_queues` was stale on the quorum queue as well. amqplib's `checkQueue` reported 100 in the first sample after the confirms and 0 in the first sample after the acknowledgements, so it is the live read for the end-state assertion. A completion signal must be something the test accounts for exactly (its own acknowledgement count) or a state that cannot regress (the complete expected end state); an event count alone is neither, because an event document exists after the first of three writes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

## Chosen Approach

A two-service Compose file that the `integration` Vitest project starts and stops itself, a
virtual host and a database per test, the services under test composed in-process from the same
classes their entry points use, the consumer's acknowledgement count as the completion signal,
and three test files that turn the two scripted runs and the ledger's six behaviour items into
assertions, plus two tests for recovery after a partial write and one for durability across a broker restart.

```
docker-compose.test.yml         name: telemetry-test; rabbitmq 127.0.0.1:5673 / 15673; mongodb 127.0.0.1:27018; no volumes
vitest.config.ts                integration project: include test/integration/**, globalSetup test/harness/global-setup.ts,
                                groupOrder 1, fileParallelism false, testTimeout 30 s, hookTimeout 60 s
test/harness/global-setup.ts    up --wait, provide('stack'), down -v when it started the stack (also on a failed setup)
test/harness/environment.ts     vhost + database per test, undo stack, dispose, clean-up of a half-created environment
test/harness/stack.ts           docker compose control, rabbitmqctl, every fault registers its recovery before the mutation and
                                returns recover(), which runs until it has succeeded once
test/harness/management.ts      RabbitMQ HTTP API client (vhosts, permissions, queue metrics, get, alarms)
test/harness/services.ts        startIngest / startProcessing in-process, spawnService for SIGTERM
test/harness/clients.ts         devices (ws), the seeded load generator, the direct AMQP publisher, queueDepth, the store gate, MongoDB readers
test/harness/wait.ts            waitFor, awaitAcked, awaitEndState (exposed on env, bound to its signal), LogCapture
test/integration/pipeline.test.ts             P1–P6
test/integration/ingest-publisher.test.ts     I1–I7
test/integration/processing-consumer.test.ts  C6–C15
test/tsconfig.json              noEmit leaf project with references
```

**Why this over alternatives:** it adds no dependency, changes no application code, and reuses
what already exists: the Compose health checks, the child-process hooks, the test device, the
publish-arguments function, the log-capture pattern and the poll helper. Every fault is the same
command the scripted runs issued. The one new mechanism, a virtual host per test, is RabbitMQ's
own isolation feature and costs two HTTP calls.

Vitest 4.1.11 (docs at the release tag):

- [`globalSetup`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/globalsetup.md) — "Path to global setup files relative to project root"; a file exports `setup`/`teardown` or a default function returning the teardown; "The global setup is called before the test workers are created and only if there is at least one test queued, and teardown is called after all test files have finished running"; "you can pass down serializable data to tests via `provide` method and read them in your tests via `inject` imported from `vitest`", with the `ProvidedContext` module augmentation. Not marked root-only, so it belongs to the `integration` project. Decisions 5, 6.
- [`provide`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/provide.md) — "Properties have to be strings and values need to be serializable because this object will be transferred between different processes." Decision 6.
- [`passWithNoTests`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/passwithnotests.md) — root-only (`<CRoot />`), default `false`. Decision 15.
- [`fileParallelism`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/fileparallelism.md) — "Setting this to `false` will override `maxWorkers` option to `1`"; tests in one file are unaffected. Decision 15.
- [`sequence.groupOrder`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/sequence.md) — "If you don't set this option, all projects run in parallel"; groups run from lowest to highest. Decision 15.
- [`testTimeout`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/testtimeout.md), [`hookTimeout`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/hooktimeout.md) — defaults 5 s and 10 s in Node; the `integration` project keeps its 30 s / 60 s. Decision 13.
- [`retry`](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/config/retry.md) — exists, default 0; deliberately not used. Decision 13.
- [Test context, `signal`](https://vitest.dev/guide/test-context#signal) — an `AbortSignal` on the test context (`({ signal })`), aborted when the test times out, the run is cancelled with Ctrl+C, `cancelCurrentRun` is called, or `bail` stops the run after another failure; in the test context since 3.2, so present in 4.1.11. Bound to `env.signal` by the accessor and handed to `execFile` (whose `signal` option kills the child and rejects) and to `waitFor`. Decision 12.
- [Test projects](https://github.com/vitest-dev/vitest/blob/v4.1.11/docs/guide/projects.md) — `extends: true` inherits root options; `--project <name>` filters; options marked root-only cannot be set in a project. Decisions 8, 15.
- Measured today with the committed `vitest.config.ts`: `vitest run --project integration` exits 1 with "No test files found, exiting with code 1" (so `pnpm test:integration` already fails, with or without `--passWithNoTests=false`); `vitest run --passWithNoTests=false apps/ingest/src/config.test.ts` runs the one unit file and exits 0 while the `integration` project matches nothing. Decision 15.

Docker Compose:

- [`docker compose`, `-p`](https://github.com/docker/compose/blob/main/docs/reference/compose.md#use--p-to-specify-a-project-name) — precedence: `-p`, then `COMPOSE_PROJECT_NAME`, then the top-level `name:`, then the directory name. Verified today: `COMPOSE_PROJECT_NAME=telemetry-test-b docker compose config` renders `name: telemetry-test-b`. Decision 2, T63.
- [Compose `ports`](https://github.com/compose-spec/compose-spec/blob/main/05-services.md#ports) — short syntax `[HOST:]CONTAINER[/PROTOCOL]`, `HOST` is `[IP:](port | range)`; "You can either specify both ports (`HOST:CONTAINER`), or just the container port. In the latter case, the container runtime automatically allocates any unassigned port of the host." Decision 2.
- [`docker compose port`](https://github.com/docker/compose/blob/main/docs/reference/compose_port.md) — "Prints the public port for a port binding". Measured today: `127.0.0.1:32770` for an ephemeral binding, `127.0.0.1:32773` for the same service after `docker compose restart`. Decision 2.
- [`docker compose pause`](https://github.com/docker/compose/blob/main/docs/reference/compose_pause.md) — "Pauses running containers of a service. They can be unpaused with `docker compose unpause`." [`restart`](https://github.com/docker/compose/blob/main/docs/reference/compose_restart.md) — "Restarts all stopped and running services, or the specified services only." [`stop`](https://github.com/docker/compose/blob/main/docs/reference/compose_stop.md) — "Stops running containers without removing them. They can be started again with `docker compose start`." Decision 12.
- [`docker compose unpause`](https://github.com/docker/compose/blob/main/docs/reference/compose_unpause.md) — "Unpauses paused containers of a service"; what it does to a container that is not paused is not documented — measured today: exit 1 with `is not paused` (and `pause` on a paused container exit 1 with `already paused`, `start` on a running container exit 0), which is why every recovery checks the service's state before it acts and may run more than once. [`docker compose ps`](https://github.com/docker/compose/blob/main/docs/reference/compose_ps.md) — "By default, only running containers are shown"; `--services` "Display services"; `--status` "Filter services by status. Values: [paused | restarting | removing | running | dead | created | exited]". Decisions 5, 12.
- [`docker compose up`](https://docs.docker.com/reference/cli/docker/compose/up/) — `--wait`, `--wait-timeout` (compose spec decision 15); measured today, an `up -d --wait` on a project whose containers already run returned once they reported healthy (4 s after a `restart`). [`docker compose down`](https://docs.docker.com/reference/cli/docker/compose/down/) — `-v` removes "anonymous volumes attached to containers" (compose plan Research). [`docker compose exec`](https://docs.docker.com/reference/cli/docker/compose/exec/) — `-T` / `--no-tty` "Disable pseudo-TTY allocation. By default 'docker compose exec' allocates a TTY.", needed from a non-interactive parent; `scripts/compose-check.mjs` already uses it. Decisions 3, 5, 12.

- `docker compose config --format json` — verified today on a two-service file with `${TEST_AMQP_PORT:-5673}` mappings: `services.rabbitmq.ports[]` carries `{ host_ip, target, published: "5673", protocol }` (`published` a string), `services.rabbitmq.environment` the resolved `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS`, and `TEST_AMQP_PORT=5999` in the environment changes `published` to `"5999"`. RabbitMQ 4.3:

- [Virtual hosts, creating with the HTTP API](https://www.rabbitmq.com/docs/vhosts#using-http-api) — `PUT /api/vhosts/{name}` "accepts a number of optional keys" (`description`, `tags`, `default_queue_type`). [Deleting a virtual host](https://www.rabbitmq.com/docs/vhosts#deleting) — "Deleting a virtual host will permanently delete all entities (queues, exchanges, bindings, policies, permissions, etc) in it." Decision 7.
- [HTTP API reference](https://www.rabbitmq.com/docs/http-api-reference) — `PUT /api/vhosts/{name}` "Creates a virtual host or updates the metadata of an existing virtual host"; `DELETE /api/vhosts/{name}` "Deletes a virtual host, as long as it is not deletion-protected"; `PUT /api/permissions/{vhost}/{user}` "Grants (creates) or updates user permissions in the given virtual host", body keys `configure`, `write`, `read`; `GET /api/queues/{vhost}/{name}` "Returns metrics of a queue"; `DELETE /api/queues/{vhost}/{name}` "Deletes a queue"; `POST /api/queues/{vhost}/{name}/get` "Get messages from a queue. (This is not an HTTP GET as it will alter the state of the queue.)", body `count`, `ackmode` (`ack_requeue_false` "positively acknowledges the messages and marks them for deletion"), `encoding` (`auto`), `truncate`; `GET /api/health/checks/alarms` "Responds a 200 OK if there are no alarms in effect in the cluster, otherwise responds with a 503 Service Unavailable"; `GET /api/whoami` "Returns the username of the authenticated user". Decisions 7, 12, and the harness.
- [Reliability guide](https://www.rabbitmq.com/docs/reliability) — "Use of acknowledgements guarantees **at least once** delivery. Without acknowledgements, message loss is possible during publish and consume operations and only **at most once** delivery is guaranteed." A message the broker stored before its confirm reached the publisher is therefore published again by ingest after a reconnect and exists twice in the queue; the ingest spec's Tests table already allows this ("duplicates allowed"), and I2 and I7 assert distinct identities, not counts. Decision 24 and the catalogue.
- [Publishers, temporarily blocking publishing](https://www.rabbitmq.com/docs/publishers#disable-publishing) — `rabbitmqctl set_vm_memory_high_watermark 0` makes "a resource alarm to go off immediately". [Effects of resource alarms](https://www.rabbitmq.com/docs/publishers#alarms) — "all connections in the cluster that attempt to publish a message will be blocked until all alarms across the cluster clear"; a consuming connection is not affected, which is why scenario I4 leaves processing out. [Memory threshold](https://www.rabbitmq.com/docs/memory#threshold) — "The default value of 0.6 stands for 60% of available (detected) RAM." Decision 12.
- [Blocked connection notifications](https://www.rabbitmq.com/docs/connection-blocked) — `connection.blocked` goes to publishing connections the first time a resource is low; `connection.unblocked` "is sent when **all** resource alarms have cleared". Scenario I4.
- [Access control, default user](https://www.rabbitmq.com/docs/access-control#default-state) — the `guest` user's loopback-only restriction applies to `guest`, not to a user created through `RABBITMQ_DEFAULT_USER` / `RABBITMQ_DEFAULT_PASS` ([Docker Hub `rabbitmq`](https://hub.docker.com/_/rabbitmq), "Setting default user and password"). Measured today: that user answers `GET /api/whoami` with `"tags":["administrator"]` from the host. Decisions 4, 7.
- [`rabbitmqctl(8)`, `list_queues`](https://www.rabbitmq.com/docs/man/rabbitmqctl.8#list_queues) — `messages_ready` "The number of messages ready to be delivered to clients."; `messages_unacknowledged` "The number of messages delivered to clients but not yet acknowledged."; `messages` "The sum of ready and unacknowledged messages (queue depth)." Measured today against `rabbitmq:4.3-management` (4.3.5): with two messages published to a durable queue and one delivery held unacknowledged by an amqplib 2.0.1 consumer (prefetch 1, no ack), `GET /api/queues/%2F/<queue>` answered `messages: 2, messages_ready: 1, messages_unacknowledged: 1, consumers: 1`, so the HTTP endpoint's `messages` is that same sum — read from the statistics store, and therefore stale by up to the interval (next bullet). Decision 13.
- [Dead letter exchanges](https://www.rabbitmq.com/docs/dlx) — a message is dead-lettered when it "is negatively acknowledged … by an AMQP 0.9.1 consumer using `basic.reject` or `basic.nack` with `requeue` parameter set to `false`", when it expires, or when a length limit is exceeded; the `x-death` `reason` is one of `rejected` ("the message was rejected"), `expired`, `maxlen` and `delivery_limit` ("the message is returned more times than the limit"). C7's rejections go through `channel.reject(message, false)`, so their reason is `rejected`; a `delivery_limit` reason would mean the poison message was requeued and retried, which is the bug C7 exists to catch.
- [Management plugin, statistics interval](https://www.rabbitmq.com/docs/management#statistics-interval) — "By default the server will emit statistics events every 5 seconds (`5000` ms)"; "Entities that emit stats (connections, channels, queues, nodes) do so periodically", and `messages`, `messages_ready` and `messages_unacknowledged` in the queue endpoints come from that store (the Compose spec measured the interval as 5 000 ms, decision 26). Measured today on a quorum queue in a fresh virtual host, sampled every 100 ms: after 100 confirmed publishes, `GET /api/queues/{vhost}/{name}` answered 200 with the `messages` field absent for 1.5 s (a 404 only before the queue is declared at all), then `messages: 0` until 6.5 s, then 100; with ten deliveries held unacknowledged it took 3.8 s to show `messages_unacknowledged: 10`; after all 100 were acknowledged it still reported 100 for 5.2 s, and for 0.2 s it showed the ten as unacknowledged again (an older snapshot). `rabbitmqctl list_queues` reported `0 0 0` right after the confirms and `100 100 0` right after the acknowledgements, so it is not live for a quorum queue either. Consequence (decision 13): a poll towards zero can be satisfied by a stale value from before the messages arrived, so no queue count is a completion signal; `checkQueue` (amqplib, below) is the live read the harness uses for depth, and the management API keeps the vhosts, the permissions, `getMessages`, the queue-existence check of I3 and the alarm endpoint.

amqplib 2.0.1 ([channel API reference](https://amqp-node.github.io/amqplib/channel_api.html)):

- `connect(url)` — an absent path segment is the virtual host `/`; "When specifying another virtual host, remember that its name must be escaped"; "Usernames and passwords should be percent-encoded". Decisions 6, 7.
- Heartbeating — "If the client fails to read data from the connection for two successive intervals, the connection will emit an error and close." Decision 14.
- Dealing with failure — a failed operation will "reject the current RPC, if there is one", "invalidate the channel object, meaning further operations will throw an exception", and "reject any RPCs waiting to be sent"; "When a channel closes, any unresolved operations on the channel will be abandoned (and the returned promises rejected)." Why the direct publisher has no recovery and C10 runs in two phases. Decision 24.
- Connection events `blocked` / `unblocked` — emitted when the server blocks the connection on a resource shortage; `close()` on a blocked connection closes immediately. Scenario I4.
- `Channel#checkQueue` — "The reply from the server is the same as for `#assertQueue()`": `{ queue, messageCount, consumerCount }`, "a recent consumer count, and a recent message count". Measured today on a quorum queue: `messageCount` followed every change in the first sample taken after it (100 after 100 confirmed publishes, 90 with ten held unacknowledged, 100 once the holding channel closed, 0 after all were acknowledged, 100 on a fresh connection 10 ms after a broker restart); it is the ready count (the ten held were not in it), and `consumerCount` still counted a cancelled consumer with unacknowledged deliveries until its channel closed. `queueDepth` in the harness. Decision 13.
- Pending replies on close (read in the installed 2.0.1 sources on 2026-09-14) — the connection's `toClosed` (`lib/connection.js`) closes every channel, and a channel's `toClosed` (`lib/channel.js`) rejects each pending reply through `_rejectPending` with "Channel ended, no reply will be forthcoming"; the connection reaches `toClosed` on the broker's close-ok, on a socket end or error, and on the heartbeat timeout. A `close()` sent to a paused broker therefore leaves every pending call pending until the unpause or the heartbeat timeout. Scenario C11c.
- `Channel#cancel` — "Messages may arrive between sending this and getting its reply; once the reply has resolved, however, there will be no more messages for the consumer", which is why C11b releases its gate only after the consumer's `consumer cancel` line reports `resolved`. Decision 24.
- `Channel#deleteQueue`, `Channel#purgeQueue`, `ConfirmChannel#publish` with a confirm callback, `waitForConfirms` — the direct publisher and queue inspection in the harness. A `close()` on a connection the broker has already closed rejects (measured today after a restart: `Connection closed: 320 (CONNECTION-FORCED)`), so the direct publisher's `close()` resolves at once when it has seen the `close` event.

### The global setup (`test/harness/global-setup.ts`)

```ts
import type { TestProject } from 'vitest/node';

export type TestStack = {
  host: '127.0.0.1';
  amqpPort: number;
  managementPort: number;
  mongoPort: number;
  rabbitmq: { user: string; password: string };
  mongodb: { user: string; password: string };
};

declare module 'vitest' {
  export interface ProvidedContext {
    stack: TestStack;
  }
}

const SERVICES = ['rabbitmq', 'mongodb'] as const;

export default async function setup(project: TestProject): Promise<() => Promise<void>> {
  // None, or one service left behind by a crashed run: this run owns the stack and removes it.
  const running = (await compose(['ps', '--services', '--status', 'running'])).trim();
  const owned = running.split('\n').filter(Boolean).length < SERVICES.length;
  const teardown = async () => {
    if (owned) await composeInherit(['down', '-v']);
  };
  try {
    await composeInherit(['up', '-d', '--wait', '--wait-timeout', '120']);
    project.provide('stack', parseComposeConfig(await compose(['config', '--format', 'json'])));
  } catch (error) {
    // A stack this run started must not outlive a failure of the steps after the `up`; the
    // original error is the one reported.
    await teardown().catch(() => undefined);
    throw error;
  }
  return teardown;
}
```

`compose` is `execFile('docker', ['compose', '-f', <absolute path>, ...args])` promisified, with
`timeout: 180_000` and `maxBuffer: 64 MiB`; `composeInherit` is `spawn` with `stdio: 'inherit'`
so an image pull on the first run shows its progress. The Compose file path comes from
`fileURLToPath(new URL('../../docker-compose.test.yml', import.meta.url))`, as
`scripts/compose-check.mjs` does, so `.env` is read from the repository root whatever the working
directory. `parseComposeConfig` takes `services.rabbitmq.ports[]` (matching `target` 5672 and
15672), `services.mongodb.ports[]` (27017), and the four credential variables from the two
`environment` maps; a missing field is an error naming the field, never printing the map.

Failure modes: Docker absent or the daemon down — `docker compose` exits non-zero, the setup
throws with the tool's own message, Vitest exits non-zero; a port already bound — `up` fails with
Docker's bind error naming the port, and the README's fix is the `TEST_*_PORT` variable; the
stack up but unhealthy — `--wait-timeout 120` ends the wait and `up` exits non-zero; the stack up
but the configuration unreadable — the `catch` tears down what this run started and rethrows.
The teardown runs the same `down -v` a developer would.

```ts
export async function createEnvironment(): Promise<TestEnvironment>;
```

`WaitOptions` is `waitFor`'s options object without `signal` (`timeoutMs`, `intervalMs`, `describe`);
`Expected` is the expectation `generateLoad` returns (the Clients section); `ProcessingInstance` is
what `startProcessing` returns (the Services section).

`createEnvironment` reads `inject('stack')`, creates the virtual host (`PUT /api/vhosts/{name}`
with `{ description: 'integration test' }`), grants the default user everything on it
(`PUT /api/permissions/{name}/{user}` with `configure`, `write`, `read` all `.*`), opens the
harness's `MongoClient`, and returns (the amqplib connection is opened on first use). If any step after the vhost creation fails, the vhost is
deleted before the error is rethrown, so a failed `beforeEach` leaves nothing behind. `env.undo(action)` registers a recovery and returns `recover()`, a wrapper that **runs the action
until it has succeeded once**: a call while an attempt is running joins that attempt (one shared
promise, never two concurrent commands on one service), a call after a success resolves at once,
and a call after a failed or aborted attempt starts a new one. A fault helper hands `recover()` to
the test, and a test that restores the fault mid-way (I4, I7, C8, C9) calls it under the test's
`env.signal`; if that attempt fails or is cut off by the test's timeout, `dispose()` runs it again
under its own timeout, so a stopped or paused MongoDB never survives into the next test — a wrapper
that ran at most once would have skipped exactly the recovery that did not happen. Every recovery
action is idempotent by inspection, because the previous attempt may have partly succeeded: the
`pause` recovery first asks `ps --services --status paused` and is done when the service is not
paused (an `unpause` of a running service exits 1, measured), the `stop` recovery's `start` is a
no-op on a running service (exit 0, measured) and its `up -d --wait` is itself the state check,
the `restart` recovery is an `up -d --wait`, and the alarm reset is unconditional. `dispose()` runs
the recoveries in reverse order (so a paused container or a raised alarm is restored even after a
failed assertion), then closes the
harness's amqplib connection and its database client after `db.dropDatabase()`, then deletes the virtual host, which closes every
connection the services under test still hold and drops their queues. Each step is awaited and
bounded; a failure in one step is collected and the others still run, and the collected errors
are thrown at the end with their step names.

Test files keep the environment optional, so that a `beforeEach` that failed leaves nothing for
`afterEach` to trip on:

```ts
let env: TestEnvironment | undefined;
beforeEach(async () => {
  env = await createEnvironment();
});
afterEach(async () => {
  const current = env;
  env = undefined;
  await current?.dispose();
});
```

Tests read `env` through a small accessor, `environment(signal)`, called as the first line of
every test body with the `signal` destructured from the test context
(`it('…', async ({ signal }) => { const env = environment(signal); … })`): it fails with a clear
message when `beforeEach` did not complete, and it binds the test's own `AbortSignal` to
`env.signal`, from where every in-body fault command and harness wait takes it (the `stack.ts`
section below). The binding happens in the test body on purpose: the `beforeEach` that creates
the environment runs under the hook's budget, and the design does not rely on which signal a hook
receives. Services started through the harness register their own `stop` on `env.undo`, so a test
that fails mid-way still stops what it started, in the reverse order of starting; a child process
from `spawnService` registers a `SIGKILL` that runs only while the child is still alive, so no
process outlives its test either.

### Broker and database control (`test/harness/stack.ts`, `test/harness/management.ts`)

`stack.ts` wraps `docker compose -f docker-compose.test.yml`:

| Helper                  | Command                                                                                                                             | Returns                                                                                                                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pause(env, service)`   | `pause <service>`                                                                                                                   | `recover()`: `unpause <service>` when `ps --services --status paused` lists it; never followed by `up --wait` (the container reads `unhealthy` for ~10 s after an unpause, measured) |
| `stop(env, service)`    | `stop <service>`                                                                                                                    | `recover()`: `start <service>` (exit 0 when already running), then `up -d --wait --wait-timeout 40`                                                                                  |
| `restart(env, service)` | `restart <service>`, then `up -d --wait --wait-timeout 15` (20 s execFile ceiling; `env.signal` ends it earlier when the test does) | `recover()`: `up -d --wait --wait-timeout 40` (0.6 s on a healthy stack, measured; recovers a mid-way kill)                                                                          |
| `raiseMemoryAlarm(env)` | `exec -T rabbitmq rabbitmqctl set_vm_memory_high_watermark 0`                                                                       | `recover()`: the same with `0.6` (unconditional, idempotent)                                                                                                                         |

Every in-body call goes through `execFile` with **the test's own `AbortSignal`** (`env.signal`,
bound by the accessor of the previous section) and a `timeout` that is only a ceiling for a run
without a signal (20 s for the in-body `restart` plus `up -d --wait --wait-timeout 15`; 10 s for
`pause`, `stop` and the `rabbitmqctl` alarm, which are sub-second). A per-command timeout cannot
bound a command relative to the _test's_ deadline — a 20 s command started 15 s into a 30 s test
would run 5 s past the test — so the signal is the mechanism: Vitest aborts it when the test times
out, when the run is cancelled with Ctrl+C, when `cancelCurrentRun` is called or when `bail` stops
the run, and `execFile` then kills the Docker child and rejects. The fault helpers take `env` and read `env.signal`; the harness waits are methods of `env` bound
to it (`env.waitFor`, `env.awaitAcked`, `env.awaitEndState`); and a `LogCapture` receives it from
the `startIngest`, `startProcessing` or `spawnService` call that creates it — so nothing is passed
at the call sites and nothing can be forgotten: the accessor is the only way to reach `env`, and
every command or wait goes through it. `env` also keeps the promise of every
fault command still running, and `dispose()` first awaits their settlement (bounded at 5 s; an
aborted command settles at once) before it runs the undo stack. Each helper registers its recovery
on `env.undo` **before it issues the mutation**, not after it returns, so a mutation whose command
was aborted or killed mid-way (a test that timed out, a broker that will not come back) is still
recovered; the helper hands the test `recover()` (the environment section), and a test that wants the fault gone before its end calls it. `dispose()` runs the recovery commands under the 60 s `hookTimeout`, each
with its own `AbortSignal.timeout` and `up -d --wait --wait-timeout 40`, never with the test's
already-aborted signal, and awaits them before it deletes the vhost.

`management.ts` is a small `fetch` client with a `Basic` authorization header built from the
provided credentials, `AbortSignal.timeout(10_000)` on every request, and these methods:
`createVhost`, `deleteVhost`, `grantAll`, `queue(vhost, name)` (→ the status and, on 200,
`{ messages, consumers }` from `GET /api/queues/{vhost}/{name}`: the existence check of I3 and
the detail of failure texts, never a wait target — the metrics are a snapshot of the statistics
store that lags by up to the 5 s interval and, measured today, read `messages: 0` for 5 s while
100 confirmed messages sat in the queue), `deleteQueue`, `getMessages(vhost, name, count)`
(`POST …/get` with `ackmode: 'ack_requeue_false'`, `encoding: 'auto'`, no truncation; `count` is
an upper bound the test derives from what it sent, never from `queue().messages`), and
`alarms()` (→ 200 or 503). The vhost name is URL-encoded once, in the client. Live queue depth
comes from `queueDepth` in `clients.ts`, not from here.

`startIngest` builds the configuration as the unit tests do,
`{ ...loadIngestConfig({ RABBITMQ_URL: env.amqpUrl, ...overrides }), INGEST_HOST: '127.0.0.1', INGEST_PORT: 0 }`
(the schema's minimum of 1 guards the environment, not a test: `apps/ingest/src/server.test.ts`),
then does what `apps/ingest/src/main.ts` does minus the process wiring: a capturing logger,
`new AmqpPublisher({ url, heartbeatSeconds, logger })`, `new IngestServer({ config, publisher, logger })`,
`startHealthServer({ port: 0, report, logger })`, `publisher.start()`, `await server.listen()`,
which resolves with the port the kernel chose. It returns `{ port, healthPort, publisher, server, logs, readiness(), stop() }` where
`readiness()` performs a real `GET /readyz`, `logs` is a `LogCapture` created with `env.signal`,
and `stop` is the `recover()` wrapper `env.undo` returned for `server.shutdown()` →
`publisher.stop()` → `health.close()`, in the entry point's order.
`startProcessing` builds the configuration with
`loadProcessingConfig({ RABBITMQ_URL: env.amqpUrl, MONGODB_URL: env.mongoUrl, MONGODB_DB: env.dbName, ...overrides })`
(the database name is the test's own, so two tests never share a collection) and mirrors
`apps/processing/src/main.ts`: `MongoStore` with `url`, `dbName`, `writeW` and `timeoutMs` from
that configuration, `AmqpConsumer` (with the optional `hostname` so two instances are told apart

health server on port 0, `consumer.start()`,
`store.start(signal).then(ready → consumer.storeReady())`. It returns `{ healthPort, consumer, store, logs, readiness(), stats(), stop() }`; `stop` is the
`recover()` wrapper of `abort` → `consumer.stop()` → `store.close()` → `health.close()`. Both
`start*` functions register that sequence on `env.undo` and return the wrapper it gives back as
`stop`, so a test's own `stop()` (C11b) and the call `dispose()` makes are one attempt, never a
second `consumer.stop()`; `logs` is a `LogCapture` created with `env.signal`.

`spawnService` is the child-process `startIngest` helper of `apps/ingest/src/main.test.ts` made
shared, under its own name so it is never confused with the harness's in-process `startIngest`:
it spawns `process.execPath` with `--experimental-transform-types --import <app>/src/test-source-hooks.ts
<app>/src/main.ts`, a process environment that contains only the given `variables`
(`LOG_LEVEL=debug` among them), parses stdout as JSON lines through a `LogCapture` created with `env.signal`, and returns `{ lines(), waitForLog(match), closed, diagnostics(), kill(posixSignal) }` (`posixSignal` is the process signal to send, unrelated to the `AbortSignal`). It registers on `env.undo` a
`kill('SIGKILL')` that runs only while the child is alive (`exitCode === null && signalCode ===

no process behind. The health port of a child is a free port the harness picks by
listening on port 0 and closing (the unit test's `net` pattern); `INGEST_PORT` the same way for
the ingest child.

### Clients and readers (`test/harness/clients.ts`)

- `connectDevice(port)` — `connectTestDevice({ port })` from `apps/ingest/src/test-device.ts`, returning the same `sendMessage`, `closed` and `terminate`.
- `generateLoad({ devices, messages, hotShare, duplicatePercent, swapPercent, seed, deviceIdPrefix })` — a seeded generator (the emulator's `random.ts` PRNG may be reused) that returns `{ sends, expected }`: `sends` is the ordered list of messages to send, one session per device, all four types in rotation with an error diagnostic every tenth message, where one hot device receives `hotShare` of the messages and the rest are spread evenly, a `duplicatePercent` share of messages appear twice in a row, and a `swapPercent` share of adjacent pairs of one device's stream are swapped; `expected` is computed from `sends` alone: the distinct identities, the highest `(sessionId, seq)` per device and section, the highest overall per device (`lastEvent`), the number of duplicate sends, and the distinct error diagnostics (the alerts). Device ids are `${deviceIdPrefix}-NNNN` by index and independent of `seed` (the way `formatDeviceId` forms them in `apps/emulator/src/config.ts`, and `deviceSeed` seeds only the payload values), so two calls with different `deviceIdPrefix` produce disjoint device populations. `mergeExpected(a, b)` combines two expectations — the union of `identities` and of `alerts`, the per-device section and `lastEvent` maps merged (a shared device key is a programmer error it rejects), `duplicates` added — because a shallow spread would keep only the second batch's collections. `deviceIdPrefix` defaults to `load`, so a single-call test needs no prefix. P6 splits `sends` per device and sends each stream over that device's connection; C6 publishes `sends` in order.
- `openDirectPublisher(env)` — an amqplib connection on `env.amqpUrl`, a confirm channel that declares the topology with the shared constants (the same six calls as the services), `publish(message, receivedAt)` using `toPublishArgs`, `publishRaw(body, properties)` for poison bodies, `close()`; every publish resolves on the confirm and rejects when the confirm fails or the channel closes. **No recovery**: a test that restarts the broker opens a new publisher afterwards (C10); a rejected publish fails the test in the publisher, where the problem is, and its `close` is on `env.undo`. It records its connection's `close` event, and `close()` resolves at once when the connection is already gone (a `close()` after that event rejects, measured after a broker restart), so a publisher whose broker restarted (C10, C15) does not fail the dispose.
- `queueDepth(env, queue = TELEMETRY_QUEUE)` — `{ ready, consumers }` from `checkQueue` on a channel opened for the call on the harness's connection (`env.amqp()`); a missing queue rejects the check and closes that channel, and the helper returns `undefined`, which a `waitFor` predicate treats as "not yet" (I3). This is the live depth: measured today, `messageCount` followed every change in the first sample, while the management API lagged by up to 6.5 s. It counts ready messages only; deliveries a consumer holds show in that consumer's `inFlight`.
- `holdInserts()` — the store gate of C11b: returns `{ wrap, release }`; `wrap(store)` returns a `StorePort & StoreWatcher` that delegates `applyState`, `insertAlert` and `watch` unchanged and makes every `insertEvent` wait for `release()` before delegating; `release` is registered on `env.undo`, so a failed test never leaves handlers waiting.
- `messages(deviceId, sessionId)` — a builder that returns `status`, `metrics`, `counters`, `diagnostic` messages with a given `seq` and payload overrides, so the tests read as identity and order, not as JSON.
- `readEvents(env)`, `readState(env, deviceId)`, `readAlerts(env)` — sorted reads of the three collections through `env.db`; C13 and C14 delete documents through the same `env.db`.

### Waiting (`test/harness/wait.ts`)

`wait.ts` exports the primitives, and `env` exposes them bound to the test's signal, which is the
only form the tests use: `env.waitFor(predicate, { timeoutMs = 20_000, intervalMs = 50, describe })`
polls until the predicate resolves truthy and rejects with `describe()`'s text after the deadline,
or at once when `env.signal` aborts, so a timed-out test stops polling (`describe` returns counts
and state names, never a URL); `env.awaitAcked(instance, count)` is
`env.waitFor(() => instance.stats().acked === count && instance.stats().inFlight === 0)`, the
completion signal of decision 13; `env.awaitEndState(expected)` polls the three collections
until every identity in `expected.identities` has an event document, every section of every
device holds its expected key, and every expected alert exists — the same comparison the
assertions make, used as the signal where a redelivery could add deliveries the test did not make
(C10): a state that cannot regress is a sound signal, a queue count is not (decision 13). Every poll written in a "Wait" cell is an `env.waitFor`. Nothing polls the management API's
`messages` towards zero. `LogCapture` holds the parsed lines of one service and is created by
`startIngest`, `startProcessing` and `spawnService` with `env.signal`; it exposes `lines`,
`find(match)` and `waitForLine(match, timeoutMs)`, which resolves on the push that matches (no
polling) and rejects at once when the signal aborts.

### Test catalogue

Every test creates its environment in `beforeEach`; the "Wait" column is the event or poll that
bounds the test before the assertions in "Assert" run. `stats()` is the consumer's
`ConsumerStats` (`received`, `acked`, `created`, `applied`, `stale`, `duplicate`, `alerts`,
`gaps`, `rejected`, `failed`, `retries`, `returned`, `abandoned`, `inFlight`, `paused`) or the
publisher's `PublisherStats` (`confirmed`, `unconfirmed`, `republished`, `returned`). `gaps` is
never asserted: with concurrent handlers a higher `seq` can be written before a lower one of
another section, which the counter reports as a gap (compose spec, Consistency). `duplicate` counts
duplicate event inserts from any cause: a duplicate or redelivered message, or a handler's
transient retry, which restarts from the event insert and reports the repeated insert
(`apps/processing/src/handler.ts`, `runAttempt` and `STATE_COLLISION`); the load tests therefore
assert `duplicate ≥ expected.duplicates` (every injected duplicate was detected as one), never
equality, no test infers the cause of a duplicate from the count, and `duplicate` is asserted
exactly only where the message and its copy cannot race on a new device's first state write
(P2, C13, C14). A numeric bound
in a "Wait" cell applies to the one step it is written next to; every other step is bounded by
the test's `testTimeout`. A threshold read while messages still move is written `≥` (I2), because
the count can pass the value between two polls; `===` is used only for final counts.
`queueDepth(env).ready` is the live depth of `telemetry.events` (another queue is named where it
is meant).

`startIngest` and `startProcessing` resolve once their own servers listen, not once the broker
connection is ready, so a scenario that injects a broker fault or needs a particular consumer to
receive work first awaits the readiness it depends on: `publisher.isReady` before a broker fault
or a queue deletion (I3, I4, I7), and `'consumer registered'` on every instance that must receive
before the publish (C6, and the second instance of any two-instance test). Without that wait a
fault could land before the publisher connected (no recycle, nothing republished) or one instance
could drain the queue before the other registered.

### What the README will say (step 8)

Docker Engine 25 / Compose 2.20.2 or newer are required for `pnpm test` and
`pnpm test:integration`; `pnpm test:unit` runs without Docker. The test stack is separate from the
development stack and both can run at the same time. The reset command is
`docker compose -f docker-compose.test.yml down -v`. Two test runs on one machine at the same
time need a different `COMPOSE_PROJECT_NAME` and different `TEST_*_PORT` values for the second.

### What this step does not change

No file under `apps/` or `packages/` changes in this step: the classes, the constants, the
child-process hooks and the test helpers are used as they are. The two consumer fixes of
2026-09-14 (`apps/processing/src/consumer.ts`: the shutdown bound and the registration bound,
found by the audit that added C11c) landed before this step, with their own unit tests. The development stack, `scripts/compose-check.mjs` and the
unit tests are untouched.

## Consistency & Failure Modes

This step adds no message path and no write path. What it adds is proof: each invariant in
`CLAUDE.md` is exercised against the real broker and database by a named test.

| Invariant                                            | Proven by                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Logical order wins                                 | P3 (an older same-section message leaves the section untouched, `stale`), P4 (a lower seq of another section is applied), P5 (a straggler of an old session is `stale`), P6 and C6 (every section holds the expected highest key under duplicates, swaps and concurrency)                                                                                                                                                                                                                                       |

## Alternatives Considered

### Testcontainers instead of a Compose file

`testcontainers` 12.1.0 is maintained (MIT, published 2026-08-04, 4.7 M weekly downloads) and
would start the two containers from the test process without a Compose file. Rejected: it is a
new runtime dependency to vet and keep current, a second way of describing the same two
containers next to the Compose files the assignment asks for, and it does not remove the
fixed-port need (decision 2) for the restart scenarios. The Compose file plus sixty lines of
global setup does the same with what is already installed.

### The development file under another project name

`docker compose -p telemetry-test up rabbitmq mongodb` would reuse `docker-compose.yml`.
Rejected: its host ports are fixed to 15672 and 27017, so the two stacks could not run together,
and its named volumes would carry state between runs. An override file could fix both, but `ports`
merge by appending unless `!override` is used, which is one more Compose rule to explain than a
45-line file.

### Compose `extends` from the development file

Would keep the image tags and health checks in one place (T61). Rejected for now: the test
service needs `!override` on `ports` and `volumes` and a comment explaining both, for two
services that are otherwise nine lines each. Named as T61's upgrade path.

### Ephemeral host ports

The cleanest answer to port collisions, and what Testcontainers does. Rejected by measurement:
`docker compose restart` re-allocates the port, and the services under test cannot follow, so
every restart and stop-and-start scenario would fail for the wrong reason.

### A test-only prefix for queue and collection names

A `TELEMETRY_NAME_PREFIX` environment variable in `packages/shared/src/topology.ts` would let
every test use its own queue on one virtual host. Rejected: it changes production code for the
tests' sake, it would not isolate broker-wide faults (pause, restart, alarm) any better than a
virtual host does, and a virtual host is what RabbitMQ provides for exactly this.

### A virtual host per file instead of per test

Fewer HTTP calls. Rejected: a delivery still in flight or a consumer still registered when one
test ends would be visible to the next test on the same queue, which is the kind of interference
these tests exist to catch. Two calls per test are measured in milliseconds.

### The services under test as containers from the built image

Would test the exact artefact Compose runs. Rejected: `docker compose up --build` costs minutes
per run, the tests would observe only logs and `/readyz`, and the Compose check already runs the
image end to end. The child-process shape covers the signal path; the in-process shape covers
everything else with typed access.

### Child processes for every scenario (the scripted runs' shape)

Rejected: the only observation channel is log-line parsing, every state read becomes a wait on a
line, and each scenario pays a process start. Kept for the two signal-path scenarios (I5, C11), where the
process boundary is the subject; the drain with deliveries in flight (C11b) is in-process,
because only there can deliveries be held (below).

### Sentinel messages as the completion signal

The first draft's rule: send a newer message, wait until it is applied, then inspect the earlier
effects. Rejected on reading the consumer: handlers run concurrently up to the prefetch, so the
sentinel can be acknowledged while an earlier handler is still between its event insert and its
alert insert. The acknowledgement count (decision 13) is the signal that follows every effect;
the only sentinel left is I6's valid frame, which is sound because ingest decodes one
connection's frames in order.

### Driving the many-devices test with the emulator fleet

The first draft's P6. Rejected: the fleet keeps no record of what it sent that a test could read,
so the expected outcome had to be derived from the stored events, and a message dropped on the
way would have been invisible. The harness generator yields both the input and the expectation;
the emulator keeps its own unit tests and the Compose check.

### A reconnecting direct publisher for the broker-restart scenario

The scripted run's shape (publish through the restart, reconnect and publish again on failure).
Rejected for C10: it adds recovery logic to the test client whose correctness the test would then
depend on, and a failure inside it would be indistinguishable from a consumer failure. Two phases
with a fresh publisher after the restart prove the consumer's reconnection with a publisher that
does nothing clever; the durability of confirmed messages is C15's, with the batch pending across
the restart.

### A larger burst to catch SIGTERM with deliveries in flight

The earlier C11: publish 2 000 messages and send SIGTERM at the child's first `delivery processed`
line. Rejected: the number of messages left for the second instance depends on when the parent
reads the child's stdout and on how fast the child processes, so `received ≥ 1` on the second
instance can fail a correct implementation; the scripted run's first attempt already saw the
signal arrive after all 300 messages had been processed. A burst is not a hold.

### Pausing MongoDB to hold a child process's deliveries

`pause(env, 'mongodb')` would make a child hold exactly its prefetch, deterministically. Rejected
for the drain test: the handlers could then never complete, so the test would observe only the
drain-budget expiry and the requeue (the abort path), and a failure in the MongoDB timeout handling
would be indistinguishable from a shutdown bug. The gate of C11b holds the same deliveries
in-process and releases them, so the drain itself — cancel, complete, acknowledge, close — is
what the test proves. Named in T65 as the upgrade path if the signal and the drain must be one
observed sequence.

### Starting the stack by hand before `pnpm test`

Rejected: `pnpm test` would fail on a clean clone until the developer read the README, and CI
would need its own start step. The ownership rule keeps the hand-started stack possible for
inspection.

### Sleeping for "nothing happens" assertions, and `retry`

Rejected (decision 13): a sleep proves nothing about what did not happen, and a retry hides the
ordering and timing bugs this suite exists to catch. Bounded waits on the acknowledgement count
instead.

### Per-package `test/integration` directories

The tooling spec's original layout. Superseded (decision 8): the pipeline tests belong to no one
