## Problem

The consistency spec fixes what a message carries, how "newer" is decided and how state is stored. It leaves to step 2 the choices that turn that into code: the wire framing between device and ingest, the validation library that also produces the TypeScript types, the logger, how configuration is loaded and which variable names exist, and where the storage document types and the queue and collection names live. Every service imports the results, so they must be decided once, with versions pinned and documentation verified, before any service is written.

| 1   | Wire framing between device and ingest                | **Newline-delimited JSON (NDJSON) over the raw TCP socket.** One message is one JSON object encoded as UTF-8 and terminated by `\n`. A frame is complete only when its newline has arrived; whitespace-only lines are ignored; a line longer than `MAX_FRAME_BYTES` (65 536) is a protocol violation — the decoder returns `ok: false` with a `FrameTooLongError` (it never throws), resets, and ingest closes that connection; bytes left without a newline when a connection closes are dropped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Two facts make the newline an unambiguous terminator. Inside string values a compliant generator must escape every control character, so a raw U+000A can never come from a `message` or `code` field (RFC 8259 §7 and §10, Research). Outside strings the JSON grammar does allow line feeds as insignificant whitespace (§2), so the guarantee for the whole message comes from the encoder: `encodeFrame` is the only producer of frames in this system and calls `JSON.stringify(message)` without the `space` argument, which inserts no whitespace at all (MDN, Research). Compact JSON is therefore part of the wire contract: a foreign device that pretty-prints its JSON is rejected line by line as invalid JSON, and the emulator uses `encodeFrame`. A trailing `\r` is insignificant whitespace to `JSON.parse` (§2), so CRLF clients work unchanged. The stream is readable with `nc` and in packet captures, which helps the technical discussion and debugging. The size bound keeps a misbehaving client from growing memory without limit; a valid message is a few hundred bytes. Rejected: length-prefixed binary framing (a custom parser on both sides, not human-readable; the upgrade path if payloads grow to many KiB); WebSocket (an HTTP upgrade plus a library for machine clients that gain nothing from it); MessagePack (smaller on the wire, another dependency, and the contract must stay inspectable).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

| 14  | Argument style, and where runtime validation runs     | Function arguments are positional by default. A single named object (a parameter object) is used when a function takes three or more arguments, or two or more arguments of the same type — `createLogger({ service, level, destination })` is the existing example. Argument and return types are derived from the message schema (`z.infer`, `Pick<>`, `.extend()` on a payload schema), never redeclared; no second schema is written for a shape the message schema already describes. Runtime validation runs only where data enters a process from outside the type system: socket frames (`decodeTelemetryMessage`), environment variables (`loadConfig`), the emulator's command-line arguments (step 3), the AMQP body and the `x-received-at` header (consistency spec, decision 18), and a MongoDB read that a branch or a test assertion depends on. Inside a process no function re-validates a value the compiler already typed. The argument rule binds new code; `max-params: ['error', 2]` in `eslint.config.js` enforces the "three or more" half of it (task 10), and the three existing signatures that keep positional same-typed arguments are named opposite. | Two independent choices hide under the word "DTO", and only the first is a style question. A parameter object makes the call site self-documenting and two same-typed arguments unswappable; below three arguments it is noise, and `isNewer(candidate, stored)` stays positional on purpose — it is the comparator idiom, and the swap that would matter lives in the MongoDB pipeline mirroring it, where a parameter object cannot help. Two further signatures keep positional same-typed arguments, each for a reason: `envInt(min, defaultValue)` is protected completely by its own import-time guard — the guard enforces `defaultValue >= min`, so any swap that changes behaviour makes the new default smaller than the new minimum and throws when the module is imported — and `FrameTooLongError(bytes, limit)` only formats an error message, where a swap costs a wrong number in one log line and no invariant, and positional arguments are the idiom for an Error constructor. Those three are the complete list in `packages/shared` after this plan; `max-params` catches the rest mechanically. Runtime validation inside a process is an assertion written expensively: `eslint.config.js` extends `recommendedTypeChecked`, which sets `no-explicit-any` and six `no-unsafe-*` rules to error, so a value typed `TelemetryMessage` can only be malformed if it entered through a cast or an untyped library return — that is, at one of the boundaries above. A third `safeParse` per message would add to the cost already named in T12 and buy nothing measurable. Rejected: validating at internal call sites (no failure mode it prevents that the linter does not, and unmotivated ceremony reads as over-engineering); a separate DTO schema per service (a second source of truth that drifts, against the "types derived from the schema" rule). Derivation gotcha, verified in the pinned declarations: in zod 4.6.2 `ZodObject` has `.pick`, `.omit` and `.extend`, but `ZodDiscriminatedUnion` has none of them, so a subset of `telemetryMessageSchema` is derived at the type level (`Pick<>`, as `MessageIdentity` does) or built from `envelopeShape` plus a payload schema. |

## Chosen Approach

`packages/shared` becomes the contract and nothing more: one zod schema is the source of the message type and of the storage document types; three pure helpers (`messageIdentity`, `orderKey`, `isNewer`), one frame codec and one decoder are the only logic; the broker and database names are constants; a pino factory and a zod-based environment loader are the cross-cutting helpers. The package performs no I/O and depends on no client library, so every service and every test imports it without a broker or a database.

**Why this over alternatives:** one library (zod) serves both the wire contract and the configuration; one logger; nothing in shared needs a mock. Each piece can be explained in one sentence in the technical discussion, and each has a unit test that names a concrete input and its outcome.

- [Zod — Defining schemas](https://zod.dev/api) (docs for 4.x, read 2026-09-11) — `z.strictObject` "throws an error when unknown keys are found"; `z.discriminatedUnion(key, options)` with `z.literal` discriminators; `z.literal`, `z.enum` on an `as const` array; `z.int()` "restricts to safe integer range"; `z.number()` "allows any finite number" and rejects `NaN` and `Infinity`; `z.string().min/max/regex`; `z.coerce.number()` = `Number(input)`; `.default()` "short-circuit[s] the parsing process … the default value must be assignable to the output type"; `.prefault()` as the parsed alternative; `z.ZodType` as the generic bound for schema parameters (section "Apply").
- [Zod — Basic usage](https://zod.dev/basics) — `.safeParse()` returns `{ success, data | error }`; `error.issues[]` carries `code`, `path`, `message`; `z.infer`, `z.input`, `z.output`.
- [Zod — Formatting errors](https://zod.dev/error-formatting) — an unknown key yields `code: 'unrecognized_keys'` with the path of the object; `z.prettifyError` exists (not used; the decoder formats issues itself so the log line stays one string).
- [Zod 4 migration guide — `z.number()`](https://zod.dev/v4/changelog#znumber) — "`POSITIVE_INFINITY` and `NEGATIVE_INFINITY` are no longer considered valid values"; `.int()` "no longer accepts unsafe integers".
- zod 4.6.2 package manifest (`npm view zod@4.6.2 exports engines`, 2026-09-11) — the root entry `"."` is `{ types: ./index.d.cts, import: ./index.js, require: ./index.cjs }`: one declaration file serves both module systems and the `import` condition resolves to the ESM build; `index.d.cts` re-exports `z` as a named and as the default export; a `./compile` entry point exists (upgrade path in decision 2); no `engines` field.
- Local probe (2026-09-11 and 2026-09-12, scratch project outside the repository, TypeScript 6.0.3 with this repository's `tsconfig.base.json` options, Node 24.21.0): the import forms compile under `nodenext` + `verbatimModuleSyntax`; every one of the 23 rows of the plan's invalid-input table produced exactly the asserted issue code and path — `invalid_union` at `['type']` for an unknown or missing discriminator, `invalid_value` at `['v']` for the literal, `invalid_format` / `too_big` / `too_small` at `['deviceId']`, `too_small` at `['seq']` for `0`, `invalid_type` at `['seq']` for `1.5` (`z.int()` reports `expected: 'int', format: 'safeint', code: 'invalid_type'`), `invalid_type` at `['sessionId']` for a string and at `['occurredAt']` when missing, `unrecognized_keys` at `[]` and at `['payload']`, `invalid_type` at `['payload','ramPercent']` when missing and at `['payload','temperatureC']` for `NaN` and `Infinity`, `too_small` at `['payload','operationsTotal']`, `invalid_type` at `['payload','uptimeMs']` for `0.5`, `invalid_value` at `['payload','state']` and `['payload','severity']` (`z.enum` reports `code: 'invalid_value'` with `values: [...]`), `too_small` at `['payload','code']`, `too_big` at `['payload','message']`, `invalid_type` at `[]` for a string and for `null`; a diagnostic `message` starting with `$` is accepted; `z.coerce.number().int().min(1).default(50)` returns `50` for `undefined`, `7` for `'7'` and rejects `'abc'` with `invalid_type … received NaN`; `JSON.parse('{"a":1}\r')` parses; a declaration build (`declaration: true`) names every exported type (for example `z.ZodDefault<z.ZodCoercedNumber<unknown>>`), so the package's `tsc -b` build works.
- [RFC 8259 — The JSON Data Interchange Format](https://www.rfc-editor.org/rfc/rfc8259) — §7 Strings: "All Unicode characters may be placed within the quotation marks, except for the characters that MUST be escaped: quotation mark, reverse solidus, and the control characters (U+0000 through U+001F)", with the two-character escape `\n` for U+000A; §10 Generators: "The resulting text MUST strictly conform to the JSON grammar"; §2: `JSON-text = ws value ws` where `ws` includes `%x0A` line feed and `%x0D` carriage return, and "Insignificant whitespace is allowed before or after any of the six structural characters". Together with the encoder rule below: string values never contain a raw newline, `encodeFrame` emits none between tokens, and a trailing `\r` is ignored by the parser (decision 1).

### Message contract (`message.ts`)

The schema is the consistency spec's `TelemetryMessage` written in zod. Rules: all five envelope fields present with the given types and ranges; `v` is the literal `1`; `deviceId` matches `^[A-Za-z0-9_-]+$` and is 1–64 characters; `sessionId` is a safe integer between `SESSION_ID_MIN` (1 500 000 000 000) and `SESSION_ID_MAX` (4 100 000 000 000, consistency spec decision 28), `seq` a safe integer ≥ 1, `occurredAt` a safe integer ≥ 0; `type` is one of `status`, `metrics`, `counters`, `diagnostic`; the payload is a strict object for that type; numbers are finite; `cpuPercent` and `ramPercent` are between `PERCENT_MIN` (0) and `PERCENT_MAX` (100); `counters` values are integers ≥ 0; `code` is 1–64 and `message` up to 1 024 characters. Unknown keys anywhere are rejected. Exported: `telemetryMessageSchema`, the four payload schemas, `TELEMETRY_EVENT_TYPES`, the types `TelemetryMessage`, `TelemetryEventType`, `TelemetryMessageOf<T>`, `PayloadOf<T>`, `StatusPayload`, `MetricsPayload`, `CountersPayload`, `DiagnosticPayload`, and the bound constants. The exact code is in the plan (task 2).

### Identity and order (`identity.ts`)

`MessageIdentity = { deviceId, sessionId, seq }`, `OrderKey = { sessionId, seq }`. `messageIdentity(m)` returns `` `${deviceId}:${sessionId}:${seq}` `` (log field, AMQP `messageId`, `alerts._id`). `orderKey(m)` returns `[sessionId, seq]`. `isNewer(candidate, stored)` is the single definition of "newer": `candidate.sessionId > stored.sessionId || (candidate.sessionId === stored.sessionId && candidate.seq > stored.seq)`; equal keys are not newer. The processing pipeline builder (step 5) is derived from it and its test runs the same cases. `extractRawIdentity(value)` returns the subset of the three fields present on an unvalidated value with the right primitive type — `deviceId` cut to `DEVICE_ID_MAX_LENGTH`, the numbers only when they are safe integers — for log lines about rejected input, which a device must not be able to inflate.

### Framing (`framing.ts`)

`encodeFrame(message)` → `Buffer` of `JSON.stringify(message) + '\n'` in UTF-8; no `space` argument, so the JSON text is one line (MDN, Research) — compact JSON is part of the wire contract, and a pretty-printed message from a foreign client is rejected line by line as invalid JSON. `FrameDecoder` keeps the unfinished tail between `push(chunk)` calls and returns the complete lines (without their newline) in order; whitespace-only lines are skipped; a trailing `\r` is left in place because `JSON.parse` accepts it as whitespace (RFC 8259 §2). `push(chunk)` never throws: it returns `{ ok: true, frames }`, or `{ ok: false, frames, error: FrameTooLongError { bytes, limit } }` when a complete line, or the buffered tail, exceeds `maxFrameBytes` (constructor argument, default `MAX_FRAME_BYTES` = 65 536), with the buffer cleared and the rest of that chunk unread; `frames` is on both branches so the lines decoded before the oversized one cannot be dropped by accident. The tail is kept as the list of chunks it arrived in and each `push` scans only its own chunk, so the cost is one copy and one scan per byte however the bytes are split (a one-byte drip up to the limit costs ~13 ms, not the ~280 ms of re-copying the tail on every push). Ingest closes the connection on `ok: false` (decision 1). `pendingBytes` exposes the buffered tail length for the log line at connection close. Bytes that are not valid UTF-8 become U+FFFD replacement characters (Node Buffer docs, Research); the frame then fails as invalid JSON or as an invalid string value, never as an exception.

### Decoding (`decode.ts`)

```ts
type DecodeResult =
  | { ok: true; message: TelemetryMessage }
  | { ok: false; reason: 'invalid_json' | 'invalid_schema'; detail: string; identity: RawIdentity };
```

`detail` is the `JSON.parse` error message, or every zod issue as `path: message` joined by `; ` (`(root)` for an empty path); each message is capped at 200 characters, so the path of every failing field survives however long one message is, and the parser message gets the same cap. `identity` is `extractRawIdentity` of the parsed value (empty for invalid JSON).

### Logging (`logger.ts`)

`LOG_LEVELS = ['trace', 'debug', 'info', 'warn', 'error', 'fatal', 'silent']`. `createLogger({ service, level, destination? })` returns a pino `Logger` with `base: { service, hostname }` and ISO time; `destination` is for tests. Three mechanisms strip `scheme://user:password@` from every line, because the path-based `redact` (`RABBITMQ_URL`, `MONGODB_URL`) cannot reach a URL inside a string: `serializers.err` runs the standard error serializer and then `redactUserinfo` over its `message`, `stack` and nested fields; `hooks.logMethod` strips every string argument and gives a bare error an explicit stripped message (pino would otherwise copy `err.message` into `msg` before any serializer runs); `formatters.log` walks the merging object (plain objects and arrays, four levels deep; an `Error` is left to the serializer; a value with its own `toJSON` is serialised through it and the result redacted when it is a string — a `URL` prints its whole `href`, userinfo included) for a connection string under any other key. `redactUserinfo(text)` is exported for callers that build their own strings. `messageLogger(logger, identity: MessageIdentity)` returns `logger.child({ deviceId, sessionId, seq })` for validated messages; `rejectedMessageLogger(logger, identity: RawIdentity)` the same for a rejected frame with whatever fields it had. Nothing wraps `flush`: on the default destination (`minLength: 0`) `flush(cb)` calls back while the write is still in flight, and the exit hook pino registers writes the queue with `flushSync` when the process exits, so a shutdown handler may log its last line and exit (trade-off T17). The `Logger` type is re-exported so that no service imports pino directly.

Failure behaviour of the helpers:

| Input                                                       | Behaviour                                                                                                                                       |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Frame is not valid JSON                                     | `decodeTelemetryMessage` → `{ ok: false, reason: 'invalid_json', detail, identity: {} }`; caller logs and drops.                                |

| Line longer than `MAX_FRAME_BYTES`                          | `FrameDecoder.push` returns `ok: false` with the error and the frames decoded before it, buffer cleared; ingest logs and closes the connection. |
| Chunk boundary inside a multi-byte character                | Bytes are concatenated before decoding; the frame decodes correctly.                                                                            |
| Frame contains bytes that are not valid UTF-8               | `Buffer.toString('utf8')` substitutes U+FFFD, never throws; the frame is rejected as invalid JSON or as an invalid string value.                |
| Device sends pretty-printed (multi-line) JSON               | Each line is rejected as invalid JSON and logged; compact JSON is part of the wire contract (decision 1).                                       |
| Connection closes with an unfinished line                   | The tail is dropped; `pendingBytes` lets ingest log how many bytes were lost (trade-off T3, device-side fire-and-forget).                       |
| Environment variable unset or empty                         | Its default applies; a required variable without a default → `ConfigError` naming it; the service exits at startup.                             |
| Environment variable invalid (`abc`, `0` below the minimum) | `ConfigError` with `NAME: problem`; all problems are listed at once.                                                                            |

Delivery semantics are unchanged from the consistency spec (at-least-once between ingest and storage, fire-and-forget device to ingest, exactly-once effect at the storage boundary).

## Scaling

A library has no instances. Two costs it adds per message are named: one `safeParse` per message in ingest and again in processing (decision 2 trade-off; measured only if a bottleneck appears), and one linear scan per socket chunk in the decoder. Neither holds state across devices, so nothing here limits horizontal scaling.

## Alternatives Considered

### Length-prefixed binary framing

A 4-byte big-endian length before every JSON body. Handles arbitrary payload sizes without scanning for a delimiter and detects truncation exactly. Costs a custom encoder and decoder on both sides and makes the stream opaque to `nc` and packet captures. Rejected for this scope; documented as the upgrade path for larger payloads (T11).

### WebSocket or HTTP

Framing, ping/pong and a client library for free, at the price of an HTTP upgrade handshake, a dependency in ingest and the emulator, and a protocol that machine clients do not need. The assignment says "socket connections"; raw TCP with NDJSON is the smallest reading of it.

### ajv (JSON Schema) instead of zod

Faster validation and a language-neutral schema document. The TypeScript type would have to be written by hand or generated by a second library, which breaks the "types derived from the schema" rule. Named as the upgrade path if validation cost is measured as the bottleneck.

### Full per-app configuration schemas in shared

One place for every variable. Rejected because shared would then carry ingest, processing and emulator knobs, which are app decisions; the names are still fixed in one place (`.env.example`).

### dotenv

Redundant with Node's `--env-file` flags; Compose sets the environment in containers.

### `@types/amqplib` and rabbitmq-client

Not needed and rejected respectively — see decision 10.
