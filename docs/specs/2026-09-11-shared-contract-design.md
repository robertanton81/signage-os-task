This spec also records the AMQP client and the MongoDB driver so that every library choice the assignment leaves open is in `docs/specs/`; those two are installed by steps 4 and 5, not here. The consistency spec (`2026-09-11-telemetry-consistency-design.md`) binds everything below; nothing in it is changed.

## Problem

The consistency spec fixes what a message carries, how "newer" is decided and how state is stored. It leaves to step 2 the choices that turn that into code: the wire framing between device and ingest, the validation library that also produces the TypeScript types, the logger, how configuration is loaded and which variable names exist, and where the storage document types and the queue and collection names live. Every service imports the results, so they must be decided once, with versions pinned and documentation verified, before any service is written.

| 1   | Wire framing between device and ingest                | **Superseded on 2026-09-13** by the WebSocket transport spec (`docs/specs/2026-09-13-websocket-transport-design.md`), decision 1 and 2. The text that follows is the earlier decision, kept for the record. **Newline-delimited JSON (NDJSON) over the raw TCP socket.** One message is one JSON object encoded as UTF-8 and terminated by `\n`. A frame is complete only when its newline has arrived; whitespace-only lines are ignored; a line longer than `MAX_FRAME_BYTES` (65 536) is a protocol violation — the decoder returns `ok: false` with a `FrameTooLongError` (it never throws), resets, and ingest closes that connection; bytes left without a newline when a connection closes are dropped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Two facts make the newline an unambiguous terminator. Inside string values a compliant generator must escape every control character, so a raw U+000A can never come from a `message` or `code` field (RFC 8259 §7 and §10, Research). Outside strings the JSON grammar does allow line feeds as insignificant whitespace (§2), so the guarantee for the whole message comes from the encoder: `encodeFrame` is the only producer of frames in this system and calls `JSON.stringify(message)` without the `space` argument, which inserts no whitespace at all (MDN, Research). Compact JSON is therefore part of the wire contract: a foreign device that pretty-prints its JSON is rejected line by line as invalid JSON, and the emulator uses `encodeFrame`. A trailing `\r` is insignificant whitespace to `JSON.parse` (§2), so CRLF clients work unchanged. The stream is readable with `nc` and in packet captures, which helps the technical discussion and debugging. The size bound keeps a misbehaving client from growing memory without limit; a valid message is a few hundred bytes. | 14  | Argument style, and where runtime validation runs     | Function arguments are positional by default. A single named object (a parameter object) is used when a function takes three or more arguments, or two or more arguments of the same type — `createLogger({ service, level, destination })` is the existing example. Argument and return types are derived from the message schema (`z.infer`, `Pick<>`, `.extend()` on a payload schema), never redeclared; no second schema is written for a shape the message schema already describes. Runtime validation runs only where data enters a process from outside the type system: socket frames (`decodeTelemetryMessage`), environment variables (`loadConfig`), the emulator's command-line arguments (step 3), the AMQP body and the `x-received-at` header (consistency spec, decision 18), and a MongoDB read that a branch or a test assertion depends on. Inside a process no function re-validates a value the compiler already typed. The argument rule binds new code; `max-params: ['error', 2]` in `eslint.config.js` enforces the "three or more" half of it (task 10), and the three existing signatures that keep positional same-typed arguments are named opposite. | Two independent choices hide under the word "DTO", and only the first is a style question. A parameter object makes the call site self-documenting and two same-typed arguments unswappable; below three arguments it is noise, and `isNewer(candidate, stored)` stays positional on purpose — it is the comparator idiom, and the swap that would matter lives in the MongoDB pipeline mirroring it, where a parameter object cannot help. Two further signatures keep positional same-typed arguments, each for a reason: `envInt({ min, max, defaultValue })` (amended 2026-09-13: a named object with an optional `max`) is protected completely by its own import-time guard — the guard enforces `defaultValue >= min`, so any swap that changes behaviour makes the new default smaller than the new minimum and throws when the module is imported — and `FrameTooLongError(bytes, limit)` only formats an error message, where a swap costs a wrong number in one log line and no invariant, and positional arguments are the idiom for an Error constructor. ## Chosen Approach

`packages/shared` becomes the contract and nothing more: one zod schema is the source of the message type and of the storage document types; three pure helpers (`messageIdentity`, `orderKey`, `isNewer`), one frame codec and one decoder are the only logic; the broker and database names are constants; a pino factory and a zod-based environment loader are the cross-cutting helpers. The package performs no I/O and depends on no client library, so every service and every test imports it without a broker or a database.

**Why this over alternatives:** one library (zod) serves both the wire contract and the configuration; one logger; nothing in shared needs a mock. Each piece can be explained in one sentence in the technical discussion, and each has a unit test that names a concrete input and its outcome.

- [Zod — Defining schemas](https://zod.dev/api) (docs for 4.x, read 2026-09-11) — `z.strictObject` "throws an error when unknown keys are found"; `z.discriminatedUnion(key, options)` with `z.literal` discriminators; `z.literal`, `z.enum` on an `as const` array; `z.int()` "restricts to safe integer range"; `z.number()` "allows any finite number" and rejects `NaN` and `Infinity`; `z.string().min/max/regex`; `z.coerce.number()` = `Number(input)`; `.default()` "short-circuit[s] the parsing process … the default value must be assignable to the output type"; `.prefault()` as the parsed alternative; `z.ZodType` as the generic bound for schema parameters (section "Apply").
- [Zod — Basic usage](https://zod.dev/basics) — `.safeParse()` returns `{ success, data | error }`; `error.issues[]` carries `code`, `path`, `message`; `z.infer`, `z.input`, `z.output`.
- [Zod — Formatting errors](https://zod.dev/error-formatting) — an unknown key yields `code: 'unrecognized_keys'` with the path of the object; `z.prettifyError` exists (not used; the decoder formats issues itself so the log line stays one string).
- [Zod 4 migration guide — `z.number()`](https://zod.dev/v4/changelog#znumber) — "`POSITIVE_INFINITY` and `NEGATIVE_INFINITY` are no longer considered valid values"; `.int()` "no longer accepts unsafe integers".

### Message contract (`message.ts`)

The schema is the consistency spec's `TelemetryMessage` written in zod. Rules: all five envelope fields present with the given types and ranges; `v` is the literal `1`; `deviceId` matches `^[A-Za-z0-9_-]+$` and is 1–64 characters; `sessionId` is a safe integer between `SESSION_ID_MIN` (1 500 000 000 000) and `SESSION_ID_MAX` (4 100 000 000 000, consistency spec decision 28), `seq` a safe integer ≥ 1, `occurredAt` a safe integer ≥ 0; `type` is one of `status`, `metrics`, `counters`, `diagnostic`; the payload is a strict object for that type; numbers are finite; `cpuPercent` and `ramPercent` are between `PERCENT_MIN` (0) and `PERCENT_MAX` (100); `counters` values are integers ≥ 0; `code` is 1–64 and `message` up to 1 024 characters. Unknown keys anywhere are rejected. Exported: `telemetryMessageSchema`, the four payload schemas, `TELEMETRY_EVENT_TYPES`, the types `TelemetryMessage`, `TelemetryEventType`, `TelemetryMessageOf<T>`, `PayloadOf<T>`, `StatusPayload`, `MetricsPayload`, `CountersPayload`, `DiagnosticPayload`, and the bound constants. The exact code is in the plan (task 2).

### Identity and order (`identity.ts`)

`MessageIdentity = { deviceId, sessionId, seq }`, `OrderKey = { sessionId, seq }`. `messageIdentity(m)` returns `` `${deviceId}:${sessionId}:${seq}` `` (log field, AMQP `messageId`, `alerts._id`). `orderKey(m)` returns `[sessionId, seq]`. `isNewer(candidate, stored)` is the single definition of "newer": `candidate.sessionId > stored.sessionId || (candidate.sessionId === stored.sessionId && candidate.seq > stored.seq)`; equal keys are not newer. The processing pipeline builder (step 5) is derived from it and its test runs the same cases. `extractRawIdentity(value)` returns the subset of the three fields present on an unvalidated value with the right primitive type — `deviceId` cut to `DEVICE_ID_MAX_LENGTH`, the numbers only when they are safe integers — for log lines about rejected input, which a device must not be able to inflate.

### Framing (`framing.ts`)

Superseded on 2026-09-13 by the WebSocket transport spec (`docs/specs/2026-09-13-websocket-transport-design.md`, "Wire contract"): the module now exports `TELEMETRY_SOCKET_PATH`, `MAX_FRAME_BYTES` (the bound of one WebSocket message, the server's `maxPayload`), `encodeMessage` (compact JSON, one message per text WebSocket message) and `decodeUtf8Strict`; `FrameDecoder`, `encodeFrame` and `FrameTooLongError` are gone, because the protocol frames messages, reassembles fragments and validates UTF-8. The paragraph below describes the earlier line decoder.

`encodeFrame(message)` → `Buffer` of `JSON.stringify(message) + '\n'` in UTF-8; no `space` argument, so the JSON text is one line (MDN, Research) — compact JSON is part of the wire contract, and a pretty-printed message from a foreign client is rejected line by line as invalid JSON. `FrameDecoder` keeps the unfinished tail between `push(chunk)` calls and returns the complete lines (without their newline) in order; whitespace-only lines are skipped; a trailing `\r` is left in place because `JSON.parse` accepts it as whitespace (RFC 8259 §2). `push(chunk)` never throws: it returns `{ ok: true, frames }`, or `{ ok: false, frames, error: FrameTooLongError { bytes, limit } }` when a complete line, or the buffered tail, exceeds `maxFrameBytes` (constructor argument, default `MAX_FRAME_BYTES` = 65 536), with the buffer cleared and the rest of that chunk unread; `frames` is on both branches so the lines decoded before the oversized one cannot be dropped by accident. The tail is kept as the list of chunks it arrived in and each `push` scans only its own chunk, so the cost is one copy and one scan per byte however the bytes are split (a one-byte drip up to the limit costs ~13 ms, not the ~280 ms of re-copying the tail on every push). Ingest closes the connection on `ok: false` (decision 1). `pendingBytes` exposes the buffered tail length for the log line at connection close. Bytes that are not valid UTF-8 were repaired to U+FFFD replacement characters until 2026-09-13 (Node Buffer docs, Research); inside a string value the repaired frame passed validation, so since then the decoder rejects such a line as `invalid_utf8` and drops it, never repairs it and never throws (failure table below, T43).

### Decoding (`decode.ts`)

```ts
type DecodeResult =
  | { ok: true; message: TelemetryMessage }
  | { ok: false; reason: 'invalid_json' | 'invalid_schema'; detail: string; identity: RawIdentity };
```

`detail` is the `JSON.parse` error message, or every zod issue as `path: message` joined by `; ` (`(root)` for an empty path); each message is capped at 200 characters, so the path of every failing field survives however long one message is, and the parser message gets the same cap. `identity` is `extractRawIdentity` of the parsed value (empty for invalid JSON).

### Logging (`logger.ts`)

`LOG_LEVELS = ['trace', 'debug', 'info', 'warn', 'error', 'fatal', 'silent']`. `createLogger({ service, level, destination? })` returns a pino `Logger` with `base: { service, hostname }` and ISO time; `destination` is for tests. Three mechanisms strip `scheme://user:password@` from every line, because the path-based `redact` (`RABBITMQ_URL`, `MONGODB_URL`) cannot reach a URL inside a string: `serializers.err` runs the standard error serializer and then `redactUserinfo` over its `message`, `stack` and nested fields; `hooks.logMethod` strips every string argument and gives a bare error an explicit stripped message (pino would otherwise copy `err.message` into `msg` before any serializer runs); `formatters.log` walks the merging object (plain objects and arrays, four levels deep; an `Error` is left to the serializer; a value with its own `toJSON` is serialised through it and the result redacted when it is a string — a `URL` prints its whole `href`, userinfo included) for a connection string under any other key. `redactUserinfo(text)` is exported for callers that build their own strings. `messageLogger(logger, identity: MessageIdentity)` returns `logger.child({ deviceId, sessionId, seq })` for validated messages; `rejectedMessageLogger(logger, identity: RawIdentity)` the same for a rejected frame with whatever fields it had. Nothing wraps `flush`: on the default destination (`minLength: 0`) `flush(cb)` calls back while the write is still in flight, and the exit hook pino registers writes the queue with `flushSync` when the process exits, so a shutdown handler may log its last line and exit (trade-off T17). The `Logger` type is re-exported so that no service imports pino directly.

## Scaling

A library has no instances. Two costs it adds per message are named: one `safeParse` per message in ingest and again in processing (decision 2 trade-off; measured only if a bottleneck appears), and one linear scan per socket chunk in the decoder. Neither holds state across devices, so nothing here limits horizontal scaling.

## Alternatives Considered

### Length-prefixed binary framing

A 4-byte big-endian length before every JSON body. Handles arbitrary payload sizes without scanning for a delimiter and detects truncation exactly. Costs a custom encoder and decoder on both sides and makes the stream opaque to `nc` and packet captures. Rejected for this scope; documented as the upgrade path for larger payloads (T11).

### WebSocket or HTTP

WebSocket gives message framing, ping and pong, and TLS on port 443 through `wss`. Its main gain is reaching devices inside customer networks, where firewalls and HTTP proxies may allow only a few outbound ports. For the connection to its cloud, signageOS needs only ports 443 and 80, and uses port 80 as a fallback when TLS on 443 fails: a wrong device clock, an invalid root certificate on the device, or a proxy that blocks WebSocket over TLS (Research). The costs are an HTTP upgrade per connection and a server library in ingest, because Node 24 ships a WebSocket client but no server (local probe, Research). The same built-in client means the emulator would need no dependency. The reading rule would still work, because `ws` pauses the underlying socket (Research). In this development system the emulator and ingest share one Compose network with no firewall or proxy between them. The gain does not apply here, so raw TCP with NDJSON stays the smallest reading of the assignment's "socket connections"; the gap is trade-off T38. A plain HTTP API is the other member of this family: signageOS offers a REST API as an optional replacement for the device socket (Tizen app 2.2.0, Research). This system does not need one.

Corrected on 2026-09-13: this section used to say that machine clients do not need WebSocket. That is wrong for devices in customer networks, which gain passage through firewalls and proxies.

Chosen on 2026-09-13: the WebSocket transport spec (`docs/specs/2026-09-13-websocket-transport-design.md`) replaces decision 1 with WebSocket on both ends — the `ws` 8.21.3 server in ingest, the `ws` client in the emulator, one compact JSON message per text WebSocket message. TLS at the edge, authentication at the upgrade request and an L7 load balancer are recorded there (decision 14), not implemented.

### QUIC (HTTP/3, WebTransport)

QUIC runs over UDP and always uses TLS 1.3. Its main gain for a device fleet is connection migration: when the client's address changes, the client keeps the connection through its connection ID, so a Wi-Fi to LTE failover or a NAT rebinding does not force a reconnect (RFC 9308 §9). It also combines the transport and TLS handshakes (RFC 9000 §7), which saves one round trip per new connection compared with TCP plus TLS, unless the server's certificate chain is too large for the first packets the server may send (Node.js `quic` docs). The limits, all sourced in Research:

- 3–5% of networks block all UDP. There a QUIC application must accept failure or fall back to another transport, and the fallback must not weaken security (RFC 9308 §2). So QUIC can only be a second transport next to a TCP one.
- Clients initiate all migrations (RFC 9000 §9). When an ingest instance restarts, is redeployed or crashes, its devices reconnect anyway.
- Load balancers must keep sending a connection's packets to the same instance when the client's address changes, for example by reading routing data from the connection ID (RFC 9308 §11.1). Each migration also costs at least one round trip for path validation and resets congestion control (RFC 9308 §9).
- A NAT may drop an idle UDP binding after 30 seconds, while an established TCP binding must survive at least 2 hours 4 minutes (RFC 9308 §3.2, RFC 5382). A server that needs to reach an idle device then waits until the device sends again, or the device sends keep-alives that cost traffic and battery.
- QUIC cannot run without TLS, so a device whose wrong clock makes the server certificate look invalid cannot connect over QUIC either. signageOS's port 80 fallback exists for this case.
- A device that runs a web engine can use QUIC for a long-lived two-way connection only through WebTransport, which Chrome supports from version 97. Tizen 7.0, the newest Samsung generation on signageOS's supported-device list, runs Chromium M94, and Samsung's engine specification does not mention HTTP/3, QUIC or WebTransport.
- Node 24 has no `node:quic` module; its experimental flag arrived in Node 25 (Node.js docs and local probe).

Rejected for this scope. QUIC is the upgrade path for fleets on mobile networks (T39), as a second transport next to TCP. The reconnect handling above the transport stays either way — the device outbox, the `(sessionId, seq)` order key, deduplication and jittered backoff — because a server restart still forces a reconnect.

### MQTT 5

MQTT 5 is an OASIS standard for lightweight publish/subscribe messaging aimed at constrained devices, and RabbitMQ 4.3 supports it natively through a plugin (Research). It has a per-message acknowledgement (PUBACK for QoS 1), a limit on unacknowledged messages announced by the receiver ("Receive Maximum", the same idea as `INGEST_MAX_UNCONFIRMED`), a Keep Alive, and a Will message that the server publishes when a connection ends without a normal disconnect. Rejected for this scope:

- Its resend guarantee lives in a session on the server. A device that reconnects to another ingest instance finds no session there, receives Session Present 0, and must discard its session state, including its unacknowledged QoS 1 messages (MQTT 5.0 §3.2.2.1.1). Keeping the guarantee would need sessions shared by all ingest instances, which breaks invariant 6: ingest holds no per-device state.
- Without shared sessions, the device must resend from its own outbox. That is the acknowledgement protocol already named as the upgrade path of T3, and it works over TCP too. MQTT 5 would be a standard wire format for that protocol, not a way around building it.
- Connecting devices straight to RabbitMQ's MQTT plugin would remove ingest, which the assignment requires to validate messages before they reach RabbitMQ.
- Ingest would need an MQTT server library, still to be vetted, and a much larger protocol: connection and acknowledgement packets, packet identifiers, topics and sessions. QoS 2 would not remove deduplication either: it is an exchange of four packets between the sender and the receiver of one message (MQTT 5.0 §4.3.3, Research), so it covers the hop from device to ingest, not the path from device to storage.

### ajv (JSON Schema) instead of zod

Faster validation and a language-neutral schema document. The TypeScript type would have to be written by hand or generated by a second library, which breaks the "types derived from the schema" rule. Named as the upgrade path if validation cost is measured as the bottleneck.

### Full per-app configuration schemas in shared

One place for every variable. Rejected because shared would then carry ingest, processing and emulator knobs, which are app decisions; the names are still fixed in one place (`.env.example`).

### dotenv

Redundant with Node's `--env-file` flags; Compose sets the environment in containers.

### `@types/amqplib` and rabbitmq-client

Not needed and rejected respectively — see decision 10.
