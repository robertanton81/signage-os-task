## Problem

Ingest publishes every valid device message unchanged to the quorum queue `telemetry.events`, at least once, with `messageId` and the `x-received-at` header (ingest spec). Nothing consumes the queue yet. Processing must: consume it from any number of instances at once, store every unique event, keep one `device_state` document per device that reflects the logical order of the device's events, create one alert per error diagnostic, and acknowledge a delivery only after MongoDB has journaled the writes — while a duplicate or redelivered message never causes a second business effect, an older message never overwrites newer known state, and neither a MongoDB outage nor a broker restart nor a poison message loses a good message or stalls the pipeline.

The consistency spec already decided the mechanism: three idempotent single-document writes in a fixed order, a freshness guard evaluated by the server inside one conditional pipeline update, the unique index on `events` as the dedup gate, at-least-once delivery with manual acknowledgement, three error classes, an in-place retry that turns into a paused consumer during an outage, and the broker's consumer-cancel behaviour of RabbitMQ 4.3. What this spec decides is the **service** around that mechanism: the module layout and its pure core, the MongoDB store and its startup, the consumer state machine and the pause/resume and shutdown sequences, readiness, log levels, the configuration, the tests, and the scripted run that proves the impure shell against real containers before step 7 automates it.

| 6   | What counts as a broker failure          | **One recycle rule**, as in ingest: connection `close`, channel `close`, or a failed step of the connect attempt → `link_closed` / `link_failed` → `backoff`, generation + 1, full-jitter delay `random(0, min(10 000, 500 × 2^attempt))` from the shared `backoffDelay`, attempt reset after `LINK_RESET_AFTER_MS` (10 000, the value of the ingest publisher's `BACKOFF_RESET_AFTER_MS`, duplicated because apps do not import each other) of an open link. `error` events are logged and are not triggers (amqplib emits `close` right after them — ingest spec, decision 12). | 20  | Graceful shutdown order                  | On the first SIGTERM or SIGINT: (1) enter shutting down, `/readyz` answers 503; (2) the `stop` event moves the machine to `draining`, whose effect cancels the consumer, so no new delivery arrives while in-flight handlers continue and still acknowledge; (3) the shell waits up to `SHUTDOWN_TIMEOUT_MS` (default 10 000) for every dispatched handler to settle, through `settleWithin` (decision 29), and then emits `drained`; (4) the `drained` transition aborts the generation signal, so retry sleeps end and any handler still running abandons, and (5) closes the channel and the connection, bounded by `AMQP_CLOSE_TIMEOUT_MS` (2 000, the ingest constant) — the broker requeues what is still unacknowledged; (6) `client.close()`, which rejects any MongoDB call still in flight; a handler catches that as `closed` and abandons with a `warn` line; (7) close the health server. ## Chosen Approach

**Competing consumers with a pure core, and the store as the only judge.** Any number of processing instances open one channel each on `telemetry.events` with a prefetch window and manual acknowledgements. Every delivery is dispatched to its own handler, which runs the consistency spec's three idempotent single-document writes in order through a small store port — insert the event (the unique index rejects a duplicate), apply the section with the server-evaluated freshness guard and read the outcome from the returned pre-update document, insert the alert keyed by the identity — and acknowledges afterwards. Transient MongoDB failures are retried in place with an abortable backoff; after a bounded number of consecutive failures the instance pauses itself: it cancels its consumer, returns what it still holds with `basic.nack(requeue=true)`, reports not ready and re-registers when a ping succeeds. Deterministic and permanent failures are dead-lettered. A broker outage recycles the link with backoff; a broker-initiated consumer cancel re-registers on the same channel. Shutdown cancels first, drains second, closes last. The consumer's lifecycle is a pure state machine with a table test, the handler is tested against an in-memory store, and the two impure shells are proven by a scripted run against real containers.

**Why this over alternatives:** the consistency spec has already made processing order irrelevant to the result, so the service needs no coordination, no routing and no reordering — only a bounded window of concurrent, individually acknowledged handlers and the two recovery paths (broker, database) done carefully. Everything else in this spec is about keeping those paths small and testable: the state machine and the port move every decision into pure code, and the scripted run covers the seams that unit tests cannot.

### One delivery, from queue to acknowledgement

`delivery.ts` turns an amqplib message into what the handler needs, without touching the broker:

```ts
export type DecodedDelivery = {
  message: TelemetryMessage;
  receivedAt: number; // header, or the clock with `receivedAtSource: 'clock'`
  receivedAtSource: 'header' | 'clock';
  redelivered: boolean;
};
export type DeliveryRejection = {
  reason: 'body_too_large' | 'invalid_utf8' | 'invalid_json' | 'invalid_schema';
  detail: string;
  identity: RawIdentity;
  bytes: number;
};
export function decodeDelivery({
  content,
  headers,
  redelivered,
  now,
}): { ok: true; delivery: DecodedDelivery } | { ok: false; rejection: DeliveryRejection };
```

Rules: `content.length > MAX_FRAME_BYTES` → `body_too_large` before any parsing; otherwise `decodeUtf8Strict(content)` from shared (a body that is not valid UTF-8 → `invalid_utf8`, never repaired to U+FFFD, the frame decoder's rule) and then `decodeTelemetryMessage(text)`; the header `x-received-at` is taken when `typeof value === 'number' && Number.isSafeInteger(value) && value >= 0`, else `now()` with `receivedAtSource: 'clock'` (the handler logs the fallback at `warn` with the identity).

`handler.ts` runs the consistency spec's sequence for one decoded delivery:

```ts
export type HandlerResult =
  | {
      verdict: 'ack';
      outcome: 'created' | 'applied' | 'stale';
      duplicate: boolean;
      alert: 'created' | 'exists' | 'none';
      attempts: number;
    }
  | {
      verdict: 'reject';
      reason: 'body_too_large' | 'invalid_utf8' | 'invalid_json' | 'invalid_schema' | 'permanent';
      attempts: number;
    }
  | { verdict: 'abandon'; cause: 'aborted' | 'closed' | 'store_unavailable'; attempts: number };

export function processDelivery(input: {
  content: Buffer;
  headers: Record<string, unknown>;
  redelivered: boolean;
  store: StorePort;
  clock: () => number;
  sleep: (ms: number, signal: AbortSignal) => Promise<void>;
  random: () => number;
  signal: AbortSignal;
  transientAttempts: number;
  logger: Logger;
}): Promise<HandlerResult>;
```

1. `decodeDelivery`; a rejection → log at `warn` (`message rejected`, `reason`, `detail`, `bytes`, raw identity fields) → `{ verdict: 'reject' }`.
2. If `signal.aborted` → abandon `aborted`. `store.insertEvent({ deviceId, sessionId, seq, type, occurredAt, receivedAt, processedAt: clock(), payload })`; `'duplicate'` → `duplicate = true`, log at `debug`.
3. If aborted → abandon. `store.applyState(deviceId, buildStateUpdate(message, receivedAt))` → `before`; `'duplicate'` (the racing first insert) → check the signal and run it once more within the same attempt; a second `'duplicate'` → treated as a transient failure. `outcome = classifyOutcome(before, message)`; `detectGap(before, message)` → `sequence gap` at `info`.
4. If aborted → abandon. For `type === 'diagnostic' && payload.severity === 'error'`: `store.insertAlert({ _id: messageIdentity(message), deviceId, sessionId, seq, code, message, occurredAt, createdAt: clock() })` → `created`, or `'duplicate'` → `exists`.
5. If aborted → abandon. Log the outcome (decision 22) → `{ verdict: 'ack', ... }`.

Failure handling around steps 2–4: a rejected port call carries a `StoreFailure`; `classifyFailure` decides. `permanent` → log at `error` with the identity → `reject('permanent')`. `closed` → log at `warn` → abandon `closed`. `transient` → log at `warn` (`attempt`, the failure), and if `attempt < transientAttempts`: `await sleep(backoffDelay({ attempt, baseMs: 200, maxMs: 5_000, random }), signal)` and restart from step 2 (an `AbortError` from the sleep → abandon `aborted`); if the cap is reached → abandon `store_unavailable`. `attempts` in the result is the number of full attempts made. Nothing in `processDelivery` can throw: the body is one `try` around the steps, and a throw that is not a `StoreFailure` is a programmer error, logged at `error` and reported as `reject('permanent')` so the delivery does not stay in limbo.

### The store port and the MongoDB store (`store.ts`)

```ts
export type StoreFailure =
  | {
      kind: 'server';
      code: number | undefined;
      codeName: string | undefined;
      labels: readonly string[];
      message: string;
    }
  | { kind: 'network'; message: string }
  | { kind: 'server_selection'; message: string }
  | { kind: 'closed'; message: string }
  | { kind: 'other'; name: string; message: string };

export type StorePort = {
  insertEvent(doc: EventDocument): Promise<'inserted' | 'duplicate'>;
  applyState(
    deviceId: string,
    update: StateUpdate,
  ): Promise<{ result: 'updated'; before: DeviceStateDocument | null } | { result: 'duplicate' }>;
  insertAlert(doc: AlertDocument): Promise<'inserted' | 'duplicate'>;
};
```

Every port method rejects with a `StoreFailure` (never a driver error): the shell catches the driver error, and `describeMongoError` maps it — `MongoServerError` → `server` (with `code`, `codeName`, `errorLabels`), `MongoNetworkError` → `network`, `MongoServerSelectionError` → `server_selection`, `MongoClientClosedError | MongoNotConnectedError | MongoTopologyClosedError` → `closed`, anything else → `other`. A `server` failure with code 11000 is turned into the `'duplicate'` result before it reaches the handler (`DUPLICATE_KEY_ERROR_CODE` from shared). `classifyFailure` in `failure.ts`:

| View                                                                                                  | Class       |
| ----------------------------------------------------------------------------------------------------- | ----------- |
| `network`, `server_selection`                                                                         | `transient` |
| `server` with label `RetryableWriteError`, or `code` ∈ {24, 50, 64, 91, 262, 10107, 11600}            | `transient` |
| `closed`                                                                                              | `closed`    |
| every other `server` (a schema-validation refusal, an unknown command, a document too large), `other` | `permanent` |

`MongoStore` (the shell):

- `constructor({ url, dbName, writeW, timeoutMs, logger })` builds the client of decision 11 and the three typed collections (`Collection<EventDocument>`, `Collection<DeviceStateDocument>`, `Collection<AlertDocument>`). No I/O in the constructor.
- `start(signal)`: loop `connect()` then `createIndex(EVENTS_IDENTITY_INDEX_SPEC.key, { name: EVENTS_IDENTITY_INDEX_NAME, unique: true, maxTimeMS })`; a `server` failure with code 85 or 86 → log at `fatal` (`index conflict`) and reject with it, which the entry point turns into exit 1; any other failure → `warn` (`store not ready`, `attempt`) and `backoffDelay` (500 ms → 10 s) with the signal; on success `ready = true`, emit `store_ready`, log at `info` (`store ready`).
- `watch(signal)`: called by the consumer's `watch_store` effect after a pause; loops `db.command({ ping: 1 }, { maxTimeMS })` with the same backoff until it resolves, logging `store not ready` at `warn` per attempt and `store ready` at `info` once.
- `insertEvent`, `applyState`, `insertAlert`: one driver call each with `maxTimeMS`; `applyState` is `findOneAndUpdate(filter, pipeline, { upsert: true, returnDocument: 'before', maxTimeMS })`, whose result is the pre-update document or `null`.
- `close()`: `client.close()`; bounded by `MONGODB_TIMEOUT_MS` through `settleWithin` (the ingest helper pattern); a rejection is logged at `warn`.

The documents are written as typed values, so a payload key that collided with `SectionMeta` would be a compile error (shared `contract.test-d.ts`).

### The state update (`state-update.ts`)

`buildStateUpdate(message, receivedAt): StateUpdate = { filter: { _id }, pipeline: Document[] }` — the consistency spec's pipeline, one `$set` stage with the section and `lastEvent`, both guarded by `newerThanStoredExpr(path, { sessionId, seq })`:

```ts
{
  $or: [
    { $eq: [{ $type: `$${path}` }, 'missing'] },
    { $lt: [`$${path}.sessionId`, sessionId] },
    { $and: [{ $eq: [`$${path}.sessionId`, sessionId] }, { $lt: [`$${path}.seq`, seq] }] },
  ];
}
```

`then` values are wrapped in `$literal` (`next = { sessionId, seq, occurredAt, receivedAt, ...payload }` and `{ sessionId, seq, type, receivedAt }`), `else` keeps `$${path}`. `classifyOutcome(before, message)` and `detectGap(before, message)` are decisions 16 and 17. The unit test evaluates `newerThanStoredExpr` with a tiny evaluator over the five documents of the consistency spec (absent section; older session; same session, older `seq`; same key; newer session with a lower `seq`) and asserts each answer equals `isNewer(message, stored)`; a second test asserts that a diagnostic `message` starting with `$` sits inside `$literal` in the built pipeline. The server-side proof of the same expression is step 7's integration test.

```ts
  | { type: 'link_failed'; generation; reason: string }
  | { type: 'link_closed'; generation; reason: string }
  | { type: 'consumer_registered'; generation }
  | { type: 'broker_cancelled'; generation }
  | { type: 'drained'; generation }
  | { type: 'store_ready' }
  | { type: 'store_unavailable' }
  | { type: 'stop' };
export type Effect =
  | { kind: 'open_link' }
  | { kind: 'schedule_backoff'; attempt: number }
  | { kind: 'consume' }
  | { kind: 'cancel_consumer' }
  | { kind: 'abort_handlers' }
  | { kind: 'return_held' }
  | { kind: 'watch_store' }
  | { kind: 'close_link' };
export function transition(
  state,
  event,
  { now, resetAfterMs },
): { state: ConsumerState; effects: readonly Effect[] };
export function isConsuming(state): boolean; // open && active && storeReady
```

`consume`, `cancel_consumer`, `return_held` and `close_link` are asynchronous in the shell; the shell runs the effects of one transition in order and feeds the completion back as the next event (`consumer_registered` after `consume` resolves; a failed `consume` or `cancel` is a `link_closed` in disguise, because amqplib rejects an RPC only when the channel is broken).

**Shell** (`AmqpConsumer`):

- `constructor({ url, heartbeatSeconds, prefetch, transientAttempts, shutdownTimeoutMs, store, logger })` with `store: StorePort & { watch(signal: AbortSignal): Promise<void> }`; no I/O in the constructor. `storeReady()` feeds `store_ready` into the machine — the entry point calls it once `store.start()` has resolved (Startup).
- `start()`: emits `backoff_elapsed` on the start state; `open_link` runs one attempt promise — `connect(url, { timeout: AMQP_CONNECT_TIMEOUT_MS })` with the heartbeat in the URL, `createChannel()`, the topology asserts in the ingest order, `prefetch(prefetch)`, the whole bounded by `AMQP_SETUP_TIMEOUT_MS` through `settleWithin`. The `close` listeners are attached to the connection and to the channel as soon as each exists; while the attempt is in flight a `close` only marks it failed (the pending RPC rejects, so the promise settles) and the shell reports exactly one event per attempt, `link_failed` or `link_opened`; after `link_opened` a `close` is `link_closed`. `error` events on both are logged only; `blocked`/`unblocked` are logged at `warn`/`info` only (a consumer is not blocked by a resource alarm, publishers are).
- `consume`: creates the generation's `AbortController` and empty held map, then `channel.consume(TELEMETRY_QUEUE, onMessage, { noAck: false })`; on resolve → `consumer_registered`. `onMessage(null)` → `broker_cancelled`. `onMessage(msg)`: put the delivery in the held map, `received++`, `inFlight++`, and dispatch `void run(msg)`.
- `run(msg)`: `processDelivery(...)` with the generation signal; on `ack` → `channel.ack(msg)`; on `reject` → `channel.reject(msg, false)`; both remove the delivery from the map **only if the map is still this generation's** (a stale generation means the tag is void and the call would break the channel — the map identity is the guard). On `abandon('store_unavailable')` → emit `store_unavailable` (idempotent). On `abandon('aborted' | 'closed')` → nothing. Finally `inFlight--`, counters.
- `cancel_consumer`: `channel.cancel(consumerTag)`; `abort_handlers`: `controller.abort()`; `return_held`: `await Promise.allSettled(dispatched)` then `channel.nack(delivery, false, true)` for every entry left in the map, `returned += n`, map cleared; `watch_store`: `store.watch(signal).then(() => dispatch({ type: 'store_ready' }))`, at most one watch at a time. `close_link`: close channel then connection, each bounded by `AMQP_CLOSE_TIMEOUT_MS` through `settleWithin`; `link_closed` events of the closing generation are ignored by the generation check.
- `stop()`: emits `stop`; if the machine is now `draining`, waits `settleWithin(Promise.allSettled(dispatched), shutdownTimeoutMs)` and then emits `drained`, whose effects abort the handlers and close the link; resolves once `close_link` has finished, within `SHUTDOWN_TIMEOUT_MS + AMQP_CLOSE_TIMEOUT_MS`. The wait is the tested shared helper (decision 29) and the sequence is the tested table, so the shell adds no untested timing logic.
- `state` (read-only, for readiness), `stats()` (decision 23).

## Consistency & Failure Modes

The message metadata, the freshness rule, the dedup key, the atomic operation and the delivery semantics are the consistency spec's (decisions 1–12, 20, 27–29) and are not restated. Processing's own part:

**Where processing enforces each rule:** the unique index exists before the first insert (decision 10); the state write is the one pipeline update with the server-evaluated guard and its outcome is read from the pre-update document (decisions 16, 18); the alert is keyed by the identity (decision 15); the acknowledgement comes after the journaled writes (decisions 7, 11, 15); nothing is acknowledged, nacked or rejected twice, and never with a tag of a dead generation (decision 7).

| Failure                                                                                 | What happens                                                                                                                                                                                                                               | Why the invariants hold                                                                                                                                                                          |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Handler crashes between writes; instance crashes; redelivery                            | The consistency spec's redelivery rows: every step is a no-op for an applied key.                                                                                                                                                          | Invariant 2 at the storage boundary.                                                                                                                                                             |
| Broker cancels the consumer (consumer timeout) while handlers run                       | `broker_cancelled`: the generation signal aborts; a handler finishes its current write and stops at the next check without acknowledging; the held map is dropped; the consumer registers again; the deliveries are redelivered elsewhere. | The write it finished is idempotent; the tag it never used was void anyway; no ack of an unknown tag, so no channel error and no incremented delivery counts for the other in-flight deliveries. |
| Link closes while handlers run                                                          | `link_closed`: same abort; the broker requeues everything unacknowledged; the new link starts a new generation with a new map.                                                                                                             | At-least-once; every write idempotent.                                                                                                                                                           |
| MongoDB unreachable                                                                     | Transient failures, retries in place, then the pause: cancel, abort, settle, `nack(requeue=true)` of the held deliveries, 503 `mongodb`, ping loop, resume with a new generation.                                                          | No good message is dead-lettered (a nack does not count in 4.3); nothing is acknowledged before it is journaled.                                                                                 |
| MongoDB frozen (no answer, socket open)                                                 | `socketTimeoutMS` and `maxTimeMS` bound every call; the timeouts are transient; the pause follows.                                                                                                                                         | Same as above; the bound is what keeps a handler from holding a prefetch slot forever.                                                                                                           |
| A handler's write is in flight when the pause aborts it                                 | The call completes (or times out); the result is discarded; the delivery is returned by the pause and redelivered.                                                                                                                         | Idempotent write, at-least-once delivery.                                                                                                                                                        |
| Two instances hold the same delivery (consumer timeout on one, redelivery to the other) | The consistency spec's overlap row: the first never acknowledges; both apply idempotent writes; the second acknowledges.                                                                                                                   | Every write keyed or conditional.                                                                                                                                                                |
| Poison body, oversized body, malformed header with a valid body                         | Dead-lettered without requeue (body); a malformed header alone is repaired with the clock and logged.                                                                                                                                      | The queue never blocks on one message; the identity in the log names it.                                                                                                                         |
| Permanent server refusal (schema validation on the collection, an unknown operator)     | Dead-lettered with the error and the identity at `error`.                                                                                                                                                                                  | Bounded: one round trip, no retry loop holding a slot.                                                                                                                                           |
| Racing first insert of a new device answers 11000 on the state write                    | One immediate retry; a second 11000 takes the transient path (the restarted handler's insert is a duplicate no-op).                                                                                                                        | Never dead-letters a good message over a server race.                                                                                                                                            |
| Stop while handlers run                                                                 | Cancel, drain up to the budget, abort, close the link (broker requeues the rest), close the client (in-flight calls reject as `closed`, abandoned with a `warn`).                                                                          | Nothing acknowledged that was not journaled; nothing lost.                                                                                                                                       |
| Index conflict at startup                                                               | Fatal, exit 1, the conflict named.                                                                                                                                                                                                         | Invariant 2 cannot be promised without the unique index; a silent start would be worse.                                                                                                          |
| Wrong database credentials, database still booting                                      | Retried forever with `warn` and 503; the queue accumulates on disk.                                                                                                                                                                        | A crash loop hides the reason; readiness shows it.                                                                                                                                               |

## Scaling

- M instances compete on one queue; RabbitMQ dispatches round-robin among consumers with free prefetch slots. Throughput per instance ≈ `PROCESSING_PREFETCH` handlers × (1 / MongoDB round-trip latency × 2 or 3 round trips); adding instances adds throughput until MongoDB's write capacity is the limit (consistency spec, Scaling).
- Per message: one indexed insert, one conditional update returning a document of about 1 KiB, one keyed insert for the rare alert; one ack frame. No batching (T46), no coordination.
- A hot device costs concurrent conditional updates on one document; losers cost one unmodified update each. No instance is pinned to it.
- Memory per instance: the held map (≤ prefetch entries with their bodies ≤ 64 KiB each, so ≤ 3.2 MiB at the default) plus the driver's pool.
- A `PROCESSING_PREFETCH` above `maxPoolSize` (100) queues handlers on the pool (T47); above 2 000 the broker caps it.

## Alternatives Considered

### `rabbitmq-client` or amqplib's opt-in recovery instead of the state machine

Automatic reconnect and re-subscribe would remove `consumer-state.ts` and the link half of `consumer.ts`. Rejected for the reasons of ingest spec decision 9 (the recovery behaviour is opaque where this design must be exact: what happens to held deliveries, when the consumer re-registers, how the store flag gates it) and to keep one client library across the two services.

### A channel per handler, or a channel per device

Would isolate a broken channel from the others. Costs a recovery loop per channel and a prefetch per channel that no longer bounds the instance. One channel with one map is enough: the failures that close a channel (a topology mismatch, an ack of a void tag) are programmer errors the design prevents.

### Batching writes with `bulkWrite`

Fewer round trips per message; per-message outcomes and acknowledgements would have to be reconstructed from the bulk result, and a partial failure would make the retry path batch-aware. Named as T46's upgrade path; not needed at the assignment's scale.

### `nack(requeue=true)` per transient failure instead of the in-place retry

The retry loop would move into the broker. Rejected by the consistency spec (decision 13): a requeued message goes to the back of the queue and to any instance, so a database outage would cycle every message through every instance, and before 4.3 it counted toward the delivery limit.

### Readiness from the driver's topology events instead of a ping loop

`serverHeartbeatFailed` and `topologyDescriptionChanged` would report the database state without a ping. They report the monitor's view, not whether a write succeeds, and their timing is the driver's `heartbeatFrequencyMS`; the ping is one round trip on the same timeout budget and answers the question the consumer actually has.

### Reading the identity from the AMQP `messageId` property

Cheaper than validating the body for a duplicate check before the insert. Rejected: the body is validated anyway (decision 18 of the consistency spec), a header can disagree with the body, and the unique index is the dedup gate, not a pre-check.

### Integration tests in step 5

Would prove the shells earlier. Rejected for the same reason as ingest spec decision 25: it would decide how the integration project starts Docker and isolates itself from the development Compose, which are step 6 and 7 questions.

### Consuming with `noAck: true` and a dedup pre-check

At-most-once delivery: a crash after the dequeue loses the message. Rejected by the consistency spec (decision 12).
