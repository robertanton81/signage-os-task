**Scope:** `apps/emulator` only. The message contract, the order key, the dedup rule and the storage guards are already decided in `docs/specs/2026-09-11-telemetry-consistency-design.md` (the consistency spec) and `docs/specs/2026-09-11-shared-contract-design.md` (the shared-contract spec); this spec does not revisit them. The socket server that receives these connections is step 4 and is out of scope, as are the Compose service definition (step 6) and the integration tests (step 7).

## Problem

The system needs a traffic source before it has anything to receive traffic. The emulator is that source: it must open a long-lived TCP connection per emulated device, produce all four event types at a believable rhythm, and — this is the part that matters for the assignment — produce the exact hazards the pipeline claims to survive: duplicates, out-of-order pairs, connection loss and device restarts.

The consistency spec already fixes what the emulator puts on the wire: device ids, `sessionId = max(Date.now(), previousSessionId + 1)`, `seq` starting at 1 and incrementing per message, the four event types and their cadence, the heartbeat, the DNS-based connection spread, the bounded outbox with its drop policy, and the four chaos-mode names. The shared-contract spec fixes the environment variable names and their defaults.

What is not decided anywhere, and what this spec decides: how one process drives N devices, how the event generator is made deterministic and unit-testable without a socket or a fake clock, what each chaos mode does exactly (the subtle part — three of the four can be written in a way that silently breaks the "a device never reuses `(sessionId, seq)`" invariant the whole design rests on), the connection state machine, and what happens on SIGTERM.

## Chosen Approach

One Node process holds a `Fleet` of `EMULATOR_DEVICE_COUNT` `DeviceClient` objects. Each client owns one TCP socket, one seeded PRNG, one `DeviceSession` (the pure generator) and one bounded outbox, and drives itself with a chained `setTimeout` whose phase is randomised.

The design's spine is the split between a **pure core** and an **impure shell**:

- The pure core (`random.ts`, `generator.ts`, `session.ts`, `outbox.ts`, `chaos.ts`) is functions and small classes with no I/O, no globals and no ambient clock. It produces `TelemetryMessage` values and decides what happens to them. It is unit-tested directly, with no timers and no sockets.
- The impure shell (`connection.ts`, `device.ts`, `fleet.ts`, `main.ts`) owns sockets, timers and signals. It is tested against a real `net.createServer` sink on an ephemeral port — a real socket, never a mock of one.

Chaos lives at the seam between the two, as a policy applied to a message on its way from the generator into the outbox. That placement is what keeps the contract invariant intact: the generator's `(sessionId, seq)` is always strictly increasing and never reused, no matter which chaos modes are on.

**Why this over alternatives:** the alternative shapes either make the generator untestable without fake timers and a server (generation inside socket callbacks), or let chaos corrupt the order key itself (chaos inside the generator), which would turn the emulator into a source of the very corruption the pipeline is supposed to be proven against — a test that passes then proves nothing.

## Research (source links)

Node.js 24.21.0 (the toolchain's pinned runtime; `package.json` requires `>=24.10 <25`):

- [`dnsPromises.lookup(hostname[, options])`](https://github.com/nodejs/node/blob/main/doc/api/dns.md?plain=1#L1081#dnspromises-lookup-hostname-options) — with `all: true` "the `Promise` is resolved with `addresses` being an array of objects with the properties `address` and `family`"; `order` defaults to `verbatim` ("addresses are not reordered"). On the treatment of failures, the same page, verbatim: "Keep in mind that `err.code` will be set to `'ENOTFOUND'` not only when the host name does not exist but also when the lookup fails in other ways such as no available file descriptors." That is the documented basis for decision 21 — the error code cannot distinguish a typo in `INGEST_HOSTS` from a transient resource shortage, so treating it as fatal would let a temporary condition kill the process, and a lookup failure is retried instead.
- [`socket.write(data[, encoding][, callback])`](https://nodejs.org/api/net.html#socketwritedata-encoding-callback) — "Returns `true` if the entire data was flushed successfully to the kernel buffer. Returns `false` if all or part of the data was queued in user memory. `'drain'` will be emitted when the buffer is again free." This is the whole basis of decision 16.
- [`net.Socket` event `'drain'`](https://github.com/nodejs/node/blob/main/doc/api/net.md?plain=1#L1137#event-drain) — "Emitted when the write buffer becomes empty. Can be used to throttle uploads."

These three links point at `doc/api/` on the `main` branch, which is where the passages were read. The drift risk is nil for this design: the `added:` metadata visible in the same source blocks dates `socket.write` and `'drain'` to v0.1.90 and `dnsPromises.lookup` to v10.6.0, the only recorded change to the latter being the v20.13/v22.1 deprecation of `verbatim` in favour of `order` — which is the behaviour quoted above and which v24.21.0 therefore has.

Retry strategy:

- [AWS IoT Device SDK for Embedded C — `backoffAlgorithm`](https://github.com/aws/aws-iot-device-sdk-embedded-c/blob/main/README.md?plain=1#L156#backoffalgorithm) — "This library uses the 'Full Jitter' strategy for the exponential backoff with jitter algorithm", for "retrying network operations (like failed network connection with server)", and it "helps to mitigate the failed network operations with servers, that are caused due to network congestion or high load on the server, by spreading out retry requests across multiple devices attempting network operations". Links to the [Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) architecture blog post. This is the reference implementation for the exact case here — many devices reconnecting to one server — and it is why decision 17 takes Full Jitter over Equal Jitter.

Test tooling (vitest 4.1.11, already pinned in the catalog):

- [`vi.useFakeTimers` / `vi.advanceTimersByTimeAsync`](https://vitest.dev/api/vi.md#fake-timers) — read and then deliberately **not used** (decision 5). `useFakeTimers` "will wrap all further calls to timers (such as `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `setImmediate`, `clearImmediate`, and `Date`)" and is "based internally on `@sinonjs/fake-timers`"; the documented caveats show how partial the replacement is — `process.nextTick` and `queueMicrotask` are not faked unless listed in `toFake`, and faking `nextTick` hangs under `--pool=forks`. Since every interval in this design is already configurable, real timers at 20 ms are both simpler and closer to what runs in production.

## Design

### Module layout (`apps/emulator/src/`)

| File            | Kind   | Responsibility                                                                                                   |
| --------------- | ------ | ---------------------------------------------------------------------------------------------------------------- |
| `random.ts`     | pure   | `createRandom(seed)` → mulberry32 PRNG with `float()`, `int(min, max)`, `bool(probability)`, `pick(array)`       |
| `backoff.ts`    | pure   | `backoffDelay(attempt, random)` — Full Jitter, so the delay schedule is unit-tested without waiting for it       |
| `generator.ts`  | pure   | Per-device baselines and the bounded random walk; builds each payload from the walk state                        |
| `session.ts`    | pure   | `DeviceSession`: identity, `sessionId` minting, `seq`, tick counter, `tick()` → `TelemetryMessage[]`             |
| `outbox.ts`     | pure   | Bounded FIFO with the diagnostic-sparing drop policy; reports what it dropped                                    |
| `chaos.ts`      | pure   | Mode parsing; `ChaosPolicy` for the per-message modes; `nextConnectionChaos()` for the connection-level schedule |
| `config.ts`     | pure   | The emulator's zod schema, `INGEST_HOSTS` and `EMULATOR_CHAOS` parsing, the device-id cross-check                |
| `connection.ts` | impure | `DeviceConnection`: DNS resolution, socket lifecycle, backoff, the write pump                                    |
| `device.ts`     | impure | `DeviceClient`: wires session + chaos + outbox + connection, owns the tick and heartbeat timers                  |
| `fleet.ts`      | impure | `Fleet`: N clients, staggered start, the summary line, the shutdown drain                                        |
| `main.ts`       | impure | Entrypoint: `loadConfig`, `createLogger`, build the fleet, install signal handlers                               |

`apps/*` depend on `packages/*` and never the reverse (`CLAUDE.md`): the emulator imports `TelemetryMessage`, `encodeFrame`, `messageIdentity`, `createLogger`, `messageLogger`, `loadConfig`, `envInt`, `logLevelEnv` and `shutdownEnv` from `@telemetry/shared`, and adds nothing to it.

### The pure core

**`createRandom(seed)`** — mulberry32: a 32-bit state, one multiply-xor-shift round per call, uniform in `[0, 1)`. Six lines, no dependency, and reproducible across platforms because every operation is on a `>>> 0` integer. Each device gets `createRandom(hash(EMULATOR_SEED, deviceIndex))`, so the fleet is reproducible as a whole and no two devices share a stream.

**`DeviceSession`** holds `deviceId`, `sessionId`, the next `seq`, the tick counter, the walk state, the last emitted `status`, the last emitted diagnostic condition, and `sessionStartedAt`. Its surface:

```ts
class DeviceSession {
  constructor(options: { deviceId: string; random: Random; now: () => number });
  start(): TelemetryMessage[]; // mints the next sessionId, resets seq, emits status online at seq 1
  tick(): TelemetryMessage[]; // the events due at this tick, in fixed order
  heartbeat(): TelemetryMessage[]; // a status message carrying the current state
  farewell(): TelemetryMessage[]; // status offline, once, at shutdown
  restart(): TelemetryMessage[]; // resets the walk and the counters, then calls start()
  readonly sessionId: number;
  readonly nextSeq: number;
}
```

Every method returns an array so the caller has one code path, and every returned message has already consumed its `seq`. `restart()` is `start()` plus a reset of the walk state and the counters — it does not mint the `sessionId` itself, so there is exactly one place that does. That place is here and nowhere else:

```ts
this.#sessionId = Math.max(this.#now(), this.#sessionId + 1); // 0 before the first session
```

which is consistency-spec decision 28 verbatim, and is the reason `restart()` is a method on the session rather than something the client does by constructing a new one.

**The walk.** Baselines are drawn once per device at construction:

| Value          | Baseline (healthy) | Baseline (faulty, 10 % of devices) | Per-tick step | Clamp |
| -------------- | ------------------ | ---------------------------------- | ------------- | ----- |
| `temperatureC` | uniform 32–48      | uniform 70–80                      | ±1.5          | 15–95 |
| `cpuPercent`   | uniform 5–40       | uniform 5–40                       | ±8            | 0–100 |
| `ramPercent`   | uniform 20–70      | uniform 20–70                      | ±4            | 0–100 |

Each tick: `next = clamp(prev + 0.1 × (baseline − prev) + uniform(−step, step))`, rounded to two decimals. The pull toward the baseline keeps the walk from drifting to a clamp and sitting there, which is what makes a stale overwrite visible as a jump. Faulty devices are drawn with `random.bool(0.10)` at construction — a named constant `FAULTY_DEVICE_PROBABILITY` in `generator.ts`, not an environment variable (decision 9).

`counters`, every fifth tick: `operationsTotal += random.int(0, 50)` (monotone within the session, starts at 0) and `uptimeMs = Math.max(0, now − sessionStartedAt)`. Both are cumulative per session, which is consistency-spec decision 6.

The clamp on `uptimeMs` is not decoration. `countersPayloadSchema` requires `z.int().min(0)`, so a clock that jumps backwards **past the session's own start** would otherwise produce a negative value, and ingest would reject a genuine event for a reason that has nothing to do with the event. With the clamp, a backwards clock costs monotonicity of a diagnostic-only field and nothing else — which is the named consequence in the failure table below.

`status`: the derived state is `degraded` when `cpuPercent > 90 || temperatureC > 75`, and returns to `online` only below 85 % / 70 °C. Inside `tick()` a message is produced **only when that state differs from the last one sent**. `heartbeat()` produces one unconditionally, carrying the current state; it is called only by the client's idle timer (decision 26). `offline` comes only from `farewell()`.

`diagnostic`: on the transition into `temperatureC > 85` → `{ severity: 'error', code: 'E_OVERHEAT' }`; on the transition into `degraded` → `{ severity: 'warning', code: 'E_DEGRADED' }`; otherwise `random.bool(0.02)` picks an `info` code from a small table (`E_CONFIG_RELOAD`, `E_NET_RETRY`, `E_CACHE_EVICT`). Messages are short fixed strings — the emulator never puts a device-controlled string of unbounded length on the wire.

**`Outbox`** is a FIFO of encoded frames paired with their `TelemetryMessage` (the message is kept for the drop log and for the type check in the drop policy). On `push` past `EMULATOR_OUTBOX_MAX`: scan from the head for the first entry whose `type !== 'diagnostic'` and drop it; if every entry is a diagnostic, drop the head. Returns what was dropped so the client can log it at `warn` with the dropped identity. The scan is O(n) in the worst case with n ≤ 1 000, and only on an already-overflowing outbox — named and accepted rather than split into two queues.

**`chaos.ts`** exposes `parseChaosModes(raw)` and a `ChaosPolicy` with three methods used on the send path:

```ts
apply(message: TelemetryMessage): TelemetryMessage[];  // what to enqueue now, in order
flushHeld(): TelemetryMessage[];                       // before a disconnect, and at shutdown
clearHeld(): void;                                     // on a restart: the messages are lost
```

`apply` is one rule with three branches, evaluated in this order:

1. `emit = duplicate fired ? [m, m] : [m]` — probability `EMULATOR_CHAOS_PERCENT` per message.
2. If something is **already held**, return `[...emit, ...held]` and clear the slot. The swap completes here, and the incoming message is never held in turn — so the slot holds at most one `apply` result and the reordering depth is always exactly one.
3. Otherwise, if `out-of-order` fired (same probability), store `emit` in the slot and return `[]`.
4. Otherwise return `emit`.

The two modes can both fire on one message: the duplicate pair is then held and released together, which is still an adjacent swap of the pair against the following message. Because `metrics` is produced on every tick, branch 2 always runs on the next tick — the held message can never be stranded, and `flushHeld` exists only for the two cases where there _is_ no next tick: a deliberate disconnect and shutdown.

The connection-level modes are a separate, stateless export from the same module:

```ts
// Which of the enabled connection-level modes fires next, and in how long.
// Returns null when neither `disconnect` nor `restart` is enabled.
nextConnectionChaos(): { mode: 'disconnect' | 'restart'; delayMs: number } | null;
```

`delayMs` is drawn uniformly in `[0.5 × EMULATOR_CHAOS_INTERVAL_MS, 1.5 × EMULATOR_CHAOS_INTERVAL_MS]` and `mode` uniformly among the enabled connection-level modes, both from the device's `Random`. `DeviceClient` calls it once at start and again after every connection-level chaos event, arming a single timer — so the schedule is as reproducible as everything else, and testable without waiting a minute for it.

### The impure shell

**`DeviceConnection`** is the state machine:

```ts
type ConnectionState =
  | { name: 'idle' }
  | { name: 'resolving' }
  | { name: 'connecting'; socket: net.Socket }
  | { name: 'connected'; socket: net.Socket; writable: boolean }
  | { name: 'backoff'; attempt: number; timer: NodeJS.Timeout }
  | { name: 'stopped' };
```

| From                       | Event                      | To                         | Side effect                                                  |
| -------------------------- | -------------------------- | -------------------------- | ------------------------------------------------------------ |
| `idle`                     | `start()`                  | `resolving`                | `dnsPromises.lookup` on every `INGEST_HOSTS` entry           |
| `resolving`                | addresses returned         | `connecting`               | `net.connect` to one pooled address picked uniformly         |
| `resolving`                | every lookup failed        | `backoff` (attempt + 1)    | log at `warn`                                                |
| `connecting`               | `'connect'`                | `connected` (writable)     | attempt := 0, log at `info` with the address, `onWritable()` |
| `connecting` / `connected` | `'error'` / `'close'`      | `backoff` (attempt + 1)    | log at `warn` with the reason and the outbox depth           |
| `connected`                | `write()` returned `false` | `connected` (not writable) | —                                                            |
| `connected`                | `'drain'`                  | `connected` (writable)     | `onWritable()`                                               |
| `backoff`                  | timer fired                | `resolving`                | —                                                            |
| any                        | `stop()`                   | `stopped`                  | clear the timer, `socket.end()` or `destroy()`               |

Every address of every `INGEST_HOSTS` entry is pooled and one is picked uniformly per attempt, and the lookup is repeated on every attempt — that is what spreads devices across ingest replicas and what lets a device find a replica that did not exist when it first connected (consistency spec, decision 15). The socket gets `setNoDelay(true)` (telemetry lines are small and latency matters more than packing) and `setKeepAlive(true, 30_000)` (so a silently dead peer is detected rather than held open forever). The backoff delay is `backoffDelay(attempt, random)` from the pure module, so the schedule is tested without waiting for it.

**Ownership of the pump.** The outbox belongs to `DeviceClient`, not to the connection: the connection knows about one socket, the client knows what there is to send. `DeviceConnection` therefore exposes only `write(frame): boolean` (the socket's own return value) and an `onWritable` callback it invokes on `'connect'` and on `'drain'`. The pump lives in the client: while the outbox is non-empty and `write` keeps returning `true`, shift and write; stop on the first `false` and wait for `onWritable`. This keeps the connection free of any knowledge of message ordering, which is what makes it testable on its own against a bare sink.

**`DeviceClient`** wires it together and owns two timers: the tick timer (chained `setTimeout`, first fire at a random phase) and the heartbeat timer (re-armed on every enqueue). On each tick it calls `session.tick()`, passes each message through `ChaosPolicy.apply`, pushes the results to the outbox, then runs the pump. It also owns the connection-level chaos timer when `disconnect` or `restart` is enabled; before a chaos `disconnect` it pushes `chaos.flushHeld()` into the outbox, and on a chaos `restart` it calls `chaos.clearHeld()` and empties the outbox.

`DeviceClient` constructs its `DeviceSession` and its `ChaosPolicy` **with the same `Random` instance**, so the chaos rolls come from the same seeded stream as the payload walk. That is what makes decision 4's promise — one seed replays the same fleet _and_ the same chaos decisions — true rather than approximate.

**`Fleet`** constructs the clients, starts them (each client's own random phase is the stagger — no extra sleep loop), runs the 10 s summary interval, and implements the shutdown drain, in this order:

1. Stop every tick, heartbeat and chaos timer, so nothing new is generated.
2. For each device: push `chaos.flushHeld()` into the outbox, **then** enqueue `session.farewell()`.
3. Run the pump and wait for every outbox to empty, or for `SHUTDOWN_TIMEOUT_MS`, whichever comes first.
4. **For every device whose outbox is still non-empty at that point, log at `warn`** with the device id, the remaining length and the connection state.
5. `end()` every socket and resolve.

Step 2's order is the point. SIGTERM stops generation, so `apply`'s branch 2 will never run again — a message held by `out-of-order` at that moment would be lost silently, with none of the `warn` line the outbox emits when it drops something. Flushing the slot before the farewell also keeps the farewell last on the wire, which is what makes it a usable end-of-session marker.

Step 4 exists because the drain is **best-effort, not guaranteed**, and the gap is not hypothetical: the backoff cap and the default shutdown budget are the same number (10 000 ms). A device that is in `backoff` when SIGTERM arrives — precisely the state a simulated ingest outage produces — may never get a writable socket before the deadline, and then its farewell and anything `flushHeld()` pushed in front of it are dropped. Every other loss path in this design logs what it lost; this one must too, or the emulator would quietly under-deliver in exactly the scenario it exists to exercise. It is named as T25 and in the failure table.

`loadConfig` already trims every value and treats an empty one as unset, so a `.env` copied from `.env.example` gets every default. The effective configuration is logged as the first `info` line; the emulator holds no credentials, so nothing is redacted beyond what the shared logger does anyway.

Two notes for the implementer:

- **`envInt` cannot express an upper bound.** It returns `z.coerce.number().int().min(min).default(value)` (`packages/shared/src/config.ts:29`), and `.max()` is not available on the `ZodDefault` that `.default()` produces: in zod 4.6.2, `ZodDefault<T>` extends `_ZodType` and `core.$ZodDefault<T>` and exposes only `unwrap()` and the deprecated `removeDefault()` (`node_modules/.pnpm/zod@4.6.2/node_modules/zod/v4/classic/schemas.d.ts:661–667`), while `.min()`/`.max()` are declared on the number schema (same file, lines 338–344) and are therefore gone once `.default()` has wrapped it. `EMULATOR_CHAOS_PERCENT` is written out as `z.coerce.number().int().min(0).max(100).default(5)` rather than through the helper. Widening `envInt` to take an optional maximum is the alternative; it touches a helper three services share, for one key, so it is not done here.
- **The device-id cross-check is a `superRefine` on the whole object**, not a rule on `EMULATOR_DEVICE_ID_PREFIX` alone, because it needs `EMULATOR_DEVICE_COUNT` as well. It formats the id of the last device and tests it against `DEVICE_ID_PATTERN` and `DEVICE_ID_MAX_LENGTH` from `@telemetry/shared`, and reports the issue on the `EMULATOR_DEVICE_ID_PREFIX` path so `ConfigError` names a variable the operator can act on. This replaces the "1–32 chars" cap the shared-contract spec documented (decision 27).
- **No cross-check between `EMULATOR_HEARTBEAT_MS` and `EMULATOR_EVENT_INTERVAL_MS`, on purpose.** A heartbeat shorter than the tick is not a misconfiguration: with the idle-only semantics of decision 26 the timer is re-armed on every enqueue, so a short heartbeat simply fires in the gaps and a long one never fires at all. Both ends are meaningful, neither breaks an invariant, so a `superRefine` here would reject a working configuration. Decision 23's cross-check exists because the other case produces a message the contract rejects.

## Consistency & Failure Modes

The emulator is the **source** of the identity and order metadata, not an enforcer of the rules. What it guarantees, and what it deliberately does not:

| Question                                        | The emulator's part                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Which metadata carries identity and order?      | It mints them: `deviceId` fixed per client, `sessionId` strictly increasing per device, `seq` starting at 1 and incrementing by one per message produced. Never reused — decisions 10, 12–15 are all written to keep this true under chaos.                                                                                                                                                                                                                          |
| How is "newer" decided?                         | Not here. The emulator only guarantees that a later-produced message has a strictly greater order key.                                                                                                                                                                                                                                                                                                                                                               |
| What is the dedup key, enforced where?          | `(deviceId, sessionId, seq)`, enforced in processing. The emulator _creates_ duplicates on purpose so the enforcement can be demonstrated.                                                                                                                                                                                                                                                                                                                           |
| Which operation is atomic?                      | None here. `seq` allocation is single-threaded inside one device object, which is all that is needed.                                                                                                                                                                                                                                                                                                                                                                |
| Redelivery / out-of-order                       | Produced deliberately (`duplicate`, `out-of-order`). The emulator asserts nothing about the outcome; step 7 does.                                                                                                                                                                                                                                                                                                                                                    |
| Emulator process crash                          | Everything in the outboxes is lost and every session ends. On restart, `sessionId` is re-minted from the wall clock — strictly greater than the previous one **unless the clock went backwards across the restart**, which is T1, already recorded.                                                                                                                                                                                                                  |
| Connection loss                                 | The session survives; `seq` continues; the outbox holds messages and is flushed on reconnect. Loss happens only when the outbox overflows, which is logged at `warn` with the dropped identity. **Outbox eviction is the emulator's only source of a genuine `seq` gap** — chaos never skips a number, it only repeats or reorders — and it is exactly what the consistency spec's gap log (`event.seq > lastEvent.seq + 1`, decision 27 there) is built to surface. |
| Emulator stopped while a device is disconnected | Best-effort: the drain waits `SHUTDOWN_TIMEOUT_MS` for a writable socket that may never come, then logs at `warn` per device with the remaining outbox length and gives up. The farewell and the flushed hold slot are lost with it (T25).                                                                                                                                                                                                                           |
| Ingest crash after a write                      | The message is gone. Device→ingest is fire-and-forget with no application-level acknowledgement (T3); the emulator does not retry a written message and cannot know it was lost.                                                                                                                                                                                                                                                                                     |
| Ingest unreachable                              | Retry forever with Full Jitter backoff, re-resolving DNS each attempt. Never exits (decision 21).                                                                                                                                                                                                                                                                                                                                                                    |
| Clock moves backwards mid-session               | `sessionId` is fixed for the session, so order is unaffected. `occurredAt` goes backwards and is diagnostic-only (consistency spec, decision 4). `uptimeMs` is clamped at 0, so a jump past the session start costs monotonicity of a diagnostic field rather than producing a negative value the schema would reject (T24). Neither is a state hazard: the order key is untouched.                                                                                  |

**In-process only.** `sessionId = max(now, previous + 1)` protects against a same-millisecond restart _within one process_ — which is the `restart` chaos mode, the case the code review flagged as A3. It cannot protect across a process restart, because nothing is persisted. That is T1's territory and the upgrade path is the same: clock discipline on the device, or a persisted counter.

## Scaling

One emulator process drives its devices from one event loop. The probe above puts the working limit at **5 000 devices at one message per second with no measurable event-loop cost**, and shows strain at 20 000 (p99 loop delay doubles) — with the receiving sink in the same process, so the real limit is higher.

The default `EMULATOR_DEVICE_COUNT` is 10, three orders of magnitude below that, so the concurrency model is not a constraint on anything the assignment asks for. `EMULATOR_EVENT_INTERVAL_MS` scales throughput independently: 10 devices at 100 ms is the same message rate as 100 devices at 1 s, but only the second spreads the load over 100 ingest connections.

The emulator scales **by device count, not by replicas** (T14): two `--scale emulator=2` replicas with the same `EMULATOR_DEVICE_ID_PREFIX` are two physical devices fighting over one state document. Running a second emulator service with a different prefix is the supported way to get more processes.

### Invariants (`CLAUDE.md`) and the emulator's part in each

| Invariant                                     | Where this design touches it                                                                                                                                        |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Logical order wins                         | The emulator _is_ the source of the order key. Decisions 10 and 12–15 exist to keep `(sessionId, seq)` strictly increasing and never reused under every chaos mode. |
| 2. Duplicates have no effect                  | Not enforced here — deliberately violated on the wire, so the enforcement downstream can be demonstrated rather than assumed.                                       |
| 3. Atomic state updates                       | Not applicable; the emulator writes no state.                                                                                                                       |
| 4. Parallel across devices, serial within one | Each device has its own connection, its own PRNG and its own `seq` space; nothing is shared between device objects except the logger.                               |
| 5. Minimal throughput cost                    | The emulator adds none: no acknowledgement wait, no per-message allocation beyond the frame, one pump per socket.                                                   |
| 6. Both services scale horizontally           | The emulator is not one of the two services. Its own scaling limit (by device count, not replicas) is T14 and is named in the README in step 8.                     |

## Alternatives Considered

### Chaos inside the generator

Rejected, and it is the most important rejection in this spec. Letting a chaos mode re-use or decrement `seq` would make the emulator violate the contract invariant that the entire storage design assumes (consistency spec, decision 28). Every duplicate would then be ambiguous: the pipeline could not distinguish "the same event arrived twice" from "two different events claim the same identity", and the second case has no correct answer. As a wire policy the hazards are exactly the ones at-least-once delivery really produces, and the invariant holds by construction.

### One shared ticker for the whole fleet

Rejected. A single `setInterval` walking the device array is fewer timers, but it fires every device in the same millisecond — a thundering herd that is both unrealistic and the worst case for the ingest socket buffers. The per-device chained timer with a random phase costs one timer per device (a heap entry) and spreads the load over the whole interval.

### Worker threads or one process per device group

Rejected as premature. The probe shows a single event loop handles 500× the default device count with no measurable cost. Adding a thread pool would also require partitioning device ids across threads and a way to aggregate the summary line, for no measured benefit. Recorded as T19 with the upgrade path.

### Persisting `sessionId` across process restarts

Rejected. It would remove T1 (a backwards clock across a restart), but it needs a writable volume per emulator container and turns the emulator into something with durable state — which is more than the assignment asks of a traffic source, and which the contract explicitly avoids by making `sessionId` the device clock (consistency spec, decision 2).

### Emitting invalid messages as a fifth chaos mode

Rejected. Ingest's rejection path (step 4) and its test (step 7) are better served by writing a known-bad frame directly to the socket in the test: it is one line, it is deterministic, and it does not put a code path into the emulator whose only purpose is to be wrong. The four chaos modes stay as the shared-contract spec fixed them.

### An acknowledgement protocol from ingest back to the device

Rejected here, as it was in the consistency spec (T3). It would remove the fire-and-forget loss window, but it changes the wire protocol from one-way NDJSON to a request/response protocol with its own correlation and timeout rules, in both the emulator and ingest. Out of scope for a traffic source; the loss window is named instead.
